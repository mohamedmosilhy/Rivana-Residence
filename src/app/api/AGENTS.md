# src/app/api: REST Route Handlers

The versioned REST API (`/api/v1/**`). Conventions: [docs/api/rest-api-conventions.md](../../../docs/api/rest-api-conventions.md); errors: [docs/api/error-model.md](../../../docs/api/error-model.md); endpoint list: [docs/api/api-contracts.md](../../../docs/api/api-contracts.md); build spec: [docs/specs/0001-m4-backend-foundations.md](../../../docs/specs/0001-m4-backend-foundations.md).

## Layout

- `v1/_http/`: the shared HTTP layer. `routes.ts` (`createRoutes`, `json`, `toHttp`), `problem.ts` (RFC 9457 bodies and the one code to status table), `body.ts` (`parseJson`, `validate`), `logger.ts` (one redacted line per request). `index.ts` wires the wrappers to `@/composition/api`.
- `v1/<resource>/route.ts`: one file per endpoint. `v1/health/route.ts` is the reference example; `v1/branches/**` and `v1/staff/branches/**` show public and staff resources (M5).
- `v1/_dto/`: view model → contract DTO mappers (e.g. `branches.ts`). DTOs are built from public view models, never from Prisma rows, so the API shows exactly what the pages show.

## Rules

- Every exported method is built from a wrapper: `export const GET = publicRoute(…)`, `staffRoute(…)`, or `webhookRoute(…)`. Never a bare `export async function`. The wrappers apply CSRF on unsafe staff methods, the 32 KB body cap, strict Zod validation (`422 VALIDATION` with `fieldErrors`), problem mapping, `Cache-Control: no-store`, `X-Request-Id`, and the log line.
- Pass `route` as the pattern (`"/api/v1/branches/[slug]"`), never the raw path. It is what gets logged.
- Public limiter wiring uses `RateLimiter` and `PublicRateLimitStore` for atomic fixed-window admission. Reuse `AVAILABILITY_RATE_LIMIT` for P5 across branches; P6 uses `QUOTE_RATE_LIMIT` for every request and `QUOTE_COUPON_RATE_LIMIT` through `publicRoute`'s `rateLimitAfterBody` only when the body sends a coupon code (it runs after the body validates). Missing trusted client addresses share an anonymous bucket. Staff sign-in keeps its separate throttle policy. Expired buckets of every public namespace (`PUBLIC_RATE_LIMITS`) are pruned through `npm run throttles -- cleanup-public` (see the deployment guide).
- P9/P10 use the `verification-request` (10/hour/client) and `verification-confirm` (20/10 minutes/client) buckets through `publicRoute`; composition lives in `@/composition/guests`. Both routes are public and global. Keep their bodies strict, filled honeypots generic within the body cap, and lock timeout details identical for guest and verification rows. The use cases own rolling phone limits, attempt commits and delivery after commit.
- P7 (`POST /api/v1/reservations`) uses the `booking-create` bucket (5/hour/client) through `publicRoute`, reads `Idempotency-Key` from the header (missing is `400 MISSING_IDEMPOTENCY_KEY`), and calls `createWebsiteReservation()` from `@/composition/reservations`. `manageUrl` is returned once on `201`, never on a replay. An online replay includes `checkoutUrl` only while the gateway session is live. P6 returns the quote use case's `paymentMethods` and drops any `phone` it is sent. The per phone coupon limit is enforced inside the booking transaction.
- P5 uses `_query/availability.ts` for numeric transport conversion and duplicate detection: missing/unknown/duplicate parameters are 400, while date, occupancy, quantity and stay values are checked by the application/domain and return 422. Its composition bypasses marketing caches and its DTO mapper exposes only public listing summaries, capped selectable quantity, and accommodation prices.
- Coupon management (S37–S39) uses `ManageCoupons`: Managers see only non-global coupons whose entire nonempty branch scope is assigned. Keep scope filtering and branch hydration in one database statement snapshot; separate Prisma relation reads can disclose foreign branch IDs during concurrent edits. PATCH reads and validates the merged state under the coupon row lock and commits joins plus audit atomically.
- Staff reservation creation (S3 and S4) requires `Idempotency-Key` scoped by staff actor and source. S1 defaults to the caller’s authorized branches. S2 returns the reservation version as `ETag`, and S15 uses an audit field allowlist. Reservation use cases own branch and guest-data access checks.
- S6, S9 and S55 read versions with `ifMatchVersion`. S6 passes field validation to the use case so an authorized, stale request with valid JSON gets `412` before field errors. S55 also checks the acknowledged change number under the reservation lock.
- G1, G3 and G4 GET use `publicRoute` with the `guest-read` bucket. G2 and G4 POST share `guest-request` (10 attempts per client per hour). Read tokens with `bearerToken(request.headers)`. The use case hashes the token and returns a uniform 401 for bad credentials on each access path. G4 GET rechecks the session after reading the detail snapshot. The manage link stays view only for a blocked phone. A session token may come from WhatsApp or email (M9-T12b); the use case resolves which (`sessionIdentity`), so the session routes never read a channel from the request. S50 to S53 (`/api/v1/staff/guests/**`) use `staffRoute`. S52 and S53 share one route file with `POST` and `DELETE` and both need a `reason`.
- G5 and G6 share separate client buckets across both guest access paths. G5 returns the reservation version in `ETag`. G6 reads it with `ifMatchVersion` and returns a new `ETag` on `200` or the same version on `202` for an open request. The use case enforces the rolling booking limit under the reservation lock. S56 to S58 use the `cancellations:decide` capability with branch scope. S57 stores the optional note in the internal audit, and S58 sends its reason to the guest.
- S28 and S29 share an empty strict query schema and the same status DTO. S28 returns 201 with branch status. S20 reads the last completed checkpoint through the inventory port. The reservation use cases enforce branch scope and own the deadline and checkpoint transaction.
- A handler parses, calls one use case, and maps the result with `toHttp`. Business rules, `authorize`, and `authorizeBranch` live in the use case, not here.
- No import from `@/infrastructure/**` or the generated Prisma client. Get use cases from `@/composition/*`.
- Each `route.ts` stays within 60 lines.
- Request and response schemas live in `src/contracts/api/v1` (Zod only) and are registered in `routes.ts` there. After adding or changing an endpoint, run `npm run openapi` and commit `docs/api/openapi.json`; a freshness test fails otherwise.
- P11 opts into `acceptTextJson` for browser beacons and `serverRequestId` to keep client supplied identifiers out of request logs. Both JSON media types use the same body limit and strict schema.
- Never log bodies, cookies, tokens, or `Authorization`. Only the logger's allow listed fields are written.
- `webhookRoute` keeps the raw bytes for signature checks and skips the session and CSRF checks; the use case must verify the signature.
- Tests: wrappers are unit tested over plain `Request` objects with `createRoutes` and fakes (`tests/unit/api/http-layer.test.ts`); D-10 is checked in `tests/unit/architecture/route-handlers.test.ts`.
