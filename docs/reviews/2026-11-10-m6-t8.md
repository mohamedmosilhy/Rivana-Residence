## Summary
The change adds the staff availability grid (API-S20: use case, contract, DTO, Route Handler, OpenAPI) and the `SearchAvailability` use case with no HTTP route, plus two read ports (`AvailabilityCatalog`, `LastSyncCheckpointReader`) and a batched `RateBatchReader.readMany`. The core rules are correct: `authorizeBranch` runs before any read, the window is parsed in the use case so calendar and length errors are 422 while unknown keys and missing params stay 400, the selectable quantity is `min(5, max(0, min free))`, refusal precedence is UNPRICED then OCCUPANCY then SOLD_OUT, the total is multiplied by the quantity even when sold out, branch today comes from the branch time zone, nothing is cached, and the search result carries no unit ids, labels, or raw counts. No blockers or majors; the findings below are a contract documentation gap, a few test assertions that would not catch plausible regressions, and a rare transient 404.

## Minor

### 🟡 S20 OpenAPI entry does not list the 400 it can return, `src/contracts/api/v1/routes.ts:245`
**Problem**: The route declares `errors: ["UNAUTHENTICATED", "FORBIDDEN", "NOT_FOUND", "VALIDATION"]`, but the `staffRoute` wrapper validates the query against `AvailabilityGridQuery` and returns `400 INVALID_QUERY` for an unknown key, a missing `from` or `to`, or a value that fails the `YYYY-MM-DD` regex (`src/app/api/v1/_http/routes.ts:211-219`). The integration test itself asserts those 400s (`tests/integration/reservations/availability.test.ts:240-243`). The public branch route at `routes.ts:109` already lists `INVALID_QUERY`, so the pattern exists.
**Why it matters**: The 400 versus 422 split is a deliberate contract (spec 0003, API surface), and the committed `docs/api/openapi.json` hides half of it from API clients. S24 (`routes.ts:259`) and S30 (`routes.ts:338`) carry the same omission from earlier tasks.
**Suggested fix**: Add `INVALID_QUERY` to the S20 errors list and regenerate OpenAPI; consider fixing S24 and S30 in the same pass or log it for a later task.

### 🟡 OCCUPANCY refusal is never tested with free units, `src/application/inventory/search-availability.ts:187`
**Problem**: The spec requires an occupancy mismatch to report `unitsAvailable: 0`. In the precedence test (`tests/unit/application/availability.test.ts:378`) the `small` listing is also full (`capacity: 0`), so its zero would come out of the capacity math anyway. The per unit occupancy test (`availability.test.ts:441`) has free units but asserts only `reason`. A regression that returned `unitsAvailable: selectable` or `available: true` alongside `reason: "OCCUPANCY"` would pass every test.
**Why it matters**: `unitsAvailable` is the only inventory signal the public sees; leaking real counts for a listing the guest cannot book weakens the disclosure rule and would mislead the T10 screen.
**Suggested fix**: In the occupancy test, assert `{ reason: "OCCUPANCY", available: false, unitsAvailable: 0 }` for the mismatched case while capacity is positive. The same applies to UNPRICED in unit tests (`availability.test.ts:420`); the integration test does cover that one at `tests/integration/reservations/availability.test.ts:324`.

### 🟡 Batched query count is not asserted against PostgreSQL, `tests/integration/reservations/availability.test.ts:247`
**Problem**: The approved task card requires an integration assertion that availability reads are batched, not per night or per listing. The unit tests count fake calls (`availability.test.ts:465-466`), which proves the use case calls each port once but not that `PrismaRateRepository.readMany` and `PrismaInventoryReader.readNights` issue a constant number of statements for many listings.
**Why it matters**: The spec names batching as a requirement ("Fetch listings, inventory, and rates in batches; avoid a query per night"); without a database level check a future adapter change could reintroduce N plus 1 silently. The `EXPLAIN (ANALYZE, BUFFERS)` capture is also still owed for the report.
**Suggested fix**: Count queries through a Prisma query event listener (or `pg_stat_statements` delta) around one search over several listings and a multi night stay and assert the count does not grow with listings or nights.

### 🟡 A listing deleted mid request turns the whole grid or search into 404, `src/application/inventory/get-availability-grid.ts:75`
**Problem**: The catalog read and the inventory read are separate statements. The CMS can delete a listing with no units (`src/app/admin/(protected)/rooms/actions.ts:53`). If that happens between `listRoomTypes` and `readNights`, the reader returns `NOT_FOUND` "The requested listing was not found." (`inventory-reader.ts`, the `foundIds` check), and both use cases propagate it (`get-availability-grid.ts:75`, `search-availability.ts:106`). Staff get a 404 on an existing branch; in T10 a public visitor would get a 404 for an active branch.
**Why it matters**: Rare and transient, but the error is wrong for the resource asked for, and the public 404 is the documented signal for a missing branch.
**Suggested fix**: Either note it as an accepted race next to the existing snapshot note, or treat the reader's missing listing failure in these two read use cases as "listing gone" (retry once or drop it) rather than returning it.

## Strengths
- Authorization order is right and tested: `authorizeBranch` precedes window parsing and every read, and the unit test proves no catalog or reader call happens for null, Editor, or wrong branch staff (`tests/unit/application/availability.test.ts:125-140`).
- The S20 400 versus 422 split is proved through the real Route Handler on PostgreSQL, including impossible date, zero and over 62 night windows, a missing param, and an unknown key (`tests/integration/reservations/availability.test.ts:230-243`).
- Disclosure is enforced by an allowlist test on result keys, and the refusal precedence, cap at 5, below zero clamp, scarcest night, and total times quantity even when sold out are each pinned.
- Branch isolation is checked by byte comparison of branch A's grid before and after writes in branch B, and the time zone test uses a UTC instant that is already tomorrow in Cairo.
- `readMany` covers base without periods, periods without base, inactive periods, and duplicate ids, with every requested id present in the map.

## Test coverage
Covered: grid authorization by role and branch, 401, 403, 404, 422 and 400 split, every status listing in `sortOrder`, zero unit listings with every night, blocks and inactive units, oversold integrity throw (unit), branch isolation, `no-store`; search 404 for missing and inactive branch, booking disabled allowed, all 422 inputs including stay policy and branch zone today, worked example $260.00 in unit and integration, UNPRICED partial price refusal, precedence, cap, quantity multiplication, published only, cross branch absence. Gaps: OCCUPANCY with free units (unitsAvailable and available not asserted), no database level batching assertion, no direct test that `readMany` itself excludes inactive periods, and no explicit HTTP test that an oversold grid becomes a redacted 500 (the throw is unit tested only). The task card's "injected sold contributions (future and past nights)" case is not present for the grid; sold flows only through the fake reader's counts.
