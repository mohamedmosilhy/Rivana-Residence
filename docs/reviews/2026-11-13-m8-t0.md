## Summary
The change retires `src/application/ports/` by splitting `repositories.ts` and `providers.ts` into seven module `ports.ts` files (`admin`, `booking`, `cache`, `content`, `enquiries`, `media`, `settings`) and three shared files (`shared/actor.ts`, `shared/providers.ts` with only `Clock` and `IdGenerator`, `PageRequest`/`PagedResult` added to `shared/pagination.ts`). It rewrites 71 importers and adds `tests/unit/architecture/ports-layout.test.ts`. I independently confirmed that this is a pure move. An AST comparison of every top-level declaration (leading comments and JSDoc included, whitespace and trailing commas ignored) gave **59 of 59 identical to HEAD**, with no declaration missing, extra, or duplicated. Every changed line in the 71 importers is an import line, every rewritten import keeps `import type`, and `docs/api/openapi.json`, `src/contracts`, and `prisma` are untouched. There are no blockers or majors. What I found is mostly about docs: the new rule text does not fully match the layout as built, and one live doc is stale. The new architecture test also has some blind spots.

## Minor

### 🟡 The rule text contradicts the layout as built, `docs/architecture/dependency-rules.md:18`, `:34`, `:35`
**Problem**: Line 35 says a port lives "in the module that consumes it" and that "the shared folder is the only common ground". The placement as built follows the owning module instead, as the card's own proposal did:
- `MediaRepository` lives in `media/ports` but is used by `src/application/content/catalog-queries.ts:9` and `src/application/public/public-site.ts:7`.
- `Room`, `Facility`, `PageRepository` and `SettingsRepository` are used by `public` (`public-site.ts:2-8`).
- `CacheInvalidator` lives in `cache`, a module that only defines it.

The text conflicts with the code in three more places:
- D-2 (line 18) still says application imports "only domain and its own ports", which these cross-module port imports now visibly break.
- Line 34 ("Do not import the other module's repository") is contradicted by the same imports.
- Before this change, `src/application/coupons/ports.ts:1` and `src/application/pricing/ports.ts:1` already imported `BranchScope` from `@/application/auth/authorize-branch`, a non-port file in another module. So "only common ground" is not true either.

The coupling is not new: the shared file used to hide it. The new paragraph, though, describes a rule the code does not follow.
**Why it matters**: M8 authors will follow this paragraph for every new reservation port. If the stated rule ("consumer owns the port") and the existing code ("owner module defines it, others import `<module>/ports`") disagree, the new ports will end up placed inconsistently, which is the drift this task exists to stop.
**Suggested fix**: Change line 35 to describe the placement as built. A port lives in the application module that owns the capability or data. Other modules import it only from `@/application/<module>/ports` (or that module's `index.ts`). Port files depend only on domain and `application/shared`, except for the existing `auth/authorize-branch` `BranchScope` type, which should be listed if it stays. Change D-2 to "imports only domain, its own ports, and other modules' listed ports or public files (D-8)". Change line 34 to match. If the owner really wants consumer-owned ports, that is a placement change and belongs in a separate decision, not in this refactor.

### 🟡 Stale live doc still lists `ports/`, `docs/learning/08-code-map.md:9`
**Problem**: The code map still says `application/  use cases per module; ports/, shared/ (Result, rate limit)`. The task updated `04-architecture.md` in the same folder but missed this file.
**Why it matters**: It points readers and agents to a folder that no longer exists and that the new test forbids.
**Suggested fix**: Replace that entry with something like "use cases and `ports.ts` per module; shared/ (Result, Actor, paging, Clock/IdGenerator, rate limit)".

### 🟡 `ports-layout.test.ts` misses some port-to-port dependencies, `tests/unit/architecture/ports-layout.test.ts:61`
**Problem**: I ran the test's regexes against sample sources. The "no port file imports another module's port file" check only matches the exact form `@/application/<m>/ports`. Three forms that set up the same dependency pass unnoticed:
- relative imports (`../media/ports`)
- the `.ts` suffix (`@/application/media/ports.ts`; the repo enables `allowImportingTsExtensions`)
- imports through a module's index that re-exports its ports (`@/application/branches`)

The index form is exactly how a type-level cycle between modules would come back. The "retired folder" check (line 47) also misses `await import(...)`, `vi.mock(...)`, and `typeof import(...)`. Line 31 already fails if the folder itself comes back, so that gap matters less. The check does work for the stated form: an `@/application/<m>/ports` import inside a port file fails it, multi-line imports and `export … from` included.
**Why it matters**: The test is the guardrail the docs cite, and M8 will add many port files. A cross-module port dependency written in any of these forms would pass CI.
**Suggested fix**: For port files, flag any import that resolves to another application module other than `shared`. Normalise relative paths against the file, strip a `.ts` suffix, and match `^@/application/(?!shared/)(?!<own module>)[^/]+(/|$)`. Then either allow-list `auth/authorize-branch` explicitly with a comment, or move `BranchScope` to `shared`. Moving it is a type move, so it should be a later task and needs approval.

## Nits
- ⚪ `src/application/media/media-library.ts:14-15` and `src/application/enquiries/list-enquiries.ts:13-17` import from `@/application/shared/pagination` twice (once with `import type`, once for values). They could merge into one `import { parsePageNumber, type PagedResult }`. `catalog-queries.ts:10/14` does the same.
- ⚪ `tests/e2e/fixtures/public-content.mts:8` now uses the `@/` alias, while every other import in that file uses the relative `../../../src/….ts` form. It works only because Node erases type-only imports. Keeping the relative form (`../../../src/application/shared/actor.ts`) would match the file's style.
- ⚪ `tests/unit/architecture/ports-layout.test.ts:36` counts only `export interface|type` names in `shared/providers.ts`. An `export const`, `class`, or `export { … } from` added there would slip past the "only Clock and IdGenerator" check.
- ⚪ `docs/delivery/milestones/m8-reservations.md:90` (item 13): `Hasher` went to `media`, its only consumer, rather than `auth` as item 3 proposed. That is the better home, but item 13 does not record the change. Items 3, 7, 9, and 10 still describe keeping `src/application/ports/`. A short "(superseded by item 13)" marker would stop readers from following them.

## Strengths
- The move is verbatim. All 59 declarations, JSDoc included, match HEAD exactly, and there are no stray edits in any importer.
- No cycles were added. The new module port files import only domain, `zod`, and `application/shared/{result,actor,pagination}`. None of the shared files imports from a module, and every cross-file reference is `import type`, so nothing new happens at runtime.
- Placement is sensible: `CacheInvalidator` sits next to `CACHE_TAGS`, `Hasher` with its only consumer, and `Actor` and the paging types in `shared` next to `Result`. The shared set really is small.
- Gates I ran myself: `tsc --noEmit` is clean. `vitest run tests/unit/architecture` passed 6 files / 103 tests, including `module-boundaries.test.ts` (D-8 unchanged for the reservation-era modules). `eslint` is clean on the new files.

- Minor, `docs/learning/08-code-map.md`: fixed.
- Minor, port to port check too narrow: replaced with an allow list (domain, zod, `application/shared`, `auth/authorize-branch`) so relative imports, `.ts` suffixes, and index imports are all refused. Mutation checks: adding `../media/ports` to a settings port file and recreating `src/application/ports/` both fail the suite, then reverted.
