# Review, m10-guest-booking-journey (M10-T6), 2026-11-27

**Reviewed by**: Claude Opus 5.5 (claude-opus-5-5), fresh context (author on a different session/model)
**Scope**: 30 files (25 source, test and doc files plus the screenshot folder), uncommitted
**Verdict**: Changes requested

## Summary
M10-T6 replaces the "payment coming soon" placeholder with step 4 (payment choice), step 5 (review, consent, submit), the P7 outcome paths, and a new `/{branch}/book/confirmed` page that rechecks the booking through G1 before it says "Confirmed". The core safety properties hold. A `useRef` guard stops a double click. The idempotency key is tied to the exact request body, kept across retries and regenerated after a price acceptance. `location.replace` keeps the details page out of history. The manage token goes only into tab storage, and is checked against branch and reference before it is used. The browser never computes a total. I found no path that books twice or shows "Confirmed" for anything other than a `CONFIRMED` G1 answer. The one Major finding is test coverage: several submit error branches that the task card names as edge cases have no test. The Minor findings are about state left over when a guest moves between steps (an old price carried across steps, and a price change after a method refusal that is never flagged), a misleading message for `PAYMENT_UNAVAILABLE`, focus being lost, and the raw seconds in the rate-limit message.

## Major

### 🟠 Several submit error branches have no test, `src/presentation/features/booking/booking-checkout.tsx:277-362`
**Problem**: Unit tests cover `BOOKING_LIMIT_REACHED`, `BRANCH_NOT_BOOKABLE`, `PHONE_BLOCKED`, `PHONE_NOT_VERIFIED`, `COUPON_INVALID` and the `PRICE_CHANGED` path where the first price check fails. E2E covers the double click, the lost reply followed by a replay, `INVENTORY_UNAVAILABLE`, `PRICE_CHANGED`, `PAYMENT_METHOD_UNAVAILABLE`, `RATE_LIMITED` and the closed branch. Nothing exercises these branches:
- `SERVICE_UNAVAILABLE` at submit (lines 318-326). This is the "service refused at submit" edge case in the task card. It forces `priced.key = ""` so extras prices again, and the logic is not obvious.
- A `201` when tab storage is blocked (lines 284-290). `saveBookingResult` returns false, so the guest must see the receipt with the reference, and with "Continue to payment" for an online booking, instead of being sent away. The task card lists "blocked browser storage" as an edge case. Only `saveBookingResult` itself is tested.
- `uncertain` followed by `RATE_LIMITED` (line 294). The screen must stay locked and keep offering "Retry same booking", and the key must be kept.
- `ONLINE_PAYMENT_REQUIRED`, `VALIDATION`, and the default branch for `PAYMENT_UNAVAILABLE`, `TRY_AGAIN` and `INTERNAL`.
- A `201 AWAITING_PAYMENT` saved to storage, then `location.replace(checkoutUrl)`, at unit level. E2E covers it only in the opt-in provider run.
**Why it matters**: The task is CRITICAL. These branches decide whether a booking that was already saved is shown, retried with the same key, or lost from the guest's view. A regression in any of them would only show up in production.
**Suggested fix**: Add journey unit tests with `createReservation` mocked for each branch:
- `SERVICE_UNAVAILABLE` with `context.kind` returns to extras with the removal notice and prices again.
- With storage blocked, a `201` shows the receipt and does not navigate. Spy on `location.replace`.
- `NETWORK` then `RATE_LIMITED` stays on "Retry same booking" with the same key.
- `PAYMENT_UNAVAILABLE` keeps the key on retry.
- `VALIDATION` shows the server's field messages.

## Minor

### 🟡 A price change found after a method refusal is never flagged, `src/presentation/features/booking/booking-checkout.tsx:201-219`
**Problem**: On `PAYMENT_METHOD_UNAVAILABLE` or `ONLINE_PAYMENT_REQUIRED`, `refreshPrice("method")` calls `onChange(next)` (the new quote) before it returns to the payment view. When the guest continues, `refreshPrice("payment")` compares the already replaced quote with a fresh one, finds them equal, and opens review with no "Accept new total", even if the total changed after the refusal.
**Why it matters**: The task card says that if the price changes, the guest must see the old and new totals and accept before submitting again. The new total does appear on review, so no wrong amount is charged. But the explicit comparison the card promises is skipped on this path.
**Suggested fix**: In the method path, compare `quote.total` with `next.priced.quote.total` before returning. If they differ, set `oldPrice` so that the next arrival at review needs acceptance.

### 🟡 `oldPrice` survives leaving the checkout, `src/presentation/features/booking/booking-checkout.tsx:135-140, 300-304`
**Problem**: `PRICE_CHANGED` sets `oldPrice` before `refreshPrice("conflict")`. If that check removes a coupon or service (`back(next)`) or changes the method (back to the payment view, where "Back to extras" is enabled), `oldPrice` is kept in the journey state, because `back()` does not clear it. Later, review shows "The price changed from X to Y", where X is the total from before the guest's own edits on extras. While `oldPrice` is set, `onLock(false)` also leaves "Change selection" visible.
**Why it matters**: It fails safe, since acceptance is still required, but the comparison it shows is misleading. This is the "state left over between steps" edge case.
**Suggested fix**: Clear `oldPrice` in `back()`, or set it again from the total the guest last saw on review.

### 🟡 No way out from the price-change alert except accepting, `src/presentation/features/booking/booking-checkout.tsx:514-535`
**Problem**: While `oldPrice` is set, the screen offers only "Accept new total". "Back to payment" is disabled (`frozen`), the cross-sell buttons are disabled, and `onLock(true)` hides "Change selection" in the price panel.
**Why it matters**: A guest who does not accept the higher price has no way to leave or change their choices on the page, other than browser navigation, which also loses the in-memory choices.
**Suggested fix**: Add a secondary "Change my choices" action next to Accept. It should call `back(extras)` and clear `oldPrice`. Or keep "Change selection" visible while only `oldPrice` is set.

### 🟡 `PAYMENT_UNAVAILABLE` is reported as "couldn’t verify the result", `src/presentation/features/booking/booking-checkout.tsx:355-361`
**Problem**: `openWebsiteCheckout` returns `PAYMENT_UNAVAILABLE` only after the booking has committed (or after a replay matched). The booking definitely exists and is `AWAITING_PAYMENT` with a hold. The default branch tells the guest "We couldn’t verify the result", and each retry uses one of the 5 per hour `booking-create` admissions.
**Why it matters**: Keeping the key and offering a retry is the right behavior. But the wording hides that the units are held now and the hold ends in about 15 minutes. With a 5 per hour bucket, a guest can easily hit `RATE_LIMITED` while the hold runs out.
**Suggested fix**: Add a separate case that keeps `uncertain` and the key, with wording such as "Your booking is saved, but the secure checkout could not open. Try again in a moment or contact the hotel."

### 🟡 Focus is lost when the price-change controls disappear, `src/presentation/features/booking/booking-checkout.tsx:503-535`
**Problem**: "Check price again" and "Accept new total" unmount themselves when they succeed. The heading focus effect depends only on `[view, receipt, contactOnly]`, so focus falls to `<body>`. Keyboard and screen reader users lose their place right before the submit button.
**Why it matters**: AC 9 requires that every step works by keyboard.
**Suggested fix**: After acceptance, move focus to the "Total with VAT" line or to the submit button. After a successful new check, move it to the alert. Use a ref plus an effect on `oldPrice` and `needsQuote`.

### 🟡 The rate-limit message shows raw seconds, `src/presentation/features/booking/booking-checkout.tsx:341-345`
**Problem**: "Too many attempts. Try again in 3540 seconds." P7's bucket is 5 per hour per client, so `Retry-After` is often in minutes or close to an hour. The extras step already formats waits with `waitText` from `verification-state`.
**Suggested fix**: Use `waitText((problem.retryAfter ?? 60) * 1000)` for consistency.

### 🟡 Reloading after a lost reply can create a second booking, `src/presentation/features/booking/booking-checkout.tsx:122-123, 270-272`
**Problem**: The idempotency key is kept in component state, as the spec intends. If the guest reloads or goes Back while "Retry same booking" is shown, the key and the verification token are lost. The draft was not cleared, so the details are filled in again. After a new verification (a new token, a new body, a new key), a second booking can be created even though the first one may have committed.
**Why it matters**: This is the "reload or back navigation" edge case. The server's per phone booking limit only partly stops it.
**Suggested fix**: This is within the spec, so it is an owner decision. The cheapest mitigation is a `beforeunload` prompt while `busy || uncertain`. Alternatively, record it as a known limit in the spec's T6 "Settled during" section.

## Strengths
- One booking per submission is protected at two levels. `sending.current` stops a same-tick double click (E2E clicks twice in one event-loop task and asserts one row). The key is regenerated only when the serialized body changes, and is reset explicitly after `PRICE_CHANGED` and "Accept new total". E2E checks that the replay reuses the original key and that PostgreSQL holds exactly one reservation.
- "Confirmed" is shown only for G1's `CONFIRMED`. The confirmation page rejects stored results from another branch or with another reference, maps 401 and 404 to the neutral message without showing the reference, and the test asserts the token never reaches the DOM. The token is taken from `manageUrl` with a strict 43-character base64url pattern and sent only as a bearer header.
- A replay (`200`) never carries an earlier booking into the next screen (`keepMatchingResult`). A blocked-storage `201` falls back to an on-page reference instead of a dead end.
- The payment step narrows correctly to online-only for email verification. Marketing is hidden and not sent for email bookings. The placeholder policy copy and consent versions are made launch blockers in `audit:content` from one shared source.
- The T5 follow-up is done: away from the extras step, the price panel says "no longer available" or "Online booking is unavailable" instead of "updates on return", with tests for both.
- The visual changes hold up at 390 px in the screenshots: the fact grid wraps, long emails break, and the full-width primary button and the 44 px+ choice cards are kept. Prices and references in the body face with `tabular-nums` are clearer.

### Recheck 2: warning before reload (Minor 7), 2026-11-27

**Rechecked by**: Claude Opus 5.5 (claude-opus-5-5), read-only, targeted Vitest only (E2E was running elsewhere)
**Verdict**: Approve with nits. Minor 7 is **resolved** within the browser's limits. No Blocker, Major or Minor remains.

I read `booking-checkout.tsx` again (the `unsettled` ref, the `beforeunload` effect, and the updates in `submit()`), the new unit tests at the end of `tests/unit/public/booking-journey.test.tsx`, and the lost-reply E2E change. The four booking unit files pass: 76/76.

**When it asks.** `unsettled` becomes true just before the P7 request (line 304). After the answer, it stays true in two cases only: the result is unknown (the default branch, line 391: `NETWORK`, `UNEXPECTED_RESPONSE`, `TRY_AGAIN`, `INTERNAL`, `PAYMENT_UNAVAILABLE`), or a rate limit arrives while an earlier result is still unknown (lines 309-310). The value is computed in the render where "Retry same booking" was clicked, so `uncertain` is current. That is exactly the window in which a reload would lose the request key. The tests cover the request in flight, unknown result → rate limit → still asking, and success.

**Paths that must not ask, checked:**
- Success, both `/book/confirmed` and the hosted `checkoutUrl`: `unsettled` is set from the answer before any `replacePage`, so it is false on every `201` or `200` path. The unit test records `asksBeforeLeaving()` inside the mocked `replacePage` and gets `[false]`.
- Sold out (`INVENTORY_UNAVAILABLE`): false before `unavailable()`. This is correct, because the server checks for a replay under the key first, so this answer proves nothing was saved. The same holds for the `unavailable()` call inside `refreshPrice` after `PRICE_CHANGED` or a method refusal. **There is no unit assertion for this path.** It uses the same line as success, so the risk is low (nit below).
- Definite refusals (`PRICE_CHANGED`, `PHONE_NOT_VERIFIED`, `COUPON_INVALID`, `SERVICE_UNAVAILABLE`, `VALIDATION`, a first-time `RATE_LIMITED`, `BOOKING_LIMIT_REACHED`, `BRANCH_NOT_BOOKABLE`): false. These are correct because P7 looks for a replay before the token check and again under the guest lock, so none of these answers can hide a committed booking under the same key. Three of them are tested.
- The receipt and the "Search again" or "Continue to payment" links after a replay: false, as they should be, because the booking is settled.

**Paths that do not ask, as expected:** none inside the component. While `uncertain` is set, every in-component exit is disabled ("Back to payment", the cross-sell buttons) or hidden ("Change selection"), so the component cannot unmount and drop its listener while unsettled. The E2E really fires the native dialog (`page.close({ runBeforeUnload: true })`), dismisses it, and then the same key replays to exactly one row. That proves the real event, not only the handler.

**The known-limit wording is accurate.** Additions worth stating where the limit is recorded:
- Soft navigation through the site's header, menu and footer `next/link` links, and Back or Forward between soft-navigated history entries, do not fire `beforeunload`. The page then unmounts and the key is lost. This is correct for the App Router, which has no route-change guard.
- iOS Safari does not show the dialog at all, and some Android browsers show it only sometimes. Closing the app or a crash also skips it.
- Browsers show only their generic text, and show it only after the user has interacted with the page. Clicking "Confirm booking" counts, so the dialog will appear where it is supported.
- In every case the server's per phone booking limit is the remaining backstop.

**Price-change box.** It is now `role="group"` with `aria-labelledby` (the title) and `aria-describedby` (the old and new totals), and it receives focus. A screen reader reads the label and totals once on focus, so the earlier double-announcement nit is resolved.

New nits:
- ⚪ `booking-checkout.tsx:132-140`, the `beforeunload` listener is registered for the whole time the checkout is mounted, not only while `unsettled`. Chrome no longer refuses the back/forward cache for this, but Firefox has historically treated any `beforeunload` listener as a reason to skip it, and web.dev advises adding the listener only when needed. Add it at the start of `submit()` and remove it when the result settles. Low impact here, because `location.replace` already keeps the details page out of history after a booking.
- ⚪ `tests/unit/public/booking-journey.test.tsx`, add a case with `INVENTORY_UNAVAILABLE` (and the online `201` redirect) that asserts `asksBeforeLeaving()` is false inside `replacePage`, so the sold-out and checkout redirects are covered as explicitly as the confirmation redirect.

Still open overall: only nits (the ones left as they are on purpose, plus the two above).
