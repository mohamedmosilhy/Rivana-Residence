## Summary
This adds service edits to S6 `ModifyReservation`. A supplied `services` list is the full selection, and an omitted list keeps all services. The plan is computed in the domain (`planServiceChanges`). Pricing is split into a new `priceChangedServices` module. `replaceStay` now reconciles service rows by kind and can skip room and night rewrites when `lines` is `null`. I found no correctness, privacy or concurrency defect. Stale-version precedence, lock order, the retained-price guard in the repository, no-flight-text history and audit, and no-op, external and started-stay rules all follow the approved card. The headline issues are test gaps that would let some meaningful regressions through, plus one ambiguity about car-count changes on inactive offerings.

I did not run any tests or gates (read-only review). The verification numbers in your message are taken as given.

## Minor

### 🟡 Started-stay service-only edit on a per-person-per-night service is untested, `tests/integration/reservations/change-reservations.test.ts` (test "keeps arrival-day changes available and permits only details corrections…")
**Problem**: The started-stay test uses only a transfer (PER_VEHICLE). The card requires keeping the T9 consumed per-person-per-night charges. The code path for that is the `preservedPersonNights` branch at `reservation-change-services.ts:94-119`. For a service-only edit it now runs with an unchanged stay and unchanged guests, and the new tests never reach it. The T9 coverage exercises it through stay or occupancy changes, not service-only details edits.
**Why it matters**: This is money logic on a Critical-tier task. A regression such as a wrong `consumedNights`, or an `occupancyEffectiveFrom` reset to `today` or `null`, would silently change breakfast totals on in-house guests. It would surface as PRICE_CHANGED on every details correction, or as a rewritten total, with no failing test.
**Suggested fix**: Add a case with a started stay holding BREAKFAST (and the transfer). Edit only the transfer details, send the stored total as `acceptedTotal`, and assert the totals, `adultQuantity`, `childQuantity` and `occupancyEffectiveFrom` are unchanged. Add a variant with a prior occupancy change, so `occupancyEffectiveFrom` is non-null.

### 🟡 "Service-only skips inventory and nightly rate reads" is not actually asserted, `change-reservations.test.ts` (test "lets staff correct flight details and remove a service without rewriting rooms or prices")
**Problem**: The `xmin` comparison correctly proves room and night rows are not rewritten. Nothing proves inventory or rates are not read. The fixture keeps inventory available and the base rate present, and it deactivates only the physical rooms. A mutation that always runs the `plan.structureChanged || override` block (`modify-reservation.ts:381`), or always runs `currentRates`, would still pass.
**Why it matters**: The card makes skipping those reads a requirement. A service-only edit that fails with INVENTORY_UNAVAILABLE for a sold-out or rate-less future night would be a user-visible regression.
**Suggested fix**: In one service-only case, make the listing sold out for the stay (or add a block) and/or remove the base rate. Assert the edit still succeeds. Optionally add the contrast case that a combined edit still fails.

### 🟡 Car-count changes on an inactive retained offering are allowed, `src/application/reservations/reservation-change-services.ts:60-71`
**Problem**: The changed-cars path looks up the current offering by kind and uses its `maxVehicles` without checking `active` (unlike `selectService`, which does). The card allows details-only edits on an inactive offering and requires `SERVICE_UNAVAILABLE` for new selections. It does not say whether changing the car count of a retained service on an inactive offering is allowed.
**Why it matters**: Today an inactive transfer offering can still have its car count raised up to the stale `maxVehicles`. For a PER_VEHICLE booking that increases the price by the stored unit price. That is probably not intended, and the behavior is untested either way.
**Suggested fix**: Confirm the intended rule with the owner. If an inactive offering should refuse car changes, require `active` here and return `serviceUnavailable`. Either way, add a test that pins the decision.

### 🟡 `SERVICE_UNAVAILABLE` is tested only for a missing offering, `change-reservations.test.ts` (first modified test, around `services: ["BREAKFAST"]`)
**Problem**: The 409 case uses a kind that has no offering row. The inactive-offering add path and the `maxVehicles === null` transfer path (`selectService` in `service-offering.ts`) are not covered for S6. The HTTP mapping for this code on the stay route is also only indirectly covered.
**Why it matters**: The card specifically says an unavailable new selection returns 409 `SERVICE_UNAVAILABLE`. An inactive offering is the common real-world case.
**Suggested fix**: Add an add-service case with an inactive offering, asserted through the route (409 and code), with `state()` unchanged afterwards.

### 🟡 PRICE_CHANGED for a service change does not assert "no write", `change-reservations.test.ts` (test "keeps stored transfer pricing terms and adds breakfast…")
**Problem**: The test checks the 409 body and then performs the successful PUT. It never asserts that the reservation state, version, history, audit and service rows were unchanged between the two calls. The earlier general "refuses a wrong accepted total…" test does check state, but only for a no-services request.
**Why it matters**: A defect that persisted the added service before the total comparison would still pass here. The ordering at `modify-reservation.ts:552` versus the mutate step is currently safe, but the evidence test cannot detect a regression.
**Suggested fix**: Capture `state(booking.id)` and the service row count before the 409 call and assert equality after it.

## Nits
- ⚪ `src/domain/reservations/reservation-change-plan.ts` (the new `planServiceChanges` and the `started && selectionOrCarsChanged` check, around lines 74-105 and 247-256), line numbers approximate: the `services` path is used for both the car and selection rejection and the details-only case. The message "Once a stay has started, only service details can be changed." is clear, but the plan never reports which kind was rejected. A per-index path (`services.N`) would help staff.
- ⚪ `src/application/reservations/reservation-change-services.ts:57-59` throws a plain `Error` for a missing retained line. It is an unreachable invariant, but the function otherwise returns `Result` and throws `DomainValidationError` (`:87`). That mixes three error styles in one 100-line function. Consider a comment that says the plain throw is an invariant.
- ⚪ `src/application/reservations/modify-reservation.ts:174-178` and `src/application/reservations/ports.ts` doc comments now exceed the surrounding wrap width.
- ⚪ `docs/api/openapi.json` (the `services` description, via `src/contracts/api/v1/reservations.ts:152`) does not mention that external reservations cannot have services, or that only stored PER_VEHICLE terms change price when cars change. The Stage 7 topic-doc pass can cover this.

## Strengths
- **Locks and ordering**: Version, authorization and `PRECONDITION_REQUIRED` precedence are unchanged. Listing locks are sorted and taken before the reservation row. Offerings are read only after the locks and only when needed (`needsOfferings`, `modify-reservation.ts:498`).
- **Retained pricing**: `priceChangedServices` builds retained lines only from stored `unit`, `priceMinor` and `childPriceMinor`. The repository then re-checks that retained rows still match those stored price terms (`reservation-repository.ts`, "A change cannot alter a retained service price."). Immutability is enforced twice, and the integration test covers a changed current offering price.
- **Car-limit grandfathering**: The limit is applied only when `changedVehiclesAt !== null`. Unchanged over-limit cars are grandfathered, and details-only edits on an inactive offering do no offering lookup at all.
- **Privacy**: Audit and history carry only `kind`, `vehicles` and a `detailsChanged` boolean. The integration test spies on `console.info`, `console.warn` and `console.error`, and checks `JSON.stringify` of changes and audit rows for the flight text.
- **Service-only writes**: `lines: null` plus the `xmin` assertion shows rooms and nights are not rewritten. Retained service rows are updated in place only when a field differs.
- **Concurrency and rollback**: Repeated lock-race tests (20 rounds) and a rollback test that throws in audit after the mutate step. The seed adds an editable transfer to the entered fixture, with the idempotency test updated.

## Test coverage
Covered: combined stay and services edit, including the 409 breakdown and the reuse of the old coupon and VAT; a service-only details edit with unchanged room and night rows; one history row and one audit row; the hotel-system flag; service removal; the car limit, including grandfathering; duplicate, breakfast-with-cars and bare-string validation errors; stale, foreign and anonymous requests; external ineligibility; started-stay details-only edits (rejecting removals, car changes and adds); rollback; and 20-round same-version races. There are also unit tests of the plan and an end-to-end S6 flow with a no-flight-text history check.

Gaps are listed in the Minor section. In order of importance:
1. Started-stay service-only edit on a per-person-per-night service.
2. Proof that service-only edits skip inventory and rate reads.
3. `SERVICE_UNAVAILABLE` for an inactive offering.
4. A no-write assertion on the PRICE_CHANGED path.
5. The inactive-offering car-change decision.

Items 1 and 2 are worth closing before acceptance given the Critical tier. The remaining items can follow.

## Keyboard test follow-up

**Verdict: Approve.** I have no blocking findings. This is read-only static review. I did not run the e2e suite, and I rely on your scratch-copy reproduction for the root cause.

**Scope checked.** The diff is one added `await page.goto("/admin");` plus a comment, in `keyboard users can reach content and the account menu` (`tests/e2e/admin-shell.spec.ts:146-148`). Every assertion is unchanged, and no `test.skip` was added. The mobile run is still covered, since the test has no `isMobile` guard. No product code is touched.

**Correctness.**
- `signInAs` (`tests/e2e/support/session.ts:6-13`) returns once the URL matches `/admin`. That is the client-side redirect state your scratch run showed to be bad. A fresh `goto` gives a new document that tabs from the top of the page, and your 3/3 mobile pass with this setup supports that.
- `goto` waits for the `load` event. The skip link is then asserted with `toBeAttached()` before the first `Tab`, which is a reasonable readiness check.
- After sign-in the session cookie is already set, so `goto("/admin")` does not bounce back to the login page.

**Findings (non-blocking).**
1. **Comment is accurate but thin.** `// Start tabbing from a fresh document after the sign-in redirect.` doesn't say why. A reader could delete the line as a redundant second navigation. Suggest one clause on the cause, for example: "after a client-side redirect, the first Tab can skip the skip link (focus stays on BODY and Tab lands on the first overview link)". I would not claim a Chromium-specific cause in the comment, because your reproduction doesn't establish one.
2. **The product behaviour behind the failure is not asserted anywhere.** A real keyboard user who signs in and then presses Tab can land on the Pages link and miss the skip link. This change makes the test pass but hides that case. If the owner considers it a real accessibility gap, it should be recorded as a follow-up, not left only in a test comment. I'm not asking for a product change in this task.
3. **Minor: the `returnTo` parameter doesn't help here.** `signInAs(..., "/admin")` already defaults to `/admin`, so the extra `goto` is the only mechanism that gives a fresh document. It is fine as is. Don't try to fold it into `signInAs`, because other tests rely on the redirect state.

**Residual risk.** The failure was reproduced on mobile only. Desktop was not shown to fail, and it passes with the extra navigation either way. Nothing further is needed there.

The test comment now explains the observed tab order after sign-in. The approved follow-up covers keyboard navigation from a fresh authenticated document.
