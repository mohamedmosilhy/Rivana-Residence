## Major

### 🟠 The current readiness gate rejects an already issued email token, `src/application/reservations/create-website-reservation.ts:221`

**Problem**: P7 checks the current global channel readiness after it has already authenticated a live booking token. If an Admin turns email verification off after issuing an email token, and WhatsApp is unavailable, `verificationUsableForBranchNow` returns false and P7 responds with `409 BRANCH_NOT_BOOKABLE` and reason `VERIFICATION_NOT_CONFIGURED`. A focused real PostgreSQL reproduction returned exactly that response, wrote no reservation, and left the token unconsumed while the gateway and branch online payment flag were both ready. Decision 9 says that turning the switch off stops new codes, while codes and booking tokens already issued may still be confirmed and used until they expire. The same section also says branches stop taking bookings when no channel is ready, so the governing text conflicts. The behavior is inherited from `HEAD`: the previous `anyVerificationChannelReady` call at the same P7 gate also returned false in this situation. M9 T12c does not create the regression, but its changed readiness rule keeps the conflict unresolved and its tests do not pin either interpretation.

**Why it matters**: A guest can successfully request and confirm an email code, then lose the promised 30 minute booking window because an Admin changes the switch. The server returns a branch configuration error even though the guest presents a valid bearer token and online payment is available. Silently choosing the other interpretation would also weaken the emergency branch gate, so this needs an owner decision rather than an incidental code change.

**Suggested fix**: Ask the owner which rule wins. If issued tokens may finish, make P7 treat an authenticated live email token as usable when online payment is available, even when the A9 issuance switch is now off, while A3 and P9 continue to use current readiness. Add a real PostgreSQL test that issues and confirms the email token, turns the switch off, proves P9 is blocked, and proves P7 can still create the online hold. If turning the switch off must stop every new booking, keep the code and update Decision 9, ADR 031, and the API contract to remove the promise that issued booking tokens may finish, then add a test for the refusal.
