## Summary

The change adds the M6 `inventory_and_rates` migration (four tables, `BlockReason`, `btree_gist`, CHECKs, two partial GiST exclusion constraints, same-branch composite FKs with `ON UPDATE/DELETE RESTRICT`), a create-only demo inventory seed step, and a thorough set of real-PostgreSQL constraint tests. ## Major

### 🟠 Topic data model not reconciled with the approved schema refinements, `docs/database/data-model.md:5`, `:255-299`, `:609-641`
**Problem**: Spec 0003 (Data model section, "These schema refinements were approved with this spec; reconcile the topic data model during T3") assigns this reconciliation to this task. Only the status table rows (lines 28-29) were updated. The model sketches and the SQL-only block still show the old design:
- `PhysicalRoom` has no `@@unique([id, branchId])`.
- `InventoryBlock` has no composite FK `(physicalRoomId, branchId) → PhysicalRoom(id, branchId)`.
- `RoomBaseRate` and `RatePeriod` have no `currency CHAR(3)` column.
- The CHECKs at lines 609-610 and 621 omit `currency = 'USD'`.
- Nothing mentions `ON UPDATE RESTRICT` on the ownership FKs.
- The header still says "5 migrations" when there are now 7.
- Line 645 still says "we must verify that `migrate diff` stays clean with exclusion constraints". The drift test now proves this, so the line should say it is verified.

**Why it matters**: T4 to T7 implementers and reviewers treat `data-model.md` as the canonical topic doc. A sketch with no currency column and no block ownership FK invites repositories and mappers that ignore both. The project rule is that docs ship with every change.
**Suggested fix**: Update the four model sketches, the SQL-only constraint block, and the composite-FK list (add the block FK) to match `schema.prisma` and the migration. Fix the migration count. Mark the line 645 verification as done (M6-T3 drift test).

## Minor

### 🟡 Doc and test comment claim the M6-T4 lock removes the deadlock outcome, but rate-period creates take no lock, `docs/database/integrity-and-concurrency.md:113`, `tests/integration/inventory-constraints.test.ts:369-370`
**Problem**: The new text says the race can end in `40P01` and that "This is why M6-T4 adds the room-type lock: it serialises writers so the loser gets a clean domain error instead of a deadlock". That holds for block creates, which take the listing lock (spec 0003 line ~165). It does not hold for rate periods: spec line 172 says period writes take "no inventory lock", and only period *edits* lock the period row. Two concurrent overlapping period **creates** on the same listing can therefore still end in `40P01`. Spec 0003 maps only `23P01` to 409 (Query shapes and errors), so a `40P01` would surface as a redacted 500. That breaks AC-2's "Concurrent period writes have one valid result".
**Why it matters**: Nothing is wrong in T3's code, but the doc records a guarantee the planned design does not give. The gap is easy to lose before T7.
**Suggested fix**: Narrow the sentence so it covers block writers only. Record an open decision for T7: map `40P01` on the period insert to `409 CONFLICT`, or serialise period creates (for example, lock the listing row `FOR NO KEY UPDATE` in the period-create transaction). Add a matching note to the test comment.

### 🟡 Demo inventory step fails with an opaque Prisma error after a demo listing slug is edited, `prisma/seed/demo.ts:52`
**Problem**: `seedDemoInventory` finds the demo listings by slug with `findFirstOrThrow`. A staff member who renames or deletes `giza-garden-room` or `giza-family-apartment` (normal CMS edits that the docs promise are preserved) makes every later `db:seed -- --demo` run fail with Prisma's generic "No record found". Atomicity holds (nothing is written, as tested), but the failure gives no hint of the cause. The existing demo photo check sets the opposite precedent: "creates nothing if a demo photo is missing, and says which".
**Why it matters**: The reviewer friction is local only, but a seed that hard-fails on an expected staff edit undercuts the "re-run safely" promise in `docs/database/migrations-and-seeding.md`.
**Suggested fix**: Resolve the listings with `findFirst` and throw a descriptive error naming the missing slug and the branch, or skip with a log line. Keep the all-or-nothing behaviour either way, and assert the message in the existing test.

### 🟡 The partial-upgrade test does not prove transactional rollback, `tests/integration/seed.test.ts:89`
**Problem**: `seedDemoInventory` resolves every listing (`Promise.all`, `demo.ts:49`) before its first write, so the missing-listing case throws before any insert. The test would pass with no `$transaction` at all. Rollback after a partial write is not exercised.
**Why it matters**: A later refactor could drop the transaction or interleave lookups and writes and still pass this test.
**Suggested fix**: Optional. Add a case that fails after the first fixture's writes, for example a unique-label clash on a second-listing unit that `skipDuplicates` cannot absorb (or a CHECK failure), and assert zero rows. Or rename the test so it claims only "resolves all targets before writing".

### 🟡 Race test does not show that the two transactions actually overlapped, `tests/integration/inventory-constraints.test.ts:337`
**Problem**: The two inserts run under `Promise.allSettled` with no barrier or lock-wait observation. If they ran one after the other, the test would still pass (second insert fails with `23P01`). Spec 0003 (Critical test scenarios) asks for "barriers and observable lock waits, not sleeps as evidence that transactions overlapped". The invariant itself (exactly one commit, final count 20) is asserted correctly, and accepting `40P01` is legitimate: concurrent conflicting inserts under an exclusion constraint can deadlock in PostgreSQL.
**Why it matters**: The test proves the constraint, not concurrency. Acceptable for T3, but it should not be cited as the C-4 concurrency evidence.
**Suggested fix**: Leave it as a constraint-under-contention smoke test. Add the barrier/`pg_locks` observation in the T4 harness (`tests/integration/reservations/`), as the spec plans.

## Nits

- ⚪ `prisma/migrations/20261108120000_inventory_and_rates/migration.sql:120`: no CHECK pairs `cancelledAt` with `cancelledById` (both null or both set). The spec does not require one, but it is a cheap invariant for the soft-cancel audit trail.
- ⚪ `prisma/schema.prisma` `PhysicalRoom`: the database still allows moving a unit to another listing within the same branch (`roomTypeId` is mutable and blocks key on `(id, branchId)`). The spec delegates this immutability to repositories. A short schema comment saying so would prevent surprise.
- ⚪ `prisma/seed/demo.ts:80-91`: `skipDuplicates` (`ON CONFLICT DO NOTHING`) also silently absorbs an exclusion conflict. Verified on PostgreSQL in a rolled-back temp table. If staff create an overlapping active period first, the fixture period is skipped without notice. This is correct behaviour; a comment would document it.
- ⚪ `prisma/seed/demo.ts:83-84`: the fixed January 2027 demo period falls into the past within about 14 months. Consider a note that it needs moving forward, or compute it from the seed date.
- ⚪ The migration's explicit `BEGIN/COMMIT` differs from the earlier migrations. It is good here (Prisma does not wrap Postgres migrations, so a failure leaves no half-applied state), and worth one comment line saying why.

## Strengths

- The migration SQL matches the spec verbatim: partial exclusion predicates, `'[)'` ranges, composite ownership FKs with explicit `ON UPDATE RESTRICT`, the extension guard with no silent fallback, and USD/positive-amount CHECKs. It is atomic, and the M5-copy rehearsal test proves that every existing row is byte-for-byte unchanged (a `to_jsonb` snapshot of every table) and that there is no drift.
- The constraint tests are precise. They assert SQLSTATE and constraint names, correctly expect `23001` (not `23503`) for `RESTRICT` deletes and moves, and cover all overlap shapes, both adjacent boundaries, cancelled and inactive exclusion, reactivation and extension through `UPDATE`, INTEGER overflow (`22003`), leap-day DATE round-trips on a UTC connection, and cross-branch rejection at the database.
- The seed is safe: create-only with stable CUID2 identities, a separate substep that also upgrades existing demo branches, and New Cairo explicitly asserted empty. The production refusal is tested through the real `prisma/seed.mts` entry point with a before/after state comparison. The staff-edit preservation test covers labels, inactive units, edited prices, inactive periods, and cancelled blocks.
- Hard-deleting an archived CMS room that now has inventory maps cleanly: the adapter turns `23001` into `P2003`, which `translatePrismaWriteError` reports as `REFERENCED`, so it is not a 500.
