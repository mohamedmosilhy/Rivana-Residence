# Review, m10-guest-booking-journey (M10-T0b), 2026-11-26

**Reviewed by**: Claude Opus 5.5 (claude-opus-5-5), independent review subagent (author on a different session/model)
**Scope**: 36 files (26 modified, 10 new), uncommitted vs HEAD 2170e23
**Verdict**: Approve with nits

## Summary

The change records the server side booking steps (P5, P6, P9, P10, P7, payment callback and reconciliation), stores the visit id on an ONLINE reservation inside the booking transaction and clears it in the same transaction that confirms or fails the payment, and adds the hourly `npm run analytics -- rollup` job that writes daily totals, deletes totalled raw events older than 90 days, and rotates the salt. I checked it against the approved task card and its seven decisions, spec 0007, ADR 029, AGENTS.md and the dependency rules. Booking and payment integrity holds: the use cases import nothing from analytics, recording runs after commit through `after()` (or inline in jobs) with every error caught, the visit id is excluded from the idempotency fingerprint, every way out of `AWAITING_PAYMENT` clears it, and the 20 round race proves one `BOOKING_CONFIRMED`. I found no blocker or major. The remaining points are small: retries of a refused P7 are counted again, the real `after()` path of P7 and P8 is never exercised, and a few contract and doc wording mismatches.

## Minor

### 🟡 A retried refused booking writes a second `CHECKOUT_REFUSED`, `src/composition/reservations.ts:256-261`
**Problem**: Refusals are not stored under the idempotency key. Only a saved booking is replayable, so a client that resends the same P7 request (same `Idempotency-Key`) after a `409 PRICE_CHANGED` or `409 INVENTORY_UNAVAILABLE` runs the use case again. Each attempt then records another `CHECKOUT_REFUSED` row. `CHECKOUT_REFUSED` is not in `REPEAT_SKIPPED_STEPS` (`src/domain/analytics/funnel-event.ts:25-29`).
**Why it matters**: The rollup's `REFUSAL` count (`src/domain/analytics/daily-totals.ts:211-219`) counts events, so a browser or network retry inflates "checkout refusals" for that reason. The `sessions` column stays correct. The spec's wording ("P7 never records on a replay") covers this in spirit, but the code does not cover it in fact.
**Suggested fix**: Do one of these: add `CHECKOUT_REFUSED` (with its outcome) to the 30 minute repeat skip, have the report use `sessions` for refusals and say so in the T0b doc updates, or accept the inflation and record it in the docs.

### 🟡 The real `after()` path is never exercised for P7 and P8, `src/composition/analytics.ts:105-111`
**Problem**: In the integration suite, `after` is called outside a request scope, so it throws and the work runs inline (`afterResponse`'s catch branch). The E2E spec proves the deferred path only for P5 and P10. The P7 path (recording from a `finally` block, after a refusal or a saved booking) and the P8 callback path (`onBookingConfirmed` → `after`) never run inside a real Next.js request scope.
**Why it matters**: The risk is low, because the same helper works for P5 and P10. Still, the card's E2E row ("a pay at hotel journey through the API") is the only planned proof of these two paths on the production server, and it was dropped.
**On the stated deviation**: The claim is accurate for the current E2E server. A pay at hotel P7 needs a usable verification channel (`create-website-reservation.ts:241-249`). WhatsApp defaults to `meta` in production and is not configured without an access token (`src/lib/env/schema.ts:85`, `whatsAppSetupReader`). `fake` is refused in production. Email bookings must pay online (Q-100). The integration test does walk the whole journey through the real route handlers on PostgreSQL. A pay at hotel P7 only enqueues outbox rows, so a dummy Meta access token plus seeded WhatsApp settings on the E2E server would probably let it pass with no network call. That would change shared E2E server configuration, so treat it as the owner's choice and not as a requirement.
**Suggested fix**: Optional. Either record the gap in the review package as accepted, or add the WhatsApp fixture approach in T1 or T10, when the journey E2E exists anyway.

### 🟡 The rollup always creates today's salt, even with tracking off, `src/application/analytics/roll-up-site-events.ts:39`
**Problem**: `salt.execute(now)` creates a fresh random `AnalyticsSalt` row every UTC day, even when `ANALYTICS_ENABLED=false`, so that the old one gets deleted.
**Why it matters**: There is no privacy harm, because a salt with no events identifies nobody. But the integration privacy case asserts `analyticsSalt.count() === 0` with tracking off, and that is true only until the job first runs. Anyone reading "tracking off stores nothing" literally will be surprised.
**Suggested fix**: When tracking is off, delete salts older than today without creating one (for example, a `deleteBefore(day)` on the salt store). Or state in the deployment doc that the job keeps one salt row.

## Nits

- ⚪ `src/composition/analytics.ts:80`: the header value is lowercased before parsing, but the P7 body value is not (`bookingAnalyticsSession`, line 87), so `"AB"×16` counts in the header and is ignored in the body. The contracts say "32 hexadecimal characters" for the header and "32 lowercase" for the body. Pick one rule.
- ⚪ `src/contracts/api/v1/reservations.ts:63-64`: `z.unknown()` puts no `type` in OpenAPI, and the T1 typed client (`z.input`) will type the field as `unknown`. Consider documenting `type: string` while still ignoring anything else at runtime (for example, `z.union([z.string(), z.unknown()])` or an OpenAPI override).
- ⚪ `src/composition/analytics.ts:122`: `occurredAt` uses the wall clock, not the injected job `Clock` that `reconcilePayments({ clock })` receives. Tests mask this by faking `Date`.
- ⚪ `src/composition/analytics.ts:20-34` with `src/composition/reservations.ts:345-353`: recording always uses the global `getPrisma()`, never the `client` that `processPaymentCallback`/`reconcilePayments` were given. In production these are the same client. The difference only matters for tests or future multi-client wiring.
- ⚪ `src/infrastructure/db/prisma/repositories/reservations/reservation-repository.ts:303-307`: `confirmPaid` adds one extra SELECT inside the payment transaction. This is correct under the lock, but the previous value could also come from a single `UPDATE … RETURNING` through raw SQL. Leave it as is unless payment latency becomes a concern.
- ⚪ `src/infrastructure/db/prisma/repositories/analytics/site-analytics-store.ts:117-124`: `daysWithoutTotals` scans every retained raw event with a correlated `EXISTS` each hour. This is fine at hotel scale (90 days of events). If volume grows, it could be bounded to day boundaries (for example, `generate_series` over the dates of the oldest and newest events).
- ⚪ `src/domain/analytics/daily-totals.ts:175`: in a branch scope, `LANDING_PAGE` is the first page in that branch, not the visit's landing page. That is reasonable, but say so in the data model doc so that M12-T4b does not read it as the visit's entry page.
- ⚪ `src/composition/reservations.ts:238-276`: `submitWebsiteBooking` holds a small amount of orchestration (strip the field, refusal versus saved, `finally`) in composition. The approved architecture puts it there, and the rules of *what* to record stay in the domain. Keep it from growing.

## Docs the code now contradicts (for the Stage 7 sync; not counted as findings)

- Spec 0007, line 210: "at most one row per session and event name per UTC day". The code skips a repeat within 30 minutes, per listing (decision 1).
- Spec 0007, lines 209 and 297: "a port the booking use cases' callers use after the use case returns" and "reach it only through the `RecordFunnelStep` port called by their callers". Now the use cases expose generic `onSaved` / `onBookingConfirmed` listeners (decision 3).
- Spec 0007, line 248: P7 `analyticsSessionId` "string up to 64 characters". The code accepts any JSON value and ignores it unless it is valid (smaller choice 2).
- Spec 0007, lines 328 and 348: "step 8 from the callback, reconcile, and expire paths". Expiry records nothing and only clears the id.
- Spec 0007, line 217: "the caller records `BOOKING_CONFIRMED`". It is now the composition listener. Also note decision 5 (a late confirmation after expiry is not counted).
- AGENTS.md "Commands" and the deployment cron need `npm run analytics -- rollup` (hourly). Spec line 310 says to enable collection only after this job runs.

## Strengths

- Integrity first: `CreateWebsiteReservation` and `ProcessPaymentCallback` import nothing from analytics. The visit id is written through the existing repository in the booking transaction, and the database CHECK (`ONLINE` and lowercase hex) can never be violated because `parseSessionId` gates the value first. The value is stripped before the use case, so it never enters the idempotency fingerprint, an audit row, or a `StoredReservation` (the explicit `map()`).
- Every way out of `AWAITING_PAYMENT` (`confirmPaid`, and `markPaymentFailed` through `endBookingPaymentHold` for expiry, a closed session, a definite checkout refusal, and booking time expiry) clears the id in the same transaction. "Submitted" is counted even when checkout fails after the commit (`onSaved` before `checkout`), and never on a replay.
- The failure isolation test is strong. A `CHECK (false) NOT VALID` on `SiteEvent` makes PostgreSQL refuse every analytics write, and the test still proves unchanged P5, P6, P7 and P8 responses and reservation state, with one fixed, data-free log line per lost batch.
- The 20 round callback versus reconcile race uses independent clients and observed lock waits (`waitForLockWaiters`), and asserts exactly one `BOOKING_CONFIRMED`. The rollup overlap guard is also tested over 20 held rounds.
- The rollup design is careful. Neighbouring days are loaded so that a visit is counted once on the day it started. The whole site `TOTAL` row doubles as the "day done" marker that deletion depends on. One failing day is skipped and retried while its raw events are kept. The CLI prints counts only and hides database errors.
