# Review, m9-payments-and-cancellations (M9-T0), 2026-11-22

**Reviewed by**: Opus 5.5 (author on Sonnet 5.5)
**Scope**: 100 changed files + 1 new file (`src/application/auth/index.ts`), uncommitted vs HEAD
**Verdict**: Approve with nits

## Summary
A moves-only refactor. It adds a public `index.ts` to `src/application/auth`, sends all 91 outside importers through it, switches the 3 internal files to relative imports, and adds `auth` to the application-only D-8 lists in the architecture test and ESLint. It also points the ports-layout allowance at the auth index and adds a leaf guard test. I checked it independently: it is import lines only, the index matches real usage exactly, and no import changed between type and value. I found no blockers or majors. The findings are about how complete the leaf guarantee is and about two doc sentences that are out of date.

## Minor
### 🟡 The leaf guard covers one hop only, so "cannot create a cycle" depends on `shared` staying clean, `tests/unit/architecture/module-boundaries.test.ts:140`
**Problem**: The guard allows `@/application/shared/**`, but no test stops `src/application/shared` from importing another application module. Today `shared` imports only `@/domain/**` and its own files (checked). If `shared` later imported, say, `@/application/reservations`, this path would become possible: auth → shared → module → `coupons/ports.ts` → auth index. The ports-layout comment (`ports-layout.test.ts:66`) and the D-8 row both say this "cannot" create a cycle.
**Why it matters**: The type-only `BranchScope` edges are erased at runtime, so the current risk is low. But the guarantee the docs give is stronger than what the tests enforce. M9 will add many use cases, and some may be tempted to put helpers in `shared`.
**Suggested fix**: Add a matching small guard that `src/application/shared/**` imports only `./`, `zod`, `@/domain/**`, and `@/application/shared/**`. Or soften the two comments to "while auth and shared import no other module".

### 🟡 The ports section of `dependency-rules.md` is now wrong for auth, `docs/architecture/dependency-rules.md:35`
**Problem**: The text says other code imports a port "from `@/application/<module>/ports`". For `auth` (and the M8-T0b modules) the D-8 test and ESLint now reject that path, and the port must come through `@/application/auth`. The same paragraph says "the shared folder is the only common ground" for module port files. In fact, three port files (`coupons`, `pricing`, `guests`) import `BranchScope` from the auth index, and that exception is the one this task changed.
**Why it matters**: The project rule is "docs ship with every change". A future author who follows this paragraph will write a deep import that the gates reject, or will not know about the auth exception.
**Suggested fix**: Change the sentence to say outside code imports ports through the module's index wherever the module is in a D-8 list. Add one clause for the auth `BranchScope` exception, which is safe because auth is a leaf.

## Nits
- ⚪ `tests/unit/architecture/ports-layout.test.ts:66`: the comment says "Type only `BranchScope`", but the regex `^@/application/auth$` also allows value imports (`SignIn`, `authorize`, …) into any `ports.ts`. Value imports were also possible under the old `authorize-branch` allowance, and the leaf rule keeps them harmless, so a comment fix is enough ("intended for the type-only `BranchScope`").
- ⚪ `docs/delivery/milestones/m14-hardening.md:64`: the list now names five modules (with `auth`), but the same sentence still says "move those four from the application-only list".
- ⚪ `tests/unit/architecture/module-boundaries.test.ts:147`: `/^\.\//` also accepts `./../<module>/…`, and the scanner misses side-effect `import "x"` statements. These are the shared scanner's existing limits, but they are the escape routes from the leaf guard. Using `^\.\/(?!\.\.)` would close the first one cheaply.
- ⚪ `src/proxy.ts:5`: `loginPathFor` used to load only `return-path.ts`. It now loads the whole auth index (authorize, sign-in, domain capabilities and throttle). All of that is pure and imports no server-only or Node modules (checked), so nothing changes. Note it in case the proxy's module graph ever needs to stay minimal.
- ⚪ Existing gap, not introduced here: `tests/**` and `src/proxy.ts` are outside ESLint's `moduleInternals` globs, and the D-8 test scans `src` only. So nothing stops the 50 rewritten test files from going back to deep auth imports. The M8-T0b review noted the same gap.

## Verification performed
- (a) **Moves only.** For all 96 changed `.ts/.tsx` files I removed every `import`/`export … from` statement from HEAD and the working tree, normalized whitespace, and compared. Non-code files changed: `eslint.config.mjs` and the 3 docs only. `docs/api/openapi.json` is unchanged.
- (b) **Index exports.** A script collected every symbol imported from `@/application/auth` in `src` and `tests` (91 files). Used and exported sets match exactly: no unused export and no missing one. That covers the 10 values and 7 types in the plan. `StaffSessionSummary`, `StaffListing`, and `SignInCommand` stay internal. Types use `export type {}`. **Cycles:** the auth module's files import only `./`, `@/application/shared/{result,providers}` (`providers` as a type), and `@/domain/auth/*` / `@/domain/shared/*`. `shared` imports no application module. No runtime cycle.
- (c) **Guard soundness.** The leaf test is not vacuous: `authFiles.length > 5` with 6 files, and it uses the same `importsOf`, which catches static, `export … from`, and dynamic imports. An `@/application/auth/ports` self-import from inside auth fails both the leaf test and D-8. The widened ports allowance also covers `auth/ports.ts` itself, and the leaf test still catches it there. See the Minor finding above for how far the guarantee reaches.
- (d) **Type vs value, D-13.** No file went from type-only auth imports to a runtime import (statement-level check). No statement uses only inline `type` specifiers that would keep a side-effect import. The tsconfig has `isolatedModules` and no `verbatimModuleSyntax`. No `"use client"` file imports `@/application/auth`. Every non-application importer is a server file (proxy, admin server pages/actions, route wrappers, composition, infrastructure).
- (e) **ESLint consistency.** The `APPLICATION_SURFACE_MODULES` lists in `eslint.config.mjs` and the test match (9 entries each, `auth` first). The `surfacePattern` negation `!@/application/auth/index` mirrors the test regex `(?!index$)`. No deep `@/application/auth/` import is left in `src` or `tests`.
- (f) **Docs.** The D-8 row and the M9 "as built" note are accurate. The M14-T11 addition is accurate except for the "four" wording and the stale ports paragraph, both listed above.
- Reran: `vitest run tests/unit/architecture tests/unit/import-boundaries.test.ts` gave 7 files / 207 tests passed, and `eslint` on `src/proxy.ts src/application/auth src/composition/auth.ts` was clean. I did not rerun the full gates.
