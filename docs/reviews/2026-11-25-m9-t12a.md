# Review, m9-payments-and-cancellations (M9-T12a), 2026-11-25

**Reviewed by**: Claude Sonnet 5.5 (author on Claude Opus)
**Scope**: 78 tracked files changed plus 16 untracked paths, uncommitted vs HEAD 3b16ce4
**Verdict**: Changes requested

## Summary

The change adds the email verification channel end to end: P9 channel and email with per email limits, a channel and email bound code HMAC (WhatsApp input unchanged), the P7 email token match, the domain `websiteBookingProfile`, the per email cap behind an email advisory lock, phone session hiding, email only guest messages, the readiness gate, the Admin switch (A9 and page), an additive migration, and tests. The structure is sound: lock order is consistent, the migration is safe for the previous release, no network I/O happens in a transaction, and the settings change is audited in the same transaction. One real cap bypass exists because the per email cap counts by a mutable booking field, and a few smaller gaps remain.

## Major

### 🟠 Per email cap counts by `guestEmail`, which a guest can change, `src/infrastructure/db/prisma/repositories/reservations/reservation-repository.ts:214`
**Problem**: `listEmailBookings` finds bookings with `guestEmail = <verified email>` and `verificationChannel = EMAIL`. The verified email is never stored on the reservation. `guestEmail` is the editable contact: a guest change through the manage link can set a new email (`apply-booking-change.ts` handles an EMAIL booking's email change by revoking the link, so the flow is reachable), and staff can edit it too. After such a change the booking no longer counts toward the cap of the email that was proven.
**Why it matters**: The per phone cap is keyed on the immutable `guestId`, so it cannot be dodged this way. The per email cap (2 upcoming pay at hotel, 1 open hold) can be bypassed: book to the cap, change the email on each booking, book again. This is the abuse control Q-93 exists for.
**Suggested fix**: Store the proven email on the reservation at insert (a new nullable column, written only with `verificationChannel = EMAIL`, not editable by contact changes) and count by it. Alternatively count through the verification row. Add a test that changes the contact email on a counted booking and shows the cap still holds. Keep the migration additive.

## Minor

### 🟡 Held message validity rejects every email only booking, `src/application/reservations/process-payment-callback.ts:552`
**Problem**: `heldStillValid` requires one held WHATSAPP row whenever `contact.phone` exists. An EMAIL verified online booking queues no WhatsApp row, so the check always fails. The callback then discards the held messages, rotates the manage token, and enqueues a fresh confirmation.
**Why it matters**: The token returned to the browser by P7 (`create-website-reservation.ts:779`) silently stops working when payment completes, unlike WhatsApp bookings. The guest still gets an email with a new link, so it is not unsafe, but the behavior is inconsistent and probably untested.
**Suggested fix**: Expect zero WhatsApp rows when `reservation.verificationChannel === "EMAIL"`, and add a payment callback test for an EMAIL booking.

### 🟡 Staff manage link audit flags are wrong for EMAIL bookings, `src/application/reservations/reservation-guest-access.ts:77`
**Problem**: `whatsappQueued: Boolean(current.contact.phone)` is recorded even though `QueueReservationMessages` never sends WhatsApp for an EMAIL booking.
**Why it matters**: The audit log claims a WhatsApp message was queued that was not.
**Suggested fix**: Derive the flag from the same rule (`phone && verificationChannel !== "EMAIL"`), ideally from one shared helper.

### 🟡 An email code can consume a victim phone's booking cap, `src/application/reservations/create-website-reservation.ts:421`
**Problem**: The per phone cap still counts every website booking on the typed phone, including bookings made with an email code by someone who only typed that phone.
**Why it matters**: A third party can use two pay at hotel bookings to block the real owner of a phone from booking online. The spec says the phone cap still applies, so this may be an accepted trade, but the risk is new with unproven phones.
**Suggested fix**: Record the trade in the spec or ADR as accepted, or count EMAIL verified bookings against the email cap only.

### 🟡 Email booking overwrites the contact of an unproven profile, `src/domain/guests/guest-policy.ts:91`
**Problem**: When the guest profile of a phone has no verified phone, an email booking replaces its name and email with the submitted values.
**Why it matters**: Anyone can type another person's phone and rewrite the stored name and email of that unverified profile. Impact is low (nothing is trusted from it), but it is data an attacker controls.
**Suggested fix**: Confirm this is intended in Decision 9, or leave the profile contact untouched for EMAIL bookings.

### 🟡 Readiness read throws if the settings row is missing, `src/infrastructure/db/prisma/repositories/reservations/guests/verification-settings-repository.ts:19`
**Problem**: `read()` uses `findUniqueOrThrow`. If the row is ever deleted, P9 EMAIL, P7 (when WhatsApp is not ready) and the branch switch return a 500.
**Why it matters**: The migration and seed create the row, so this is unlikely, but readiness should degrade to "email off".
**Suggested fix**: Treat a missing row as disabled in `verificationChannelReadiness`.

### 🟡 Email limits can be sidestepped with address aliases, `src/application/guests/phone-verification.ts:151`
**Problem**: The per email limit keys on the lowercased address, so `a+1@x` and `a+2@x` count separately.
**Why it matters**: This does not bypass the per phone or per client limits, so abuse is bounded, but the per email limit gives less protection for the recipient than it appears to.
**Suggested fix**: Document it as a known limit, or normalize plus tags for known providers later.

## Strengths
- Lock order (phone, guest row, email, verification row) is applied identically in P9 and P7, and the tests observe the lock waits for 20 rounds on the email lock.
- The code HMAC leaves the WhatsApp input untouched, so codes sent before a deploy still confirm, and email and WhatsApp codes can never confirm each other.
- Token handling fails closed: a phone session passes no expected email and so refuses every email token, and P7 checks the email at both the preflight and the locked check.
- `websiteBookingProfile` is a pure, tested domain function that never verifies the phone and never records consent for an email code.
- The migration is additive, keeps the old release working (column default, nullable channel, CHECK compatible with old inserts), and the settings update is audited in the same transaction under a row lock with a lock timeout.
- Outgoing code email stores no plaintext code and the SMTP failure mapping drops the provider message.
- Staff block invalidates open codes by phone, which covers email rows too.

## Test coverage
Coverage is broad and aimed at behavior: use case tests for channel and email binding, domain tests for tokens, caps and the profile policy, an email adapter contract suite, PostgreSQL tests for the email lock race and the email cap race (20 rounds with observed waits), the readiness gate, the Admin switch, the migration, and E2E for P9 and the admin page. I did not run the integration suite (another run was in progress). Gaps: no test that a contact email change keeps the cap (the Major finding), no payment callback test for an EMAIL booking, and no test for the audit flags on a staff manage link resend for an EMAIL booking.

### Checks requested in the recheck

- **`verifiedEmail` write discipline**: only the reservation insert writes it (`reservation-repository.ts:799`), and only with the channel EMAIL, using the verification row's email, which its own CHECK forces to lowercase. No update path (guest change, staff edit, outbox, payment callback) touches it. Staff and external bookings insert null. The CHECK `COALESCE(channel = 'EMAIL', false) = (verifiedEmail IS NOT NULL) AND (verifiedEmail IS NULL OR verifiedEmail = lower(verifiedEmail))` also rejects any future code path that forgets it.
- **Deploy safety**: the previous release does not know the two columns, so its Reservation inserts leave `verificationChannel` null and `verifiedEmail` null. `COALESCE(null = 'EMAIL', false)` is false and `verifiedEmail IS NOT NULL` is false, so the CHECK holds. The channel CHECK (`NULL OR source = 'WEBSITE'`) holds for all old inserts, and the backfill sets WHATSAPP only for WEBSITE rows. A website booking from the old release reads as WhatsApp. Safe.
- **`guestWhatsAppAllowed` coverage**: used at every guest WhatsApp site I found: queueing (`reservation-messages.ts:207`, which covers all event kinds), the manage link replacement on a contact change (`apply-booking-change.ts:43`), the staff resend audit (`reservation-guest-access.ts:81`), and the held message check (`process-payment-callback.ts:558`). The held check also keeps the email count rule and the manage token hash check. Phone sessions are filtered at `guest-reservation-reader.ts:25`.
- **Test only changes**: `tests/e2e/phone-verification-api.spec.ts` giving the email P9 test a per project `X-Forwarded-For` is correct and follows the existing pattern in `guest-access-api.spec.ts:408`; the other new E2E test inserts rows directly and does not hit the per client limit. `tests/integration/transfer-vehicles-migration.test.ts` expecting `verificationChannel: null` and `verifiedEmail: null` is correct, since that row is a staff booking (the migration backfills only website bookings and the CHECK allows null).

## Resolution of the recheck findings (author, 2026-11-26)

- **N1 (Minor 4), fixed by owner decision.** The owner chose the recommended fix: an email booking never rewrites the name or email of an existing guest profile, whether its phone was verified or not. A staff booking at the desk creates the profile with the details staff entered and an unverified phone, so the old rule let a stranger replace them. A new profile already starts with the typed details, and `emailVerifiedAt` is set only when the profile's own email is the proven one. The reservation keeps what the guest typed. Code: `src/domain/guests/guest-policy.ts` (`websiteBookingProfile`). Tests: `tests/unit/domain/guest-values.test.ts` ("leaves an unproven profile's contact and its other email alone") and `tests/integration/reservations/create-website-reservation.test.ts` ("leaves the contact of an unproven profile staff created at the desk alone"). Docs: spec 0006 Decision 9, ADR 031 as built note, Q-93.
- **N2, fixed.** ADR 031's as built note now describes `Reservation.verifiedEmail`, its CHECK, and that the per email cap counts by it.

The owner accepted M9-T12a on 2026-11-26.
