## Summary

Both credential paths apply pay-at-hotel changes within one inventory transaction. The first revision returned a reduced price summary in place of the published quote and omitted the change action from eligible guest reservation views. The missing-phone recovery path also needs direct coverage.

## Major

### 🟠 The preview omits the contracted quote fields, `src/application/reservations/guest-reservation-changes.ts:279`

**Problem.** G5 specifies `Quote` for both the current and proposed price. The new mapper and schema expose `totalMinor` and omit the stay, unit and nightly breakdowns, coupon description, and service unit prices. G6 constructs its price conflict preview with the same mapper. [G5 and G6](../api/api-contracts.md#L54) · [Existing Quote contract](../../src/contracts/api/v1/quotes.ts#L110)

**Impact.** A client following G5 cannot pass `preview.proposed.total` as the money object required by G6. With two same-price stays on different dates it cannot show the guest which dates changed from the response. FR-GCHG-2 requires the guest to see what changed before confirming.

**Suggested fix.** Return the existing public Quote shape for the stored and proposed stays, retaining the stored nightly amounts, coupon and VAT. Reuse the mapping for a G6 price conflict. Test an equal-price date move, validate the returned objects against the existing Quote schema, and pass the proposed total through to G6.

### 🟠 Eligible guest detail responses omit the change action, `src/application/reservations/guest-reservation-changes.ts:684`

**Problem.** G6 returns the shared guest reservation view. Its action list contains only `REQUEST_CANCELLATION` or is empty. G1 and G4 use that same view. FR-LKP-1 requires the permitted booking-change and cancellation actions to appear when the guest opens the reservation. [Shared view](../../src/application/reservations/guest-reservation-reads.ts#L122) · [Guest access requirement](../requirements/functional-requirements.md#L173)

**Impact.** For a confirmed, priced pay-at-hotel booking before the deadline, G5 and G6 both succeed while a guest screen rendering the advertised actions can offer only cancellation. The returned view continues to omit the action after G6 succeeds.

**Suggested fix.** Derive change eligibility for the current stay in the shared view, including payment method, recorded price, status, active request, deadline and blocked phone. Check the action in eligible G1, G4 and G6 responses, and verify its absence for ineligible bookings.

### 🟠 The test suite does not prove credential revocation when the booking phone is unusable, `tests/integration/reservations/guest-changes.test.ts:563`

**Problem.** The email-change test covers a website booking with a valid phone. The browser test starts from a staff booking but changes its source to `WEBSITE` before calling the guest API. Neither exercises the separate branch that clears both manage-token fields when a staff or legacy booking lacks a usable phone. [Credential handling](../../src/application/reservations/guest-reservation-changes.ts#L402) · [Browser fixture](../../tests/e2e/guest-access-api.spec.ts#L115)

**Impact.** A regression that retains the former email holder’s bearer, or sends a replacement to the new email when there is no usable phone, could pass the suite. Decision 8 explicitly requires revocation and hotel-assisted recovery in this case.

**Suggested fix.** Keep a real staff-source booking, set up a previously issued manage bearer and an absent or unusable booking phone, then replace an existing email. Assert that the old bearer fails, both persisted token fields are null, no replacement link is queued or returned, and the former email receives only the minimal notice.
