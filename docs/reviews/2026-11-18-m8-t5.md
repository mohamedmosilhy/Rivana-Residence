## Major

### 🟠 A blank example setting breaks unrelated routes, `src/lib/env/schema.ts:24`

**Problem**: The original optional schema rejected the empty value shipped in `.env.example:49`. I reproduced the shared environment parser throwing with the empty string and succeeding with the variable omitted.

**Why it matters**: An operator who copies the example and configures the required application settings can lose access to routes that use the database or authentication. The approved behavior is for verification alone to return 503 when its secret is absent.

**Suggested fix**: Treat an empty or whitespace only value as absent. Preserve the bytes of a supplied secret and reject short nonempty secrets. Cover all cases with the real environment parser.

### 🟠 Guest lock timeouts disclose profile existence, `src/application/guests/phone-verification.ts:91`

**Problem**: P9 forwarded the guest repository error unchanged. P10 did the same at line 176. When an existing guest row stays locked for five seconds, the repository returns “Guest record is busy.” The public problem serializer includes that message as its detail. Contention on the phone or verification lock says “Verification is busy.”

**Why it matters**: The guest specific detail confirms the submitted phone has a profile, contrary to Decision 3. The HTTP success shape test only exercises uncontended rows.

**Suggested fix**: Give lock timeouts one public verification response across both use cases. Exercise both the existing guest and verification lock failure paths.

### 🟠 The verification browser tests run without a disposable database, `tests/e2e/phone-verification-api.spec.ts:10`

**Problem**: With `E2E_DATABASE_URL` absent, global setup skips database preparation. The new suite still makes a valid P9 request and inserts a known code at line 37. Its SQL helper falls back to `DATABASE_URL`. Other database backed browser suites skip in this configuration.

**Why it matters**: Running the ordinary Playwright command against an existing configured development database can create verification records, consume real limits and attempt a WhatsApp delivery. Inheriting the shell's verification secret also makes the fixture dependent on deployment credentials and fails if the shell exports an empty value.

**Suggested fix**: Use the suite level disposable database guard and share a fixed test secret between Playwright and the fixtures. Verify the suite skips when the disposable database URL is absent.

## Minor

### 🟡 Long honeypot strings get a field specific response, `src/contracts/api/v1/phone-verifications.ts:11`

**Problem**: A filled `website` value over 200 characters is rejected by the HTTP schema before the application can return the generic 422. The application schema has the same limit.

**Why it matters**: A valid request with a 201 character website receives a field error that identifies the trap. Q-74 calls for a generic rejection on a filled honeypot.

**Suggested fix**: Let any string within the existing HTTP body cap reach the same honeypot check. Compare the short and long refusal bodies and verify neither case writes a verification or sends a code.

### 🟡 Verification limiter cleanup lacks regression coverage, `src/application/shared/public-rate-limit-policy.ts:51`

**Problem**: The new namespaces are registered correctly. Existing PostgreSQL cleanup tests exercise other namespaces, while the T5 tests exercise admission. A missing entry in the cleanup list would leave those tests green.

**Why it matters**: Decision 3 requires the cleanup command to prune both new client buckets. They have different expiry windows and their rows can accumulate indefinitely if registration is lost.

**Suggested fix**: Seed expired and live request and confirmation buckets, invoke the existing cleanup and assert that the correct rows survive each cutoff.
