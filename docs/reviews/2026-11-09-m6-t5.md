# Review, m6-inventory-and-availability (M6-T5 physical units), 2026-11-09

**Scope**: 23 files, uncommitted (10 tracked modified, 13 untracked new)
**Verdict**: Approve with nits

## Summary
Adds physical unit administration (API-S21 to S23): a scoped `PhysicalRoomRepository`, a narrow `RoomTypeCatalog` bridge, the `ManagePhysicalRooms` use case, composition, Zod contracts, DTO mapper, thin Route Handlers, OpenAPI, and unit, integration, concurrency, and E2E tests. The critical paths are correct. Authorization runs before data access. Id paths return a hidden 404 through a scope-constrained lookup, both before the transaction and again under the row lock. Deactivation always goes through `InventoryGuard`, even when the preliminary read says the unit is inactive. The guard takes the listing lock, then the unit row lock, then reloads, reads sparse future consumption from branch-local today, validates, writes, and audits in the same transaction. Edits, activation, and creation take no listing lock and never wait for one, so the spec's lock order holds and no deadlock cycle is possible. No blockers or majors. The minor findings are about lock-timeout mapping outside the listing lock, error translation that ignores which constraint failed, and one race the tests do not cover.

## Minor

### 🟡 A lock timeout on the unit row inside the guard becomes a 500, not 503 TRY_AGAIN, `src/infrastructure/db/prisma/repositories/reservations/inventory/physical-room-repository.ts:87`
**Problem**: `lockVisible` runs `SELECT ... FOR UPDATE` without a try/catch. In the deactivation path, `PrismaInventoryLock` has already run `SET LOCAL lock_timeout = '5s'`, so a 5 s wait on the unit row raises `55P03`. Nothing maps it, so it surfaces as a redacted 500. Only `PrismaInventoryLock.lockRoomTypes` translates `55P03` to `TRY_AGAIN`.
**Why it matters**: The spec says lock timeout `55P03` becomes `503 TRY_AGAIN` with `Retry-After: 5`. This is unlikely in M6 because row holders (plain edits) are short. Once T6 block writers and M8 reservation writers also lock unit rows, the window grows.
**Suggested fix**: Translate `55P03` in `lockVisible` to `failure("TRY_AGAIN", ...)` and return a `Result`, or share the translation helper with the inventory lock. Add an integration case that holds the unit row while a deactivation waits.

### 🟡 The plain update path has no lock_timeout, so contention ends as a Prisma transaction timeout, `src/application/inventory/manage-physical-rooms.ts:191`
**Problem**: `plainUpdate` opens a unit of work and takes `FOR UPDATE` on the unit row without `SET LOCAL lock_timeout`. If another transaction holds the row, the wait is bounded only by the 10 s interactive transaction timeout (`RESERVATION_TRANSACTION_TIMEOUT_MS`), which fails as a Prisma transaction error (500).
**Why it matters**: The spec keeps the transaction timeout above the 5 s lock timeout precisely so that callers get `503 TRY_AGAIN` instead of an opaque transaction failure. Today the edit path does not follow that.
**Suggested fix**: Have `lockVisible` (or a small helper the repository owns) set `lock_timeout = '5s'` before the row lock, and pair it with the `55P03` mapping above.

### 🟡 Error translation ignores constraint identity, `src/infrastructure/db/prisma/repositories/reservations/inventory/physical-room-repository.ts:36`
**Problem**: `isDuplicate` treats every `P2002`/`23505` as a duplicate label. `translate` maps every `P2003`/`23503` to "This listing was not found in the branch." But `PhysicalRoom` also has an `updatedById` FK to `User` (`prisma/schema.prisma:345`). An update or create by an actor whose `User` row no longer exists would be reported as a missing listing. The other unique constraints (`id`, `(id, roomTypeId)`, `(id, branchId)`) would also be reported as label conflicts.
**Why it matters**: The spec says to "map known PostgreSQL or Prisma driver errors by SQLSTATE and constraint identity". The current mapping gives a misleading 404 or 409 instead of letting an unexpected failure become a redacted 500. The risk is low today, since ids are generated and sessions are tied to users.
**Suggested fix**: Check the constraint name or target (`meta.target` / `meta.constraint`, or the driver error's constraint field) for `(branchId, label)` and for the `(roomTypeId, branchId)` composite FK, and rethrow anything else. The spec asks for the real Prisma 7 adapter envelope to be verified in integration tests, so extend the existing duplicate-label and cross-branch FK tests to assert on it.

### 🟡 No real-database race test for activation versus deactivation, `tests/integration/reservations/concurrency.test.ts:206`
**Problem**: The new concurrency cases cover competing deactivations, deactivation waiting behind a held listing lock with a fresh reload, and branch isolation. Spec line 174 also claims "unit activation versus deactivation without lost updates", and that path mixes the unlocked plain path with the guarded path. No test races them.
**Why it matters**: This is the one interleaving where one side holds only the unit row and the other holds listing plus row. The code is correct by inspection: the plain path re-reads under the row lock and needs no listing lock, so no cycle forms. A 20-iteration test would pin that down before T6 adds more writers on the same rows.
**Suggested fix**: Add a 20-iteration case that runs `update(active:true)` and `update(active:false)` on separate clients with a barrier. Assert that both succeed, that the final row equals the last committed transition, and that there are exactly two audit events with consistent `from`/`to` values.

### 🟡 The test wiring duplicates the production composition by hand, `tests/integration/reservations/support/physical-rooms.ts:29`
**Problem**: `physicalRoomUseCase` rebuilds the same object graph as `src/composition/inventory.ts:20`, with its own context factory. If the production composition changes (for example, M8 swapping the consumption adapter or adding a port), the integration and concurrency tests keep exercising the old wiring.
**Why it matters**: The concurrency proofs are only evidence for production if they run the production graph.
**Suggested fix**: Have `managePhysicalRooms` accept an optional client and overrides (consumption, audit wrapper, clock), and have the test helper call it. Alternatively, add a test that asserts the two context factories return the same adapter types.

## Nits

- ⚪ `src/domain/audit/audit-event.ts:26`: on `physical-room.created`, `notesChanged` really means "has notes". A name like `hasNotes` would read more clearly, though keeping it matches the update event.
- ⚪ `tests/unit/architecture/persistence-boundaries.test.ts:65`: removing every `entityType:...` fragment before the regex runs also hides a real `"PhysicalRoom"` reference that shares the line. A narrower exemption (only `src/domain/audit/audit-event.ts`, or only quoted labels after `entityType:`) keeps the guard tight.
- ⚪ `src/contracts/api/v1/inventory.ts:5`: the label and notes limits repeat 40 and 500 instead of importing `PHYSICAL_ROOM_LABEL_MAX` and `PHYSICAL_ROOM_NOTES_MAX`, so the contract and the domain could drift.

## Strengths
- The authorization order matches spec section "Authorization, audit, and lifecycle" exactly. Explicit branch paths use `authorizeBranch` (403) before any read. The id path checks the capability first, then makes a scope-constrained lookup that returns the same 404 for missing and foreign units. Scope is applied again inside `lockVisible`, and an empty manager scope short-circuits to null.
- Deactivation is robust. It always goes through the guard, the unit row is re-locked and reread after the listing lock, `today` comes from `localDateAt(clock.now(), branch.timeZone)`, consumption is read sparse and unbounded from today, and capacity is read only on sold nights. Audit happens inside the transaction, and a no-op writes nothing and is not audited.
- Lock ordering is sound. Listing (`FOR NO KEY UPDATE`) comes before the unit (`FOR UPDATE`). Non-reducing paths never request the listing lock, and FK inserts take only `FOR KEY SHARE` on `Room`, which does not conflict with the listing lock. The HTTP integration test proves that edits, activation, and creation finish while the listing is held, and that deactivation returns 503 with `Retry-After: 5`.
- Audit never contains note text, only `notesChanged`, and tests assert this (unit test with "old secret", integration audit checks). Rollback on audit failure is proven for create, edit, activation, and deactivation.

## Test coverage
Strong. Unit tests sweep every role and assignment state across S21 to S23 and assert that no port is called on refusal. They also check port call order under the guard (lock-listing, then lock-row, blocks, sold, assignments, update, audit), the horizon-free sparse sold check, the blocked-unit double count, assignment refusal, the already-inactive guarded no-op, TRY_AGAIN with no reads, and post-lock disappearance. Integration on real PostgreSQL covers the repository scoping, the composite FK at the database boundary, the 409 label field error with no audit, case-sensitive per-branch labels, 401/403/404/422/CSRF through the real handlers, immutable ownership, audit rollback, injected consumption refusals, and listing-lock behaviour over HTTP. Concurrency covers competing deactivations, the wait plus fresh reload (observed through `pg_stat_activity`), and C-8 branch isolation, each over 20 iterations. Chromium E2E covers the REST flow and the role and branch restrictions. Gaps (minor): the activation versus deactivation race, `55P03` on the unit row lock, and constraint-identity assertions in error translation.
