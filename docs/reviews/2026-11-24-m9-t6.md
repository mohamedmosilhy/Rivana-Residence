# Review, m9-payments-and-cancellations (M9-T6), 2026-11-24

**Reviewed by**: claude-opus-5-5 (independent reviewer subagent; author on a different session)
**Scope**: 24 files (18 tracked + 6 untracked), uncommitted (working tree vs HEAD 127c5cb)
**Verdict**: Changes requested

## Summary
The change adds `ExpirePaymentHolds` (`expire-holds`) and `ReconcilePayments` (`reconcile-payments`). It extracts `expireHoldIfOverdue` so that booking creation and the job share one expiry step, and it makes `ProcessPaymentCallback.applyVerifiedEvent` public so that P8 and reconciliation apply gateway answers through the same code. A new `PrismaPaymentSweepStore` provides cross-branch candidate reads. The lock rule holds on every path I traced. Expiry and every reconcile write lock only the reservation row. A success found by a lookup goes through the existing redo and listing-lock path. Every write re-checks state under the lock, and the store updates are conditional `updateMany`s. C-14 and C-12 interleavings cannot oversell or deadlock: `release` updates only the redemption row and never locks the coupon. One major problem remains, a money-safety gap. A lost success callback on an expired payment gets one lookup. After that lookup the payment drops out of every sweep, even when the lookup ran before the gateway had settled. The other findings are minor: sweep starvation, refund-stamp bookkeeping that T8 will build on, a query that scans the whole payment history, and test gaps.

## Major

### 🟠 A lost success on an expired payment gets one lookup. A single early "no success" answer ends recovery for good, `src/application/reservations/reconcile-payments.ts:222`
**Problem**: The expiry job runs every minute and moves an `INITIATED` payment to `EXPIRED` at `holdExpiresAt`, which is `expiresAt + 2 min`. Step A (`findStaleInitiated`) therefore sees a payment only in the 2-minute gap between session end and hold end, and a job that runs every 5 minutes often misses that gap. The spec notes say the real recovery path for a lost callback is step C (`cleanHeldMessages`). Step C asks `getTransaction` once. On `NOT_FOUND`, `DECLINED`, or `SESSION_CLOSED` it deletes the held rows at lines 222 to 236. `findHeldCleanup` selects only payments whose reservation still has `HELD` notifications (`payment-sweep-store.ts:74`), so after that delete no sweep ever looks at the payment again. The lookup can run very soon after the hold ends, as little as `expiresAt + 2 min`. Some gateways accept a payment that started before the session deadline and finish it a few minutes later (3-D Secure, delayed capture). Some return `NOT_FOUND` or a provisional answer until their inquiry index catches up. If the callback for such a payment is also lost, the guest is charged but has no booking, no refund, and no staff alert. The 24-hour fallback ends recovery in the same way. Deleting the rows is harmless in itself, because a late success issues a new token. The trouble is that the presence of held rows is also the only queue for reconciling expired payments.
**Why it matters**: Money is taken and nothing in the system acts on it. This sits right on the question the task card asks: can a paid customer be left unrefunded? The condition is rare, because it needs a lost callback and an early or wrong negative answer together. The implementation follows the spec text literally ("asked after the payment's `expiresAt`"), so the owner needs to decide whether that wording is enough.
**Suggested fix**: Trust a no-success answer only once a grace period has passed since `expiresAt`, for example 15 to 30 minutes. Before then, count it as `pending` and leave the rows. The selector will then ask again on later runs. Another option is to reconcile `EXPIRED` payments inside the fallback window whether or not held rows exist. Either way, add an integration case: an early `NOT_FOUND`, then a later `SUCCEEDED` lookup that still takes the late-success path.

## Minor

### 🟡 Bounded sweeps can starve behind stuck items, and the logs give no way to find them, `src/infrastructure/db/prisma/repositories/reservations/payment-sweep-store.ts:51`
**Problem**: `findUnsentRefunds` sorts by `updatedAt asc` with a limit of 50. An item whose transaction id the gateway cannot find (counted as `pending`), or whose `refund` call keeps throwing, never touches `updatedAt`, so it stays at the head of the queue. Once 50 such rows exist, newer unsent refunds are never sent. `findOverdueHolds` (sort by `holdExpiresAt asc`, limit 100) behaves the same way with rows that keep throwing, for example the "no initiated payment" invariant error at `booking-payment-holds.ts:67`. The jobs log nothing, by owner decision, so the only signal is `failed` or `pending` in the summary. Nothing shows which item is stuck.
**Why it matters**: The thresholds are high for a hotel, so this is unlikely. If it happens, refunds stop without any sign.
**Suggested fix**: Move a refused or not-found item behind the others: touch `updatedAt` or a `lastSweptAt` column on failure, or use keyset paging past the last item tried. As an alternative, log the payment or reservation id with the outcome code. Ids are allowed under the project's log rule.

### 🟡 The refund stamp is not tied to the attempt that was sent, and a definite `FAILED` result is recorded as sent, `src/application/reservations/reconcile-payments.ts:185`
**Problem**: The sweep reads `refundAttempt` without a lock and sends `refundAttemptKey(id, attempt)`. Under the lock it then stamps through `markRefundRequested`, which checks only `status = REFUND_PENDING` and `refundRequestedAt IS NULL` (`booking-payment-store.ts:161`). It never compares `refundAttempt` with the attempt it sent. It also ignores `sent.status`, so a `FAILED` result gets stamped as if the refund were under way. With the fake gateway in a CLI process, every refund returns `FAILED` (no session), so staging data will show refunds stamped as requested that never happened. The T5 review raised the same pattern for `requestRefund`, and that resolution added only the status and null checks.
**Why it matters**: Today only one attempt exists, so nothing breaks yet. Once T8 adds `RetryRefund`, a sweep that read attempt n can stamp attempt n+1, and that newer attempt is then never sent. Until the deferred 10-minute refund lookup exists, a definitely failed automatic refund sits in `REFUND_PENDING` with nothing to act on it.
**Suggested fix**: Pass the attempt to `markRefundRequested` and include `refundAttempt = attempt` in its `where`. Use the same `where` for the T5 path. Carry the `FAILED` outcome into T8's `CompleteRefund` hand-off, or note the gap explicitly in the T8 task card.

### 🟡 Lookups in steps A and C do not check that the answer is about the payment that was asked about, `src/application/reservations/reconcile-payments.ts:119`
**Problem**: Step B checks `found.paymentId === payment.id` and `matchesPayment`, through `confirmedTransactionId`. Steps A (line 119) and C (lines 224 to 236) do not. In step C, a `DECLINED` answer about another payment, which would be an adapter fault, leads to this payment's held rows being deleted. A `SUCCEEDED` answer about another payment is applied to that other payment and counted as `recovered`, while this payment's rows stay.
**Why it matters**: It is a defence against adapter faults. The cost is low and it matches step B.
**Suggested fix**: Treat any answer whose `paymentId` differs from the payment asked about as `pending`, in both steps.

### 🟡 `findHeldCleanup` scans every expired or failed payment ever made, on every run, `src/infrastructure/db/prisma/repositories/reservations/payment-sweep-store.ts:66`
**Problem**: The filter is `status IN (EXPIRED, FAILED) AND expiresAt <= now`, sorted oldest first, with semi-joins to `Reservation` and `NotificationOutbox` (`HELD`). Historical abandoned checkouts never leave those statuses, so each 5-minute run walks the whole history through `Payment [status, expiresAt]` before it finds 50 rows that match.
**Why it matters**: The cost grows linearly with every abandoned checkout ever made. It is small today and gets worse every year.
**Suggested fix**: Start from the small set (`NotificationOutbox WHERE status = 'HELD'`, which has an index on `status`) and join to reservation and payment from there. A lower bound on `expiresAt`, such as the fallback window plus a margin, would also keep the scan bounded.

### 🟡 Gateway calls have no deadline and runs have no overlap guard, `src/application/reservations/reconcile-payments.ts:98`
**Problem**: `getTransaction` and `refund` are awaited with no timeout, and nothing stops a second cron run from starting while one is still going. A hung provider call keeps a process and its Prisma pool alive. A new process starts every 5 minutes. Expiry can also take over 1 minute: 100 items, each waiting up to 5 s on a lock. Runs that overlap are safe for correctness, because every write re-checks under the lock and refund keys are idempotent, but they pile up.
**Suggested fix**: Require adapters to time out their calls (state it in `provider-adapters.md` and the contract suite), or wrap the calls in a job-level deadline. A `pg_try_advisory_lock` per job, skipping the run when the lock is taken, would stop the pile-up.

### 🟡 Test gaps for a Critical-tier task, `tests/integration/reservations/payment-jobs.test.ts:314`
**Problem**: The title "whichever of the job and the booking expires the hold" promises both orders, but the test covers only the order where the job holds the lock first. The order where the booking expires the hold and the job skips it is not run against the job. Also missing:
- step C's `discardHeld` racing a late-success callback (the re-check at `reconcile-payments.ts:253` is never reached under contention);
- two parallel `reconcile-payments` runs (the card lists "two concurrent job runs idempotent", but only expiry has this);
- a late success found by reconciliation when the unit has already been resold, so the auto-refund goes out through `applyVerifiedEvent` and the job's own gateway;
- unit coverage of the branches in step C and `confirmedTransactionId`. Integration covers most of them.
**Suggested fix**: Add the reverse-order race (or rename the test), a 20-round discard-vs-late-success race with observed lock waits, a parallel reconcile run that checks one stamp and identical keys, and a reconcile-driven auto-refund case.

## Strengths
- `applyVerifiedEvent` is the one place where an authenticated event is applied. Reconciliation adds no second confirm, late-success, or auto-refund path, so C-12 behavior, idempotency by `providerEventId`, and the redo-to-listing-locks path come for free.
- `expireHoldIfOverdue` is shared by booking creation and the job. It takes only the reservation lock, re-checks status and deadline, and the 20-round races with observed lock waits show that the job is safe against both a success callback and a rival booking. The cross-branch reads are labelled clearly as candidates, and every write re-checks under the lock.
- Step B follows the T5 hand-off exactly. It looks up a missing transaction id, accepts only a matching successful answer, stores the id under the lock, uses the original key, and stamps only after the call returns. The integration tests prove the "young, failed, retried, looked up, refused lookup" sequence.

## Test coverage
New logic is well covered at the integration level on real PostgreSQL with the production wiring: the expiry end state (units, coupon, held rows kept, notice, audit), idempotency and parallel expiry, both lock orders of expiry against a success, expiry against a rival booking (one order), lost-callback recovery and session-closed handling, `NOT_FOUND` and gateway-error no-ops, provider and timing filters, the no-gateway mode, the unsent-refund path (key, stamp, retry, id lookup, refused lookups), held-row cleanup (no-success, success applied, non-transaction answer, 24-hour fallback, confirmed booking untouched), a captured-log check, and the CLI commands. The unit tests are thin (isolation, batch sizes, no-gateway). Gaps are listed in the last Minor: discard racing a late success, parallel reconcile runs, an auto-refund through reconciliation, the reverse-order expiry race, and (from the Major) an early negative lookup followed by a later success.

## Resolution (2026-11-24)

Reviewer verdict was Changes requested with no blockers and one major. The owner asked for the major, every minor, every nit and the deprecation warning to be fixed, then accepted the task. Status:

- **Major, held messages deleted too early: fixed.** A "no success" answer (including `NOT_FOUND`) now deletes the held messages only 30 minutes after the payment's session deadline. Before that the rows stay and the job asks again. A success found at any time before the 24 hour fallback is applied through the late success path. New tests: an early "not found" followed by a later success confirms the booking; a "no success" answer inside the grace period keeps the rows; after it they go.
- **Minor, stuck items block the head of the queue: fixed.** Every sweep reads in pages and excludes the items it already saw in the run (`sweep-pages.ts`), at most 5 pages per run. Unit tests prove a stuck hold and stuck refunds do not stop a newer item. Per item failure ids are not printed; the summary carries counts only.
- **Minor, refund stamp ignored the attempt number: fixed.** `markRefundRequested` takes the expected attempt, used by both the T5 callback refund and the reconciliation refund. A definite `FAILED` refund result is still stamped as sent; refund results belong to M9-T8.
- **Minor, answers not checked against the payment: fixed.** Steps A and C act only on a `TRANSACTION` answer whose payment id matches (the same helper step B uses).
- **Minor, held message query scanned every payment: fixed.** It starts from the held outbox rows (index on status) and then reads those payments.
- **Minor, no gateway timeout or overlap guard: fixed.** Every reconciliation gateway call has a 15 second timeout. Each job runs under a PostgreSQL advisory lock held by a guard transaction in `src/infrastructure/db/prisma/job-lock.ts`; an overlapping run prints `{"skipped":"ALREADY_RUNNING"}`.
- **Minor, test gaps: fixed.** Added the reverse order expiry race, a 20 round cleanup versus late success race, two parallel reconcile runs, an automatic refund triggered by reconciliation, the attempt stamp, and the overlap guard.
- **Nits: fixed.** The counter is now `answered`; no non null assertion; the script narrows commands with type guards and has no cast; `AGENTS.md` lists the new jobs; the dispatch location (`payment-jobs.ts`, avoiding an import cycle) is recorded in the spec.
- **Deprecation warning:** it comes from Prisma's pg adapter (7.10 with pg 8.23) inside interactive transactions and also appears in existing booking and callback tests. It names no data. `scripts/reservations.mts` drops that one notice so cron stderr stays empty; the real fix is a dependency upgrade (revisit in M14).

Gates after the fixes: `npm run check` (2,416 tests, 112 files), integration (940 tests, 60 files), e2e (214 passed, 33 skipped), client bundle scan found none of the six server markers. One architecture test caught composition importing Prisma; the advisory lock moved into the database infrastructure folder.
