## Summary
The change adds the staff guest directory (S50, S51), global block and unblock (S52, S53), and the view-only guest reads G1 (manage token), G3 and G4 (guest session token). The core security design holds up. Bad tokens always get one identical refusal. Ownership is part of every reservation query (unique token hash, or `guest.phone`). Staff reservation lists and counts are filtered by branch. Block takes the phone advisory lock, then the guest row lock, then the verification rows, which matches the existing request, confirm and booking flows, so I found no deadlock path. Logs never contain tokens or the Authorization header. No production bug blocks the merge. The one Major is test adequacy for a Critical-tier task: the approved plan's rollback test is missing, and the race tests do not prove the overlap they claim. Several Minors cover authorization consistency for staff with no branches, a domain check that always passes, and an untested blocked-session branch.

Spot checks run by the reviewer: `npx vitest run` on `tests/unit/application/guest-access.test.ts`, `phone-verification.test.ts`, `persistence-boundaries.test.ts` and the OpenAPI test: 4 files, 48 tests passed. I did not rerun the integration or E2E suites (shared database), so those rest on the author's report and on reading the code.

## Major

### 🟠 The Critical-tier concurrency and rollback evidence is weaker than the plan and the docs claim, `tests/integration/reservations/guest-access.test.ts:563`
**Problem**:
1. "Two parallel blocks write one decision" (`:563-590`) starts two `execute` calls with `Promise.all` and has no barrier and no observed lock wait. The two transactions may never overlap. Without overlap, the idempotency check (`guest-staff.ts:132`) gives "one audit event" even when no lock is taken, so the test cannot tell locked behaviour from unlocked. `tests/integration/reservations/AGENTS.md` (Rules) says "Coordinate overlap with barriers... sleeps are not evidence that transactions overlapped."
2. "A block waits for a booking's guest lock" (`:592-628`) holds a raw `SELECT ... FOR UPDATE` on the guest row. It is not a real in-flight booking or confirmation. The plan (section 8) promised "block versus in-flight booking on the same phone". No test covers the case that motivates `invalidateOpenForPhone`: a `ConfirmPhoneVerification` or `RequestPhoneVerification` racing a block, after which no live token or usable code may survive.
3. The plan's "Rollback: failure injected at the audit write leaves the guest unblocked" test does not exist. Nothing proves that `setBlocked`, `invalidateOpenForPhone` and the audit append commit or roll back together.

**Why it matters**: This is a Critical-tier task, and S52 is its only write and its main concurrency claim (`docs/api/api-contracts.md:145`: "it cannot land halfway through a booking or code check"). The code looks correct when read. Still, the tests would stay green if a future refactor dropped `lockPhone` or `lockById` from `ChangeGuestBlock`, or moved the audit append out of the unit of work.

**Suggested fix**:
- For the parallel blocks: hold the guest row (or the phone advisory lock) on a third client, start both blocks, wait with `waitForLockWaiters(client, 2)`, then release.
- Add a 20-round race where a real `ConfirmPhoneVerification` holds the guest lock (or is made to wait behind the block). Assert that afterwards no row for the phone has a non-null `tokenHash`, and that the issued token gets 401 on G3.
- Add the audit-failure injection test, following the pattern in `change-reservations.test.ts`. Assert `blockedAt` is still null and the verification rows are unchanged.

## Minor

### 🟡 S51 and S52/S53 ignore the "scoped role with no branches" rule that S50 and S2 apply, `src/application/guests/guest-staff.ts:54-65`, `:102-106`
**Problem**: `ListGuests` returns an empty page to a Receptionist or Manager with no branches (`:42-49`). The existing single-record read `loadReservation` (`staff-reservation-reads.ts:138-143`) returns `NOT_FOUND` in the same state. `GetGuest` and `ChangeGuestBlock` have no such check: an unassigned Receptionist can still read a guest's phone, name, email, marketing timestamps, block reason and history by id, and an unassigned Manager can block or unblock any guest everywhere.
**Why it matters**: The authorization model becomes inconsistent. A staff member taken off every branch (a common offboarding step) keeps a global write and a guest profile read. The risk is low, because a guest id is hard to find without S50, but the inconsistency is not documented.
**Suggested fix**: Apply the same `scope !== "ALL" && scope.length === 0 → NOT_FOUND` rule in `loadGuestView` and before the transaction in `ChangeGuestBlock`, and add both cases to the role sweep. If the owner prefers to keep this, document it in the S51 and S52 rows.

### 🟡 The G4 contact check always passes, `src/application/reservations/guest-reservation-reads.ts:67-72` and `:212-216`
**Problem**: For G4, `guestReservationView` passes the session phone both as `grant.phone` and as the `phone` argument of `canReadReservationContact`. `grant.phone.equals(phone)` is therefore always true. The R-8 rule is enforced only by `findForPhone` filtering on `guest.phone`. The domain policy adds no second check, though the comment suggests it does.
**Why it matters**: Defense in depth is lost. If the reader query ever changes (for example to load by reference first), contact data would appear with no domain refusal.
**Suggested fix**: Pass the reservation's own contact phone (`PhoneNumber.parse(stored.contact.phone)` when present) as the `phone` argument, so the policy compares the session phone with the reservation's phone.

### 🟡 The `PHONE_BLOCKED` branch of the guest session is untested and effectively unreachable, `src/application/reservations/guest-reservation-reads.ts:171-174`
**Problem**: Every block clears `tokenHash` on all of the phone's rows (`phone-verification-repository.ts:73-90`), and confirmation refuses a blocked phone, so `findByTokenHash` returns null before the blocked check can run. In practice G3 and G4 answer 401, not the documented `403 PHONE_BLOCKED` (`docs/api/api-contracts.md:52`, OpenAPI error lists). No unit or integration test exercises this branch. The integration test asserts 401 after a block (`guest-access.test.ts:468`).
**Why it matters**: The documented contract does not match what clients will see. An untested security branch can also drift silently.
**Suggested fix**: Add a unit test, or an integration test that sets `blockedAt` directly while keeping a live token, to exercise the 403. Reword the G3 and G4 docs: after a block, existing sessions get 401, and 403 is a defensive fallback.

### 🟡 The audit row stores the staff block reason as free text, which differs from the approved plan, `src/application/guests/guest-staff.ts:149`, `:164`
**Problem**: Plan section 4, step 5, said "audit guest.blocked (reason length only, no free text in the log...)". The code stores the full reason in `AuditEvent.reason`, and S51 returns it as `blockHistory[].reason` to every `guests:read` holder in every branch. The integration log check strips `reason` before asserting (`guest-access.test.ts:540`).
**Why it matters**: This may be the intended reading ("log" meaning the application log; other audit events keep staff reasons). Staff notes about a guest are personal data, though, and here they are retained and shown across branches.
**Suggested fix**: Ask the owner to confirm the deviation. If kept, mention in the threat model or data model that block reasons are personal data retained in the audit log and shown to every `guests:read` holder.

### 🟡 `verificationsInvalidated` overstates the change, `src/infrastructure/db/prisma/repositories/reservations/guests/phone-verification-repository.ts:78-81`
**Problem**: `tokenHash: { not: null }` also matches consumed BOOKING tokens and expired tokens that the daily job has not cleared yet. The `verifiedAt: null, expiresAt > at` branch also re-counts codes already exhausted at 5 attempts. The integration test expects 3 for a case with one live session and one open code (`guest-access.test.ts:499`). Clearing the consumed booking token is harmless: website booking replays match on the idempotency key before any token lookup (`create-website-reservation.ts:146`, `:283`).
**Why it matters**: The audit number reads as "live credentials killed" but counts rows touched. That misleads anyone investigating an incident.
**Suggested fix**: Restrict the match to live credentials: `tokenHash not null AND consumedAt null AND tokenExpiresAt > at`, OR `verifiedAt null AND expiresAt > at AND attempts < max`. Alternatively, rename the field to `verificationRowsCleared`.

## Nits
- ⚪ `src/application/guests/guest-staff.ts:86-90`: the docblock says the lock order "matches phone verification and booking". Only the request flow takes the phone advisory lock; confirm and booking start at the guest row. The order is compatible (a prefix), but the wording is inaccurate.
- ⚪ `src/application/guests/guest-staff.ts:121-129`: the phone used for the advisory lock and `invalidateOpenForPhone` comes from the read before the lock. It is safe today because `Guest.phone` is immutable (`updateContact` leaves it alone, and contact changes relink the reservation instead). A one-line check that `guest.phone === known.phone` after `lockById` would keep it safe if that ever changes.
- ⚪ `src/application/reservations/guest-reservation-reads.ts:121-126`: G1 loads the full reservation (several queries) before checking expiry. An expired token therefore takes longer than an unknown one. This is not exploitable (256-bit tokens), but putting `manageTokenExpiresAt > now` in the `findFirst` where clause is cheaper and evens the timing.
- ⚪ `src/contracts/api/v1/guests.ts:156`: `cancellationRequest: z.null()` means M9 must change the contract type, despite the file comment "M9 fills them in without changing the contract". Consider `CancellationRequestDto.nullable()` now.
- ⚪ `src/app/api/v1/staff/guests/[id]/block/route.ts:9-30`: the strict body is validated in `staffRoute` before the use case authorizes. A Receptionist with an invalid body gets 422, not 403. This is the project-wide pattern, mentioned only for completeness.
- ⚪ `src/infrastructure/db/prisma/repositories/audit/audit-log.ts:72`: `listForGuest` has no `take`. It is fine at realistic volumes, but S51 caps reservations at 100 and the history could use the same cap.
- ⚪ The persistence-boundaries guard (`\.reservation\b`, `\.guest\b`) pushes awkward names such as `record.stored` and `const { guest } = view`. Adding `"Guest"` to `AUDIT_ENTITY_LABELS` is correct and narrow, because it exempts only `entityType` literals and raw SQL on `"Guest"` is still detected.
- ⚪ A possible deadlock between the block `updateMany` and the daily `expire-tokens` `updateMany` on overlapping rows would surface as a 500 (40P01), not `TRY_AGAIN`. The chance is extremely low.

## Strengths
- Token handling is tight. `bearerToken` only splits the header. Format, hash and lookup sit in the use case. Missing, malformed, unknown, expired, rotated and wrong-purpose tokens (including a session token on G1 and a manage token on G3) return byte-identical problems, and the integration test asserts this with `toEqual` on the whole body apart from `requestId`.
- Ownership is built into every query (`manageTokenHash`, `guest: { phone }`). A foreign, unknown or malformed G4 reference gives the same 404, tested with three variants.
- Staff branch scope is applied inside the reader for both counts and reservation lists. The tests sweep admin, scoped, foreign-branch, unassigned and editor roles. Capability checks run before any port call, as the unit test with a zero port-call count shows.
- Block lock order (advisory, then guest row, then verification rows) is compatible with every existing flow I traced: request, confirm, website booking and contact update. Repeats change nothing and write no audit event. Request logs contain only the route pattern, status and principal.
- Docs (api-contracts, test-matrix, both AGENTS.md files) and the OpenAPI (`guestToken` bearer scheme, new components) were updated together with the code.

### New nit from the recheck
- ⚪ `phone-verification-repository.ts:73-99` together with `checkPhoneVerificationToken` (`verification-policy.ts`): the narrower invalidation no longer clears expired or consumed tokens. They keep their `tokenHash` until the daily `expire-tokens` job runs. `checkPhoneVerificationToken` checks `blocked` before purpose, expiry and consumption, so after a block such a stale token (for example the guest's own consumed BOOKING token) gets `403 PHONE_BLOCKED` on G3/G4, not `401`. This is not a real leak, because only the token's holder can present it and the 403 is the documented neutral refusal. It does make the G3 doc wording ("only a defensive fallback for a token that somehow survives a block") slightly inaccurate. Either reword the doc ("an old expired or used token may get 403"), or check token validity before `blocked` in `sessionPhone`.
