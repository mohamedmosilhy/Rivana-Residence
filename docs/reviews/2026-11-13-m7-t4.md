## Summary
M7-T4 adds staff management of branch service offerings (S35, S36) and the global VAT rate (A5): a domain VAT parser, two audited use cases with ports, Prisma repositories under `repositories/reservations/commercial`, composition, thin Route Handlers, Zod contracts, and the OpenAPI document. The production code is correct and follows the task card closely: authorization runs before every repository call, writes and audit events share one READ COMMITTED transaction, an identical PUT writes no audit row, VAT is a non-null integer 0..10000, and the insert-then-lock upsert gives coherent before/after values. The headline issue is the test evidence for the Critical-tier locking claim: both concurrency loops start two writers with a bare `Promise.all` and never prove the transactions overlapped, which `tests/integration/reservations/AGENTS.md` explicitly requires; the busy-lock (`TRY_AGAIN`) path and audit-failure rollback are also not exercised.

## Major

### 🟠 Concurrency tests do not prove overlap or lock waits, `tests/integration/reservations/commercial.test.ts:265` and `:374`
**Problem**: The two 20-round loops fire both writers with `Promise.all` on independent clients and then check audit coherence. Nothing makes the transactions overlap: there is no barrier, deferred signal, or `waitForDatabaseLock` probe on `pg_stat_activity`. If the two transactions happen to run one after the other, which is common with tiny transactions, the assertions pass whether or not `FOR UPDATE` / the `ON CONFLICT` key wait is present. Removing the `FOR UPDATE` in `commercial-settings-repository.ts:42` would most likely still leave these tests green in most runs. The directory's `AGENTS.md` says: "Coordinate overlap with barriers or deferred signals. Observe PostgreSQL lock waits through `pg_stat_activity`; sleeps are not evidence that transactions overlapped." M6's `rates.test.ts` (around lines 620 to 700) shows the expected pattern: the holder blocks inside its audit append, the waiter's backend pid is observed waiting, then the holder is released. Related gaps on the same lock code: (a) neither repository's `55P03` → `TRY_AGAIN` (503, `Retry-After`) mapping is tested (`service-repository.ts:140`, `commercial-settings-repository.ts:62`), although both routes advertise `TRY_AGAIN` in the contract; (b) the "first inserter rolls back" case for the service upsert (the waiter's `ON CONFLICT DO NOTHING` then inserts, and its audit must show `before: null`) has no test, while M6 has the matching case for base rates.
**Why it matters**: The task card names "row/key locks give audit order coherent with commit order" and "concurrent VAT edits yield coherent before/after" as acceptance criteria at the Critical tier. As written, the 20 repetitions do not show that the lock does anything, so a regression in the locking SQL would not be caught.
**Suggested fix**: Rewrite both races in the M6 style: hold the first writer inside a wrapped `audit.append` (row locked, transaction open), start the second writer, `waitForDatabaseLock(observer, pid)` to prove it waits, release, then assert results, final row, and audit `before == previous after`. Order the audits by a deterministic key that does not depend on timing (for example, use the `before === null` audit as the first, as M6 does) rather than `occurredAt` alone. Add one `TRY_AGAIN` test per repository (holder keeps the row or key locked past `lock_timeout`, expect 503 with `Retry-After` and zero audit rows), and one services race where the first inserter rolls back.

## Minor

### 🟡 "Rolls back when the audit append fails" never reaches the audit append, `tests/integration/reservations/commercial.test.ts:253`
**Problem**: The test uses a missing actor id so that "the FK on updatedById rejects the write". That FK fails inside the `INSERT` in `service-repository.ts:84`, before `context.audit.append` is called (`AuditEvent.actorId` has no FK, per `prisma/schema.prisma:650`). So the test proves that a failed upsert persists nothing. It does not prove that a failed audit append rolls back an upsert that already succeeded, which is what the name and comment claim. A5 (VAT settings) has no rollback test at all.
**Why it matters**: The rule "the audit is in the same transaction as the write" is the main promise of the audit design. A future refactor that moved the append outside `unitOfWork.run` would still pass this test.
**Suggested fix**: Inject a failing `AuditLog` through the context factory (as `rateUseCases(..., { audit })` does in M6). Assert that the use case rejects and that no `ServiceOffering` row exists or the VAT stays at 1500. Do this for both use cases.

### 🟡 A description-only edit writes an audit event whose before and after are identical, `src/application/services/manage-services.ts:111` (with `service-repository.ts:117`)
**Problem**: The repository's `same` comparison includes `description`, so changing only the description returns `changed: true`. The audit snapshot leaves out the description on purpose (`audit-event.ts:20`), so the event records `before` and `after` with the same values. No test covers this case.
**Why it matters**: An auditor sees a `service.update` event that appears to change nothing. That is confusing and looks like a bug. The behavior is defensible (it records who touched the row and when), but it should be a deliberate, visible choice.
**Suggested fix**: Pick one of two options. (a) Add a non-personal flag such as `descriptionChanged: boolean` to the `service.update` changes. (b) Document that a description-only edit is audited with equal snapshots and add a test that pins it. Option (a) keeps the free text out of the audit and still explains the event.

### 🟡 Branch routes do not record the branch on the request log, `src/app/api/v1/staff/branches/[id]/services/route.ts:8`, `[kind]/route.ts:11`
**Problem**: Every existing `branches/[id]/*` route (blocks, physical-rooms, availability, the branch itself) calls `setBranch(branchId)` so the request log line carries the branch. The new S35 and S36 handlers do not.
**Why it matters**: Logs for service edits cannot be filtered by branch, unlike the M6 endpoints next to them. It is a small observability regression and an inconsistency with the routes around it.
**Suggested fix**: Destructure `setBranch` and call it with `String(params.id)`, as `blocks/route.ts` does.

## Nits
- ⚪ `src/application/services/ports.ts:34`, the `now` comment says it is "Read after the row lock is held". On the insert path, `write.now()` is evaluated when the `INSERT` is built (`service-repository.ts:94`), before any key wait. Ordering is still coherent, because only the first inserter for a key keeps that timestamp. Reword the comment to say so.
- ⚪ `docs/api/openapi.json` (S36), the `{kind}` path parameter is typed as plain `string`. Advertising `enum: [BREAKFAST, AIRPORT_TRANSFER]` would let clients and generated SDKs validate it, if the route generator can express it.
- ⚪ `src/domain/audit/audit-event.ts:22,87`, `ServiceSnapshot.priceUnit` and `changes.kind` are typed `string`. `ServicePriceUnit` / `ServiceKind` would keep the audit shapes exact, which is the stated purpose of `AuditChanges`.
- ⚪ `src/application/services/manage-services.ts:35`, `money()` hardcodes `"USD"` instead of passing `value.currency` through. That is safe because of the DB CHECK, but `money(record.price)` would not need the cast.
- ⚪ The HTTP wrapper validates the body against the contract before the use case authorizes. A Receptionist sending a malformed VAT body therefore gets 422, not 403. This is the existing `staffRoute` design (shared with M6), not something introduced here, and it reveals nothing. Mentioned only so the order is a known choice.

## Strengths
- Authorization comes first everywhere. `authorize`/`authorizeBranch` run before parsing, before `branchExists`, and before the transaction, and the tripwire sweep plus the unit tests (`services.branchExists not called`, `unitOfWork.run not called`) prove it.
- The insert-then-lock upsert (`INSERT … ON CONFLICT DO NOTHING` followed by `SELECT … FOR UPDATE` under READ COMMITTED) handles the create race without a separate advisory lock. The no-op detection returns the stored row, so an identical PUT writes no row update and no audit event. The `55P03` → `TRY_AGAIN` handling and the `ResultAbort` rollback match M6.
- VAT validation is strict and complete: integer, 0..10000, no null, unknown keys refused. Unit and integration tests cover -1, 10001, fractions, null, string, missing, and both bounds, and they check the stored rate and the audit count after each refusal.
- The new `route-segments.test.ts` guards a real Next.js startup failure that `next build` does not catch, and it explains the `[id]` deviation.

## Test coverage
Covered: the VAT parser (domain unit), both use cases with fakes (authorization order, audit shape, no-op skip, the 422 cases including a child price on a non-person unit and unknown keys), additions to the authorization sweep for all four calls with role expectations, and HTTP-level integration on PostgreSQL.
