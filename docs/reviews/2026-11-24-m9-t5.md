## Summary
The change adds P8 (`POST /api/v1/payments/callback`) and `ProcessPaymentCallback`: adapter verification, per-event recording, on-time confirmation under the reservation lock, decline and session-closed handling, and a late-success path that takes listings, then coupon, then reservation, re-checks capacity and either re-confirms or refunds after commit. The lock rule is respected on every path I traced (no listing lock after a reservation lock; the redo path commits the reservation-only transaction before opening the listing-lock one), duplicates serialize correctly on the reservation or listing lock with the `APPLIED` check under that lock, and no path confirms without a verified, provider-, amount- and currency-matched payment. The one major issue is test adequacy for a Critical task: the redo branch (success read as awaiting, found `PAYMENT_FAILED` under the lock) is not exercised, and the planned unit and E2E tests are absent. The rest are minors around refund bookkeeping, defensive storage of event fields, and spec drift.

## Major

### 🟠 The reservation-lock-to-listing-lock redo path and planned unit/E2E tests are missing, `src/application/reservations/process-payment-callback.ts:196`
**Problem**: The branch at lines 196 to 201 (unlocked read saw `AWAITING_PAYMENT`, the hold ended before the lock, so the reservation-lock transaction returns `{ redo: true }` and `handle` re-runs under listing locks at line 139 to 140) is never executed by any test. Every late-success test in `tests/integration/reservations/payment-callback.test.ts` reaches `PAYMENT_FAILED` before the callback starts, so `handle` goes straight to `applyUnderListingLocks` (line 133 to 140). The approved plan listed "success racing expiry" in the integration tests, a unit test file `tests/unit/application/process-payment-callback.test.ts` covering every outcome and result code, and an E2E "simulated checkout success reaches CONFIRMED". None of these are in the change. Also untested: parallel duplicates of a *late* success, a success on a non-awaiting, non-failed reservation (the cancelled auto-refund branch documented in the spec notes), a success with no `providerTransactionId`, and a token rotation that leaves the email unchanged (the T4 handoff test changes the email and nulls the hash in one step, so it does not isolate the link check at lines 464 to 473).
**Why it matters**: This is a Critical-tier task, and the redo path is exactly where C-12 and C-14 meet. An error there (for example, stale `read.lines` or the coupon lock ordering) would confirm or refund wrongly only under a narrow race that no test reaches.
**Suggested fix**: Add a real PostgreSQL race where a success callback is paused after its unlocked read (or while waiting on the reservation lock) and a session-closed or in-transaction expiry commits first. Assert that the callback re-runs under listing locks (observed lock waits), and that the result is confirm-late or refund depending on resale. Add the planned unit test with fake ports for each `PaymentEventResult` and decision branch (including cancelled-reservation auto-refund, missing transaction id, token-only rotation), and the E2E simulated-checkout case, or record the owner's decision to drop them.

## Minor

### 🟡 Refund result is discarded and the "requested" stamp is unconditional and unlocked, `src/application/reservations/process-payment-callback.ts:486`
**Problem**: `requestRefund` ignores `sent.status`, so a definite `FAILED` from `gateway.refund` is stamped as requested. `markRefundRequested` (`booking-payment-store.ts:145`) updates by `id` only, outside the reservation lock that the port comment requires for writes. It does not check that the payment is still `REFUND_PENDING` at the same `refundAttempt`.
**Why it matters**: In T5 only one attempt exists, so the race is latent. Once T8 adds retries, a slow attempt-n response can stamp `refundRequestedAt` on attempt n+1, so the T6 null-stamp sweep skips the newer attempt. A definite failure sits as `REFUND_PENDING` until the T6 10-minute lookup, while the guest and staff were told the refund is under way.
**Suggested fix**: Make the stamp conditional (`where id, status REFUND_PENDING, refundAttempt = attempt`), passing the attempt through `RefundRequest`. Record the definite outcome for T8, or at least note in the spec that T5 deliberately drops it.

### 🟡 Auto-refund without a transaction id can never be refunded, `src/application/reservations/process-payment-callback.ts:327`
**Problem**: When neither the event nor the payment has `providerTransactionId`, the payment becomes `REFUND_PENDING` but no refund request is built. The T6 sweep will hit the same gap, because `RefundInput.providerTransactionId` is required.
**Why it matters**: Captured money stays stuck in `REFUND_PENDING` with no actor.
**Suggested fix**: Treat a success without a transaction id as a contract violation (record it as ignored, or alert staff explicitly), or document that adapters must always supply it and cover it in the contract suite.

### 🟡 Held confirmations (with raw manage tokens) stay `HELD` after an automatic refund, `src/application/reservations/process-payment-callback.ts:308`
**Problem**: The refund branch never calls `discardHeld`. The resale test asserts that no confirmation is `PENDING`, but three `HELD` rows remain. Their payload carries a working manage link for a `PAYMENT_FAILED` booking. T6's cleanup criteria (payment `EXPIRED` or `FAILED`) no longer match because the payment is now `REFUND_PENDING`, so only the 24-hour fallback removes them.
**Suggested fix**: Discard held rows in the refund branch, in the same transaction.

### 🟡 Event fields are stored without checking column bounds, `src/application/reservations/process-payment-callback.ts:176`
**Problem**: `amountMinor` is kept whenever it is a safe integer, but the column is `Int` (int4). `currency` goes into `Char(3)` and `providerEventId` into `VarChar(120)` unchecked. A verified event outside those bounds, for example a mismatched amount above 2^31 - 1, throws inside the transaction. The route returns 500, the gateway retries forever, and the event is never recorded.
**Suggested fix**: Store `null` for out-of-range amounts and non-3-letter currencies, and refuse or truncate an over-long event id deterministically. The adapter contract suite can assert the id length.

### 🟡 Late success counts overdue, unexpired holds as sold, `src/application/reservations/process-payment-callback.ts:383`
**Problem**: Booking creation runs `expireListingPaymentHolds` under the listing locks before counting (AGENTS.md, T4). `unitsFree` does not, so an overdue `AWAITING_PAYMENT` hold still consumes the unit.
**Why it matters**: The result is conservative (no oversell), but a paying guest can be auto-refunded for a unit that is free in practice.
**Suggested fix**: Call `expireListingPaymentHolds` inside `load` after the listing locks and before the coupon and reservation locks, or record the conservative choice in the spec.

### 🟡 A second success with a different transaction is silently ignored, `src/application/reservations/process-payment-callback.ts:302`
**Problem**: `IGNORE_DUPLICATE` covers both a replay and a distinct capture (a different `providerTransactionId` on an already `SUCCEEDED` payment). The second is recorded `IGNORED_STATE` with no alert.
**Why it matters**: If a provider ever allows two captures for one order, the second charge is never noticed. Whether that can happen depends on the gateway.
**Suggested fix**: When the transaction id differs from the stored one, enqueue a staff alert, or at least log the ids and outcome. Add a contract-suite note.

### 🟡 No staff alert for the automatic refund of a non-failed reservation, `src/application/notifications/reservation-messages.ts:45`
**Problem**: `payment.staff-alert` is gated on `PAYMENT_FAILED`. A success that reaches a cancelled awaiting booking is refunded with no message to anyone, only an audit row. The spec note records the guest-message gating, but the staff alert is what lets the hotel notice money movement.
**Suggested fix**: Let the staff alert through for any auto-refund (keep the guest message gated), or confirm with the owner that this is intended.

### 🟡 Spec drift on audit actions and mismatch logging, `src/application/reservations/process-payment-callback.ts:342`
**Problem**: Spec 0006 Decision 10 lists `payment.confirmed` and `payment.refund-requested`. The code writes `payment.succeeded` and `payment.auto-refund-pending`. Decision 5 says `IGNORED_MISMATCH` is "logged without payload", and Decision 10 asks for captured-log tests, but the use case writes no log line at all and no captured-log test exists. `security-controls.md` now states that "callback logs carry no payload", which is true only because nothing is logged.
**Suggested fix**: Align the names in the spec or the code. Either add an id/kind/result-only log for ignored events with a captured-log test, or amend the spec to say the `PaymentEvent` row is the record.

### 🟡 Port contract "an applied row is never changed" is not enforced by the adapter, `src/infrastructure/db/prisma/repositories/reservations/booking-payment-store.ts:103`
**Problem**: The upsert's `update` overwrites `result` unconditionally. Callers check first (under a lock in `apply`, but not in `recordOnly`), so the invariant depends on every caller. Today the same event id always takes the same path, so this is latent.
**Suggested fix**: Make the update conditional on `result <> 'APPLIED'`, for example a raw `ON CONFLICT ... DO UPDATE ... WHERE`, or narrow the port comment.

## Strengths
- The lock rule is implemented exactly as the spec states. The redo path commits the reservation-only transaction before opening the listing one, so no listing lock is ever taken after a reservation lock. The two 20-round C-12 races with observed lock waits prove both orders.
- Idempotency is decided under the same lock that serializes the write (`apply` re-reads `findEventResult` after `lockById` or the listing locks). A failed `Result` rolls back without recording, so a retried event is still applicable.
- The held-message handoff is careful: recipient equality plus token-hash verification, with rotate-and-requeue as the safe fallback.
- The refund call runs after commit, with a deterministic key (`refundAttemptKey`) and a null stamp on a throw, which T6 can pick up.
- The 401 path is uniform (absent gateway, thrown verify, rejected verify) and leaks no detail. The route is thin.

## Test coverage
Covered on real PostgreSQL: on-time confirm and held release with dispatch, 5 parallel duplicates (one `APPLIED`, one version bump), forged, altered and unsigned bodies, amount, currency and unknown-payment mismatches, decline then session-closed (coupon released, held kept), `REFUND` events recorded as `IGNORED_STATE`, late success with free units (coupon reacquired), resale refund (refund key, one gateway call on replay, thrown refund leaves a null stamp), lost held rows (token rotated), email change plus revoked token, and two 20-round C-12 races. The route test covers 200, replay, 401 without detail, and 413.

Not covered: the reservation-lock to listing-lock redo path, parallel duplicate late successes, the cancelled-reservation auto-refund branch, a success without a transaction id, token-only rotation, out-of-range event fields, captured logs, the planned unit-level use case test, and the planned E2E.
