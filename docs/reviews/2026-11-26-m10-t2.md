## Summary

The change adds the public `/{branch}/book` search page. It is a native GET form that works without JavaScript, gets its results from the existing P5 use case through the shared `availability` limiter, shows exact nightly prices and a stay total before VAT, and gives plain reasons for unavailable listings. When the branch is not bookable now, the branch contact fallback replaces the form. A narrow `GetBookingSearchSetup` read uses the same readiness rule as P7. The limiter wiring now lives in its own composition module, so the scheduled CLI jobs never import it. Branch boundaries, readiness parity, date and price semantics, and analytics privacy are correct. No blockers or majors. The findings are about diagnostics, test strength, an e2e rate limit budget, and one missing regression guard.

## Minor

### 🟡 The failed search path loses all diagnostics and can catch Next control flow errors, `src/app/(marketing)/[branch]/book/page.tsx:45`

**Problem**: `runSearch` catches everything and logs the fixed string `"Booking availability search failed."` with no error class or code. The `try` also wraps `await headers()`.
**Why it matters**: Scenario: the database pool runs out, or the rate limit store throws. Every guest sees "We couldn't check availability", and the log line cannot tell a database outage from a programming error. The existing convention in `src/app/(marketing)/actions.ts:32-38` logs `error.name` and `error.code` without personal data. Wrapping a Next request API in a bare `catch` can also swallow Next's internal control flow errors. The route is dynamic today, because `searchParams` is awaited first, so the risk is latent, not live.
**Suggested fix**: Read `await headers()` before the `try`, or call `unstable_rethrow(error)` first in the `catch`. Log the error class and code the way `actions.ts` does, for example `[booking-search] availability failed: <name> (code <code>)`.

### 🟡 The privacy part of the e2e analytics test can pass when suppression is broken, `tests/e2e/booking-search.spec.ts:266`

**Problem**: After one recorded row, the test sends three suppressed requests (DNT, Sec-GPC, `Purpose: prefetch`) and then one normal request. It then polls until `toHaveLength(2)`. Rows are written in `after()`, so they arrive asynchronously.
**Why it matters**: Scenario: a regression stops honoring `DNT`. The DNT request writes a row, so the count reaches 2 before the later rows land, and `expect.poll` passes at that moment. The test meant to prove request privacy would stay green. The domain filter has unit coverage from T0a, so this is a weak test, not a live bug.
**Suggested fix**: Assert the stable end state, not the first time the count matches. One way: after the final normal request, poll until 2 rows, wait briefly, and check that it is still exactly 2. Another: select the rows with `occurredAt` and check that none is dated between the first recorded event and the final normal request.

### 🟡 The focused e2e run uses most of the shared per client search budget, `tests/e2e/booking-search.spec.ts:106` (with `playwright.config.ts:103`)

**Problem**: Each browser project runs about 10 page searches: 2 in the keyboard test, 2 in the invalid dates test, and 6 in the analytics test. All of them come from loopback and land in one `availability` bucket of 60 per minute (`src/application/shared/public-rate-limit-policy.ts:6-9`). With `CROSS_BROWSER=1`, the focused run has 5 projects running in parallel, which is about 50 searches in the same minute.
**Why it matters**: Scenario: CI retries one failed test (`retries: 2`), or someone adds one more search per test. The bucket passes 60, the page renders "Too many searches", and an assertion on "Available stays" fails for a reason that has nothing to do with the change.
**Suggested fix**: The e2e server already sets `AUTH_TRUST_PROXY_HEADERS=true`. Give each project its own `X-Forwarded-For` through `use.extraHTTPHeaders`, and also through the no-JavaScript `browser.newContext` in the first test. The analytics test's `setExtraHTTPHeaders` calls must then keep that header. Or cut the searches per project.

### 🟡 Nothing guards the CLI import isolation that this change restores, `src/composition/public-rate-limit.ts:4`

**Problem**: `public-rate-limit.ts` imports `throttleKeys` from `@/composition/auth`, which imports `next/navigation`, `next/headers`, `react` `cache`, and Better Auth. I checked that only `src/composition/api.ts`, `src/composition/booking-search.ts`, and one integration test import it. No module reachable from `scripts/reservations.mts`, `scripts/analytics.mts`, or `scripts/throttles.mts` imports it, so the earlier regression is fixed today. But no test enforces this. `tests/integration/reservations/payment-jobs.test.ts` imports `payment-jobs` under Vitest, not under `tsx --conditions=react-server`, so it would not catch a reintroduction.
**Why it matters**: Scenario: a later task imports `consumePublicRateLimit` or `searchAndRecordAvailability` into a module the jobs share, such as `composition/analytics.ts` or `composition/http.ts`. `npm run reservations -- reconcile-payments` would again load Next navigation and React code, and the problem would only show when the cron job runs.
**Suggested fix**: Add an architecture test that walks the static and dynamic imports from `src/composition/{payment-jobs,reservation-jobs,analytics-jobs,throttles}.ts` and fails on `@/composition/auth`, `@/composition/api`, `@/composition/booking-search`, `@/composition/public-rate-limit`, or `next/navigation`. Or add a CI smoke run of each CLI with a no-op or help argument.

### 🟡 Page outcome branches and reason texts have no test, `src/app/(marketing)/[branch]/book/page.tsx:78`

**Problem**: The page maps the P5 result to its UI. `NOT_FOUND` becomes a 404, `VALIDATION` becomes field errors, `RATE_LIMITED` shows "Too many searches" with the wait time, and a thrown error shows the generic message. Only the `VALIDATION` mapping is exercised, by the invalid dates e2e. The integration test proves the composition returns `RATE_LIMITED` with `retryAfterSeconds: 60`, but nothing renders it. The `OCCUPANCY` and `UNPRICED` texts in `src/presentation/features/booking/availability-results.tsx:28-32` are never asserted. The no availability e2e (8 adults) lists every listing as `OCCUPANCY` but checks only the heading.
**Why it matters**: This is branching UI logic for failure cases. A wrong key or a swapped condition, for example showing the generic error when rate limited or the wrong reason text, would ship unnoticed.
**Suggested fix**: In the existing no availability e2e step, assert "Does not fit the number of guests entered." Add a small render test, or extract a pure `searchView(result, queryErrors)` helper and unit test it for `RATE_LIMITED`, a thrown error (`null`), `VALIDATION` with field errors, and `UNPRICED`.

## Nits

- ⚪ `src/presentation/features/booking/stay-search-form.tsx:81`: the check-out `min` is `today`. `today + 1` would match "check-out after check-in" for the earliest stay. P5 still validates, so this is only friendlier native validation.
- ⚪ `src/app/(marketing)/[branch]/book/search-query.ts:1`: query parsing and display defaults sit in `src/app`, and a unit test imports them through `@/app/...`. `src/presentation/features/booking/` would keep `app` to routing only. Optional.
- ⚪ `src/application/booking/get-booking-search-setup.ts:10`: spec 0007 plans `GetBookingSetup` for T4. T4 should extend or replace this class, not add a second readiness read, so the search page and the details page cannot disagree about `bookable`.
- ⚪ `tests/e2e/fixtures/public-content.mts:~119`: the rate period date is computed at prepare time, and the tests compute `today()` at run time. A run that crosses Cairo midnight would move the $140 night. This is very unlikely. Computing both from one fixed offset recorded in the database would remove it.
- ⚪ `src/presentation/features/booking/stay-search-form.tsx:69`: the error summary has a title only. A list of the field errors with links to the inputs (GOV.UK pattern) would help screen reader users. The fields already use `aria-describedby`, so this is optional.

## Strengths

- **Branch boundaries hold**: the page resolves the branch with `requireBranch`, re-reads it fresh in `GetBookingSearchSetup`, and passes only the server's `branch.slug` to P5, which resolves it again. `room` is used only for highlighting, and links use `search.branchSlug`. The e2e checks that no Giza, draft, or retired listing appears.
- **Readiness matches P7**: the rule is `onlineBookingEnabled`, then `checkInTime`, then `verificationUsableForBranchNow(channels, branch.onlinePaymentEnabled && gatewayReady)`, the same helper and order as `create-website-reservation.ts:234-250`, so email counts only when online payment is usable. The rendering is dynamic per request: a dynamic segment without `generateStaticParams`, plus no cached repository. The unit table covers the email, payment, and gateway combinations, and checks that channels are not queried when a prerequisite is missing.
- **Date and price semantics are right**: the branch today comes from `localDateAt`. The `max` attributes match `validatePublicStay` exactly (540 days inclusive for check-in, plus 30 nights for check-out). Every P5 issue path (`checkIn`, `checkOut`, `adults`, `children`) reaches a field, so a validation error never falls through to the generic message. Nights are listed from check-in by offset and formatted in UTC. The copy says "Stay total for one unit, before VAT", which matches P5's default `unitsRequested = 1`.
- **Analytics are private and have no side effects on the booking**: the page passes an explicit `null` session, so a header sent with the GET is ignored. `RecordFunnelStep` keeps only `NO_AVAILABILITY` without a session, `omitSiteEvent` covers DNT, GPC, prefetch, and bots, and the write runs in `after()`. No hold, booking write, REST, schema, or provider change.
- **The limiter is shared correctly**: same `AVAILABILITY_RATE_LIMIT` bucket and keys as P5. The integration test proves that 59 P5 calls plus 1 page call use up the window, both paths then get 429, and both recover after 60 seconds. Malformed input is refused before the limiter is consumed.
- **No duplicate ids**: `search-feedback` is used by the general error, the form error summary, and the results heading, but I checked that the three render conditions never overlap, so the `#search-feedback` fragment always focuses exactly one heading.
- **Seed and fixture setup are scoped**: the demo search example is only in the demo seed, and its test checks `demo-giza` stays off. The browser setup for bookable search runs only under `BOOKING_SEARCH_E2E=1`, needs `E2E_DATABASE_URL`, refuses to reuse a running server, and uses a fictional token that is never sent.
