# Review, m10-guest-booking-journey (M10-T6b), 2026-11-27

**Reviewed by**: Claude Opus 5.5 (claude-opus-5-5), fresh context (author on a different session/model)
**Scope**: 46 files (43 modified, 3 new: the migration, `stay-dates.tsx`, `stay-dates.test.tsx`), uncommitted
**Verdict**: Approve with nits

## Summary

M10-T6b adds two optional branch settings, latest check-in (`checkInUntilTime`) and earliest check-out (`checkOutFromTime`). It enforces them in three places: the domain rule on create, the merged patch in `ManageBranches.update`, and PostgreSQL CHECKs. It then shows each stay date with the hotel's hours in the "Your stay" panel (both summaries, review included) and on the confirmation page, through one `StayDates` component. The change does what the approved card says. The migration is safe on existing data. The cross-field rules read the stored row when a patch carries only one side of a pair. The API change is additive. Price, availability and the cancellation deadline are not touched. I found no blocker or major issue. The Minor findings are: `StayDates` crashes on an `undefined` time, which a stale on-disk public cache can supply; `api-contracts.md` does not list the new fields; and a few rule paths are untested at the route level.

## Minor

### 🟡 `StayDates` crashes on an `undefined` window, which a stale public cache entry can supply, `src/presentation/features/booking/stay-dates.tsx:19`

**Problem**: `arrival` and `departure` test `checkInUntilTime === null` and `checkOutFromTime === null` (lines 19 and 27). The confirmation page takes these values from `requireBranch` (`src/app/(marketing)/[branch]/book/confirmed/page.tsx:22-27`). `requireBranch` reads the `PublicBranch` list through `unstable_cache` (`src/composition/public.ts`, key `["public","branches"]`, no revalidate). Next 16 builds that key from `cb.toString()` plus the key parts (`node_modules/next/dist/server/web/spec-extension/unstable-cache.js:54`). Neither changed in this diff, so a `.next/cache/fetch-cache` entry written before the migration is still served after it, and that entry has no `checkInUntilTime` or `checkOutFromTime`. For a branch with `checkInTime` set, `undefined === null` is false, so `range("14:00", undefined)` calls `displayTime(undefined)`, and `undefined.split` throws. The confirmation page then fails to render, right after the guest has booked. The same stale entry also leaves the two fields out of `GET /api/v1/branches/{slug}`, although the contract marks them required.
**Why it matters**: The production flow builds every release in a fresh `releases/<id>` directory (`docs/operations/deployment.md`, step 4), so a production deploy should start with an empty fetch cache. The risk is real in any checkout that keeps `.next/cache` between builds: local review, the demo site, staging, or a manual rebuild in place. The entry clears only after a branch edit or a manual cache wipe. It is a cheap failure to remove.
**Suggested fix**: Make `StayDates` treat a missing value like null: test with `== null`, or normalize the four times at the top of the component. Optionally add a line to the T6b deployment note: clear `.next/cache/fetch-cache` when a build reuses the directory. Add one `StayDates` test case that passes `undefined` windows.

### 🟡 `api-contracts.md` does not mention the new fields, `docs/api/api-contracts.md:40`

**Problem**: API-P2 (line 40) still describes `BranchDetail` as "check-in and check-out times". API-A3 (line 172) lists `checkInTime` and `checkOutTime` among the patchable fields, but not `checkInUntilTime` or `checkOutFromTime`, and not their cross-field rule. `openapi.json`, the data model, the branch model and the spec were updated. This document was not.
**Why it matters**: AGENTS.md requires the docs to stay in sync with the code. `api-contracts.md` is the readable index of the REST API. A client author reading it would not know the fields exist or that a window needs its main time.
**Suggested fix**: In API-P2, add "latest check-in and earliest check-out (Q-102)". In API-A3, add `checkInUntilTime` (later than `checkInTime`, same day) and `checkOutFromTime` (earlier than `checkOutTime`). Note that each needs its main time, so clearing a main time that has a window returns `422` with a field error on the window.

### 🟡 Some rule paths have no test: the route level, the check-out clearing case, and clearing both together, `tests/unit/domain/branch-websites.test.ts:347`

**Problem**: The new `ManageBranches` test covers three refusals: a new check-in that passes the window, clearing `checkInTime` while a window exists, and an invalid `checkOutFromTime`. It also covers one success. Untested:
- Clearing `checkOutTime` while `checkOutFromTime` is set.
- The intended way out, clearing a main time and its window in one patch (`{ checkInTime: "", checkInUntilTime: "" }`), which must succeed.
- The strict `BranchPatch` and `BranchInput` contracts at the route. `tests/integration/branch-api.test.ts` was not touched, so nothing sends the new keys through `PATCH /api/v1/staff/branches/{id}` or `POST`, and nothing asserts the `422` field error shape at HTTP level or the two fields in the `GET /api/v1/branches/{slug}` body.
- The database refusal as the repository sees it, for example a concurrent edit that passes the use case but violates a CHECK. The integration tests use raw `client.branch.update` for the CHECKs, not `PrismaBranchRepository.update`.

**Why it matters**: The card names "clearing a main time that has a window" and "the API contract being additive" as attention points. The strict contract would reject the new keys with a 400 if someone dropped them from `branchFields`. Only the OpenAPI snapshot would notice, not a behavior test.
**Suggested fix**: Extend the unit test loop with the check-out clearing refusal and the clear-both success. Add one `branch-api.test.ts` case: a PATCH that sets a valid window (200), a PATCH that clears `checkInTime` while the window exists (422 with `fieldErrors.checkInUntilTime`), and a GET of the detail that contains both fields.

## Nits

- ⚪ `src/application/branches/manage-branches.ts:191-245`: the row is read, merged and checked without a lock, so two concurrent saves can each pass the merged rule and the second hits a CHECK. `translatePrismaWriteError` turns that into a generic `VALIDATION` "A value violates a content rule." with no field error. The data stays correct (the CHECK is the real guard), and the sync minutes rule already works this way. A short comment, or mapping the two constraint names to field errors, would make the rare case clearer.
- ⚪ `src/presentation/features/booking/price-summary.tsx:46` and `selection-summary.tsx:32`: the two-column `dl` sits in a sidebar that is at least 18rem wide at `lg`. "12:00 AM – 11:30 AM" in `text-small` may wrap inside a column of about 110px, for example after the dash or between "11:30" and "AM". I could not check this (no T6b screenshots yet, and no browser runs allowed). If it wraps badly at 1024 to 1280 px, use a non-breaking space between the time and AM/PM in `displayTime`, or `whitespace-nowrap` on each time.
- ⚪ `src/presentation/features/booking/display-date.ts:22`: `[hour = 0, minute = ""]` mixes a number default into a string tuple. It works, because the input is always `HH:MM` under the CHECK, but `const [hour, minute] = time.split(":")` with `Number(hour)` reads more plainly.
- ⚪ `src/presentation/features/booking/stay-dates.tsx:13-14`: a screen reader reads the en dash range as "2:00 PM 11:30 PM" or "2:00 PM dash 11:30 PM". Visually hidden "to" text, or `aria-label` on the hours `dd`, would read more naturally. This is optional and does not block AA.
- ⚪ The details page and the confirmed page each build the same four-field `times` object by hand. A small `stayTimes(branchLike)` picker next to `StayTimes` would keep M10-T8 (manage page) from building it a third time.

## Strengths

- **Migration safety on existing data.** It adds two nullable columns and three CHECKs that pass on NULL. Every existing row passes immediately, with no backfill. Rows written by the previous release during a deploy (no new columns) also pass, and the previous release's own format CHECK already restricts `checkInTime` and `checkOutTime` to `HH:MM`. That makes the text comparison in the new CHECKs sound.
- **Correct merged patch handling.** `pick` uses the patch value when the key was sent (a blank becomes `null`, so clearing counts) and the stored value otherwise. A patch that carries only one side of a pair, or that clears a main time under an existing window, is judged against the full result. `parseBranchUpdate` already stops defaults from leaking in. The same `branchCrossFieldIssues` runs in `branchCreateSchema`, so create and update cannot drift apart.
- **Defense in depth.** The domain, the use case and PostgreSQL share one rule. The integration test proves each constraint by name, including the equal-time boundary on both sides.
- **The contract change is additive.** The response gains nullable fields. The request schemas gain optional keys. `UpdatedStaffBranch` and the guest reservation API are unchanged. The OpenAPI snapshot test passes (`tests/unit/architecture/openapi.test.ts`, 6/6, run by this review).
- **Every branch save and display path was found.** That covers the repository select, `BranchRow`, `PublicBranch`, the DTO, both admin pages, `BRANCH_FORM_FIELDS` (so the Server Action forwards the fields), the audit diff (through `changedFields`), the demo seed (new branches only; existing demo rows untouched), and the production seed (the empty-field fill only touches `checkInTime` and `checkOutTime`).
- **The confirmation page uses branch times safely.** It shows the route branch's times only after the client has checked `result.data.branch.slug === contact.slug`, so it never shows another branch's hours.
- **Tests are behavior focused.** `stay-dates.test.tsx` covers every 12-hour edge (00:00, 00:30, 11:59, 12:00) and each fallback (both windows, main times only, no check-out time, none). The confirmation test asserts the full definition list in order (11/11 passing, run by this review).
