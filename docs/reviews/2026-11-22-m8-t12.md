## Initial minor findings

### 🟡 Unknown query parameters reach both handlers, `src/app/api/v1/staff/branches/[id]/sync-checkpoints/route.ts:7`

**Problem**: Neither S28 nor S29 declares a query schema. The shared wrapper skips query validation in that case (`src/app/api/v1/_http/routes.ts:213`). The REST conventions specify a 400 for unknown parameters (`docs/api/rest-api-conventions.md:37`).

**Why it matters**: An authorized POST with a valid body and an unsupported query parameter still appends a checkpoint. With the two routes' actual wrapper options and stub success handlers, adding `?preview=true` reached both handlers and returned 201 and 200.

**Suggested fix**: Declare an empty strict query schema for these two routes, document `INVALID_QUERY` in OpenAPI, and cover the 400 on each method. For POST, check that the rejected request leaves both tables untouched.

### 🟡 The availability contract accepts arbitrary checkpoint text, `src/contracts/api/v1/inventory.ts:157`

**Problem**: S20's `lastSyncCheckpoint` accepts any string. I passed `"yesterday"` to its Zod schema and it succeeded. S29's schema rejected the same value for `lastCompletedAt`. Both represent the same UTC instant.

**Why it matters**: The S20 DTO mapper emits valid timestamps today, but contract validation would accept a malformed response. OpenAPI consumers also miss the date and time format on this field.

**Suggested fix**: Use the same nullable UTC datetime schema as S29 and regenerate OpenAPI. A contract assertion can pin acceptance of a real UTC instant and null, and rejection of arbitrary text.
