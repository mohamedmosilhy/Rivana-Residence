## Major

### 🟠 The started stay capacity check has no refusal test, `src/application/reservations/modify-reservation.ts:365`
**Problem**: For a started stay the use case checks capacity only on the added nights (`checkedStay` is the range from the old check out to the new one, or null when no night is added). The only integration test of this branch, "extends the check out without touching the nights already consumed" at `tests/integration/reservations/change-reservations.test.ts:1462`, extends into a night that is free. No test fills the added night and expects `409 INVENTORY_UNAVAILABLE`, and no test shows that a sold out night before today does not block a legitimate extension or shortening. The `checkedStay === null` path (shortening or an occupancy only change on a started stay) is never run against the database.
**Why it matters**: This is new branching code on the oversell path of a Critical task. If a later edit made `checkedStay` null for an extension, or read the wrong range, every current test would still pass and the hotel could be oversold on the extension nights.
**Suggested fix**: Add three small database tests with the later clock: (1) fill the night of 13 April for the listing with another booking or a block, extend to 14 April, expect `INVENTORY_UNAVAILABLE` and no writes; (2) sell out the night of 10 April for the listing after booking (for example by reducing units or blocking the other units), then extend to 14 April and expect success; (3) shorten to today (check out 11 April) and expect success with the first night kept.

## Minor

### 🟡 A price override or an occupancy change on a started stay still changes amounts for nights before today, `src/application/reservations/modify-reservation.ts:144`
**Problem**: The spec now says a started stay "keeps its check in, its units and the nights before branch today" (`docs/specs/0005-m8-reservations.md:84`). The planner protects the dates, but `manualNights` requires an amount for every night of the stay and the override replaces all of them (line 540), so staff can reprice nights that are already consumed. An occupancy change on a started stay also recomputes per person and per night service amounts (breakfast) for the past nights, because services are priced over the whole stay with the new guest count.
**Why it matters**: Both may be acceptable as staff corrections, but the documented rule says otherwise, and the history row would show a changed total for nights the guest already used.
**Suggested fix**: Ask the owner. Either refuse an override amount that differs from the stored one for a night before today (and decide what an occupancy change means for past service amounts), or write in the spec that an override and an occupancy change may correct past nights. Pin the answer with a test.

### 🟡 One API doc sentence now contradicts the assignment rule, `docs/api/api-contracts.md:70`
**Problem**: The API-S6 row first says a unit keeps its physical room while that room stays valid, then ends with "Units that move or change dates lose their physical room assignment", which is the old behavior. The same row still marks `services` as "planned M8-T9" where it means T9b. `docs/specs/0005-m8-reservations.md:84` says "Every change bumps `Reservation.changeSeq`", but cancelling a booking that was never entered does not bump it (by design, `reservation-repository.ts:424`).
**Why it matters**: AGENTS.md requires docs that match the code; the API table is what the desk screens in M11 will be built against.
**Suggested fix**: Delete the last sentence of the API-S6 row, change "planned M8-T9" to "M8-T9b", and say in the spec that every stay change, and the cancellation of an entered booking, bumps `changeSeq`.

### 🟡 The started stay test title promises a case it does not run, `tests/integration/reservations/change-reservations.test.ts:1483`
**Problem**: "refuses a moved check in, removed past nights, and added units" runs only two attempts: a moved check in and an added unit. There is no attempt that removes a past night, and no attempt that moves a unit to another listing. The unit test at `tests/unit/domain/reservation-change-plan.test.ts:192` covers both, so the rule is tested, but the integration title overstates it (the same kind of issue as the first pass cancellation title).
**Suggested fix**: Add the two attempts (check out 11 April with today 12 April, and a different listing) or shorten the title.

### 🟡 The inactive unit path of `unitFree` is not tested, `src/infrastructure/db/prisma/repositories/reservations/reservation-repository.ts:388`
**Problem**: Tests drop an assignment for another reservation's assignment and for an active block, but not for a deactivated unit, and not for a cancelled block (which must not drop it). Owner item 3 names all three conditions.
**Suggested fix**: Add one case that deactivates `garden-unit-0` before an extension and expects the unit dropped, and one where the covering block has `cancelledAt` set and the unit is kept.

### 🟡 S15 still hides the cancellation reason code, and the new actions have no S15 assertion, `src/infrastructure/db/prisma/repositories/audit/audit-log.ts:78`
**Problem**: The first pass resolution says reasons stay out of history because they are free text. That holds for the override reason and the note, but `changes.reason` of `reservation.cancelled` is one of four enum codes, and it is dropped because the allowlist keeps only numbers, booleans and null. `couponReleased` and `guestNotified` are also dropped. No test reads S15 for `reservation.stay-modified`, `reservation.cancelled` or `reservation.pms-update-entered`.
**Why it matters**: A Manager reading history cannot see why a booking was cancelled or whether the guest was told, though the data is stored and contains no personal values.
**Suggested fix**: Allow the cancellation `reason` code (validated against `CANCELLATION_REASONS`), `couponReleased` and `guestNotified`, and add one S15 assertion per new action.
