**Reviewed by**: claude-opus-5-5 (author on a different model)
**Scope**: 22 files (17 tracked, 5 untracked), uncommitted (M8-T7b: API-P7 route, Idempotency-Key, `booking-create` bucket, `BRANCH_NOT_BOOKABLE` reason, PAYMOB refusal, honeypot, P6 phone drop, OpenAPI, captured log test). This review is also the mid milestone security review.
**Verdict**: Approve with nits

## Summary

The change exposes `CreateWebsiteReservation` as `POST /api/v1/reservations`. The route is 26 lines. It reads the key from the header, calls one composed use case, and maps the result through a small DTO. That DTO returns `manageUrl` only on a fresh `201` and never on a replay. The security sensitive ordering is right. The honeypot, the PAYMOB refusal and every body check run before the token is read. The read only token pre check runs before any branch disclosure, guest write or lock. Blocked phone, per phone cap and per phone coupon outcomes are reachable only by someone who holds a valid token for that phone. Logs stay on the allow list, and P6 can no longer evaluate a phone at all. No blockers or majors. The remaining items cover the OpenAPI header declaration, rate limit interaction with idempotent retries, the strength of the HTTP C-9 proof, two untested reason paths, and stale security docs.

## Minor

### 🟡 `Idempotency-Key` is not declared as an OpenAPI header parameter, `src/contracts/api/v1/routes.ts:98`

**Problem**: The generated `docs/api/openapi.json` operation for P7 has no `parameters` entry. The header appears only in the `summary` prose. `parameters()` in `openapi.ts:175` emits path and query parameters only.
**Why it matters**: The header is required. A generated client or a contract test driven from the spec will omit it and get `400 MISSING_IDEMPOTENCY_KEY`. The format (8 to 128 printable characters) is also not machine readable. P7 is the first Idem route, and S3, S4 and S62 will need the same.
**Suggested fix**: Let `ApiRoute` declare header parameters (name, required, schema with the pattern) and emit them in `parameters`. Then regenerate the OpenAPI file.

### 🟡 Idempotent retries and early refusals use up the 5 per hour bucket, `src/app/api/v1/reservations/route.ts:13`

**Problem**: `publicRoute` takes the `booking-create` admission before it parses the body or reads the key. Every request counts, including a replay of a booking that already committed, a `400` for a missing key, and a `409 PRICE_CHANGED`. Suppose a guest gets two price changes, makes one successful booking whose response is lost, and then retries. The retry, which is exactly what idempotency is for, can get `429` for up to an hour. Separately, the `anonymous` bucket and the leftmost `X-Forwarded-For` rule (`src/composition/http.ts:23`) were acceptable at 60 per minute. At 5 per hour, a proxy misconfiguration is much more costly. With trust off, the whole site shares 5 bookings an hour. Behind a proxied Cloudflare zone without real IP restoration, guests share edge addresses.
**Why it matters**: A legitimate guest can be told to wait an hour, even though their reservation exists. A deployment mistake becomes a site wide booking outage.
**Suggested fix**: This needs an owner decision, not necessarily code. Options are to accept the behavior and document it, or to admit replays without counting them (look up the key hash before consuming, or consume only on non replay outcomes). In either case, add `booking-create` and its proxy sensitivity to `docs/operations/deployment.md` (line 93 talks only about P5) and to the hosting preflight.

### 🟡 HTTP C-9 does not show that the requests overlapped, `tests/integration/reservations/create-website-reservation-route.test.ts:231`

**Problem**: The 20 round C-9 starts three requests with a plain `Promise.all` on the shared pool. There is no barrier and no `pg_stat_activity` observation. `tests/integration/reservations/AGENTS.md` asks for both. If the three calls run one after another, every retry is answered by the first read only lookup, and the test still passes.
**Why it matters**: The test matrix says "C-9 over HTTP for 20 rounds", and the task row lists C-9 under T7b. The lock path itself is proven at use case level (pg_stat_activity, after the T7 review). As written, the HTTP test proves response shape and final row counts, not concurrency.
**Suggested fix**: Either reuse the use case test's paused audit hook or guest lock holder to observe one request waiting on the guest row, or reword the matrix entry to "parallel replay shape over HTTP; overlap proven in `create-website-reservation.test.ts`".

### 🟡 Two `BRANCH_NOT_BOOKABLE` reason paths are not asserted, `src/application/reservations/create-website-reservation.ts:176`

**Problem**: `CHECK_IN_TIME_MISSING` is never asserted. The use case test at `create-website-reservation.test.ts:230` checks only the code, and the route test covers `ONLINE_BOOKING_DISABLED` and `WHATSAPP_NOT_CONFIGURED`. The second mapping inside the transaction (`:385`, `!bookable && available` becomes `ONLINE_BOOKING_DISABLED`) is also untested. It is the path taken when booking is turned off between the pre check and the locked quote.
**Why it matters**: `context.reason` is new public contract surface, and these branches can regress silently.
**Suggested fix**: Assert `context.reason` in the existing use case test for all three reasons. Add one case where `QuoteBooking` reports `bookable: false` with `available: true` (a stubbed quote in the context is enough).

### 🟡 Security and error docs are not in sync with P7, `docs/security/security-controls.md:157`

**Problem**: `security-controls.md` still says "P7 single-use consumption ... remain their later tasks". It does not describe the `booking-create` bucket, the honeypot, the fact that idempotency replay is fingerprinted with the token hash, or that the manage link is returned once. `docs/api/error-model.md:57` defines `PAYMENT_METHOD_UNAVAILABLE` only as "Paymob not configured for the branch, or the total is zero". It does not mention the M8 refusal of all PAYMOB requests.
**Why it matters**: AGENTS.md requires docs to ship with the change, and this task doubles as the mid milestone security review the security doc should reflect.
**Suggested fix**: Add a short P7 paragraph to `security-controls.md` and widen the error model row to "or online payment is not offered yet (M8)".

### 🟡 The E2E spec's rate limit budget breaks under CI retries, `tests/e2e/reservations-api.spec.ts:9`

**Problem**: The spec spends 2 of 5 hourly admissions per project, and both `desktop-chromium` and `mobile-chromium` run it, so 4 are used. `playwright.config.ts:31` sets `retries: 2` in CI. Any retry, or a rerun within the hour against the same database without a reset, gets `429` and fails for a reason unrelated to the original failure.
**Why it matters**: A flaky retry hides the real failure, and the next CI run on a warm database can fail outright.
**Suggested fix**: Run the spec in one project only, send a distinct trusted client address per project (if the E2E server trusts proxy headers), or have the spec clear the `booking-create` bucket in setup.

## Nits

- ⚪ `src/app/api/v1/_dto/reservations.ts:34`: on a fresh booking, `status: "CONFIRMED"` is hard coded and `totalMinor ?? 0` would silently report a $0 total if the value were ever null. Use `result.status` (narrowed) and treat a null total as a programming error.
- ⚪ `src/app/api/v1/reservations/route.ts:16`: the missing key check runs after body validation, so a request with no key and an invalid body gets `422`, not the documented `400`. `.trim()` is redundant because Fetch already trims header values.
- ⚪ `tests/unit/application/create-website-reservation-input.test.ts:80`: `if (!result.ok) expect(...)` passes vacuously if the parse succeeds. Assert `result.ok === false` first, as the neighboring test does.
- ⚪ `src/contracts/api/v1/reservations.ts:74`: `WebsiteReservationReplayed.status` is `z.string()`. The reservation status enum would document the possible values.
- ⚪ `tests/integration/reservations/create-website-reservation-route.test.ts:320`: the P6 test passes even without `withoutPhone`, because the composition is already phone blind (`phoneAware: false`). Nothing pins the route level drop. That is fine as defense in depth, but say so, or add a unit test that spies on the body `quoteBooking` receives.

## Strengths

- The ordering is correct for security. The honeypot, strict body, PAYMOB refusal and key format are checked before the token. The read only token pre check runs before the branch, setup and listing reads. Unverified callers therefore learn nothing about branch configuration, blocked phones, caps or coupon use, and a made up token writes and locks nothing.
- Replay is safe. The fingerprint includes the token hash and the verified phone, a mismatch never returns the stored row, and the DTO turns any replay (or any null token) into `200` with `manageUrl: null`. The manage token exists only in the `201` body and the outbox payload. It is never stored in plain text or logged.
- The P6 change resolves Decision 9.1 without a contract break. The field stays accepted but is dropped before the use case. The contract description marks it deprecated, and an HTTP test proves P6 answers the same with and without the phone, while P7 still enforces the per phone limit.
- The captured log test (AC-8) uses distinctive values and runs success, replay, price change and strict refusal. It checks every console channel and the refusal bodies for name, email, phone, token, key and manage token. The logger's allow list makes this structurally sound.
- The bucket is namespaced and HMAC keyed (`booking-create`), has its own cleanup entry in `PUBLIC_RATE_LIMITS`, and returns `429` with `Retry-After`.

## Test coverage

The tests cover AC-1 over HTTP (201, CONFIRMED row, 3 outbox rows, token consumed, `no-store`), replay with `manageUrl: null`, key reuse, a missing key that leaves the token unused, strictness against price, status and branch keys, PAYMOB `409`, a honeypot that writes nothing, `401`, `409 PRICE_CHANGED`, `422` for a foreign listing, two `BRANCH_NOT_BOOKABLE` reasons, the 5 per hour limit with `Retry-After`, a 20 round parallel replay, AC-8 over captured console output, and P6 phone blindness alongside per phone coupon enforcement in P7. Unit tests cover the PAYMOB, honeypot and payment enum parsing. Gaps: the `CHECK_IN_TIME_MISSING` reason and the reason mapping inside the transaction are not asserted. A malformed key (`422`) is not tested over HTTP. `PHONE_BLOCKED`, `BOOKING_LIMIT_REACHED` and `INVENTORY_UNAVAILABLE` are not tested over HTTP, though the status table maps them and the use case tests cover them. HTTP C-9 lacks an overlap proof. The E2E spec checks transport rules only, which suits it, but its rate limit budget is fragile.

## Resolution (2026-11-20)

All six minors and five nits were fixed before the task was accepted by the owner.

- `Idempotency-Key` is now an OpenAPI header parameter (`ApiRoute.headers`, with a unit test on the generated document).
- Rate limit retries: the owner accepted the behavior. It is documented in `docs/operations/deployment.md` and `docs/operations/hosting-preflight.md`, to be revisited with Paymob in M9.
- HTTP C-9 now holds the guest row from a second client, waits until three requests are blocked on it in `pg_stat_activity`, then releases.
- All three `context.reason` values and the in-transaction path are asserted; a malformed key is tested over HTTP.
- `security-controls.md` and `error-model.md` are updated.
- The e2e spec runs in the desktop project only.
- Nits: the DTO throws instead of reporting a $0 total, the redundant `.trim()` is gone, the vacuous unit test asserts first, the replay `status` is an enum, and the P6 route level drop is pinned by a unit test (`publicQuoteRequest`).
