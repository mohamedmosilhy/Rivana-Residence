## Summary

The implementation follows the approved layer boundaries, uses scoped resource lookups, and implements the separate base insertion and row lock statements. One period creation timeout defect and three gaps in the required Critical risk evidence need attention before acceptance. ## Major

### 🟠 Period creation has no bounded exclusion lock wait, `src/infrastructure/db/prisma/repositories/reservations/pricing/rate-repository.ts:247`

**Problem**: `createPeriod` inserts without setting the transaction's five second `lock_timeout`. Base writes and period edits set it, but creation can also block while PostgreSQL checks the exclusion constraint against an uncommitted overlapping row. Its `55P03` translation therefore does not protect the ordinary creation path on a server with the default unlimited lock timeout.

**Why it matters**: The approved task and spec 0003 require transient lock failures to return `503 TRY_AGAIN` with `Retry-After: 5`. I reproduced this on the real test database with independent holder, writer, and observer connections. The observer confirmed the writer's `Lock` wait in `pg_stat_activity`. With the holder still open, creation remained pending after 10,532 ms. When the holder committed, it eventually returned a conflict. In a second run, when the holder rolled back after 10.5 seconds, the use case threw `TypeError` after 10,539 ms instead of returning the expected retry result. The shared HTTP wrapper converts that exception to `500 INTERNAL`. The second run left no rate row or audit, but the request contract and bounded wait are broken.

**Suggested fix**: Set the same local lock timeout before the period insert, retain the existing safe `55P03` mapping, and include `TRY_AGAIN` in S32's contract. Add a direct handler test that holds an uncommitted overlapping period until the contender returns `503`, checks the retry header, and verifies no partial resource or audit. This needs no listing or inventory lock.

### 🟠 The claimed races do not prove concurrent transactions, `tests/integration/reservations/rates.test.ts:344`

**Problem**: The base creation race here and the period race at line 384 only start two promises. Neither uses a barrier at the transaction boundary nor observes a database lock wait. Both tests can pass when the operations execute serially. The base test also only checks that the successor's before amount differs from its after amount, rather than matching the committed predecessor and final stored row. The period audit assertion counts events only for surviving row ids, so an orphan audit for the losing attempt would escape that assertion.

**Why it matters**: `tests/integration/reservations/AGENTS.md` and spec 0003 explicitly require coordinated overlap, observable waits, and final resource and audit assertions. Twenty repetitions do not establish those conditions. The particularly important branch where a competing first base insertion rolls back, and the successful writer must still audit a null predecessor, is not exercised. These tests would accept a sequentially correct implementation that fails under a real competing insertion.

**Suggested fix**: Hold one actual transaction before commit, start the contender on another client, and observe its database lock wait before releasing the holder. Repeat the required scenarios 20 times. Assert the complete predecessor to successor audit chain, the final persisted base value, one period winner, and all audits for both attempts. Include a competing base creator that rolls back, with no phantom predecessor or leftover audit.

### 🟠 The authorization sweep omits period mutations, `tests/unit/application/manage-rates.test.ts:156`

**Problem**: The role table calls only `GetRateCalendar.execute` and `ManageRates.setBaseRate`. It never calls `createPeriod`, `updatePeriod`, or `deactivatePeriod`. The PostgreSQL test at `tests/integration/reservations/rates.test.ts:243` and the browser role test also leave period edit and delete authorization untested. The unit table has no unassigned Manager or Receptionist case, and it does not assert that all repository access is absent when capability authorization fails.

**Why it matters**: AC-7, ADR 018, and the approved Critical task require a sweep of every staff use case across roles and branch assignments. A regression that grants `pricing:read` permission to period creation, or removes the scope filter from period mutation lookup, would leave this suite green. These are separate entry points from base rate writing.

**Suggested fix**: Extend the sweep to all five operations with anonymous, Editor, Receptionist, Manager, and Admin principals, plus own branch, foreign branch, and no assignment cases where applicable. Assert refusal before repository access for missing capabilities. Exercise foreign and nonexistent period ids through PATCH and DELETE, requiring the same hidden `404` and unchanged resource and audit state.

### 🟠 Period failure and rollback paths lack required evidence, `tests/integration/reservations/rates.test.ts:255`

**Problem**: The only rate audit failure test covers initial base creation. There is no persisted rollback test for an existing base update, period creation, period update, or deactivation. Active overlap is exercised only on creation, with no conflicting date edit or reactivation test. The audit success checks compare partial snapshots, leaving complete before and after dates, amounts, currency, label, and activity unverified.

**Why it matters**: AC-2 and AC-7 require exclusion refusal and exact transactional history for every rate state change. The shared unit of work tests do not prove that each new use case supplies its mutation and audit through the correct transaction context. A period update that writes outside that context, or a failed reactivation that leaves an audit, could pass the current rate tests.

**Suggested fix**: Add focused real database cases that force audit failure after each distinct mutation and assert that the entire resource and audit state remain unchanged. Exercise overlapping date edits and reactivation, asserting `409` date field errors and no partial state. Check complete audit snapshots and unchanged writes, including repeated base PUT and period deactivation, without duplicate audit events.

## Strengths

* The base protocol uses `INSERT ... ON CONFLICT DO NOTHING RETURNING` followed by a separate `FOR UPDATE OF br` statement. It distinguishes insertion from an existing locked predecessor and does not lock the joined listing row.
* Capability checks precede repository access in the implementation. Id based lookups use allowed branch scopes, and request bodies cannot supply ownership fields.
* Period patches merge after acquiring the period row lock. Mutations and audit appends use the same composed unit of work, and unchanged values return without another write or audit.
* Domain values keep dates structural and amounts positive integer USD cents bounded by PostgreSQL `INTEGER`. Route Handlers stay thin, use the shared CSRF and problem wrappers, and expose explicit DTOs. The reviewed changes introduce no network I/O inside transactions or unsafe SQL.
