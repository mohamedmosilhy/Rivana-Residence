# Review, m8-reservations, 2026-11-20

**Reviewed by**: claude-opus-5-5 (author on claude-sonnet-5-5)
**Scope**: 34 files, uncommitted (M8-T7 `CreateWebsiteReservation`)
**Verdict**: Changes requested

## Summary

The change adds the pay at hotel website booking use case. One transaction checks idempotency, locks the guest, consumes the verification token, applies the per phone cap, locks the listings and then the coupon, prices the booking through `QuoteBooking` on that transaction's readers, and inserts the reservation, redemption, guest update, audit and outbox rows. It also adds an optional `prepare` step to `InventoryGuard`, the slim `PublicListingReader`, and a persisted redemption reader that stays phone blind on P6. The production code is careful and the lock order matches spec 0005 Decision 1. The main problem is in the tests: the concurrency proofs are weaker than the test matrix says. C-11 does not exercise the coupon lock at all. Nothing shows that C-9 reaches the second idempotency lookup under the guest lock. C-2 and C-3, as the integrity document defines them, are missing. There are also some smaller correctness gaps: replay ordering, a same key race, and lock ids taken outside the transaction.

## Major

### 🟠 C-11 does not prove the coupon lock, and the per phone coupon limit is untested, `tests/integration/reservations/create-website-reservation.test.ts:542`

**Problem**: All six parallel bookings use the same listing (`garden`), so `PrismaInventoryLock` already runs them one at a time before any of them reaches `lockByCode`. If the coupon `FOR UPDATE` were deleted from `PrismaCouponRedemptionStore.lockByCode`, this test would still pass. Spec AC-3 and C-11 also cover per phone coupon limits under parallel use (`maxRedemptionsPerPhone`). No booking test covers that limit, either one after another or in parallel. The only per phone check is a direct call to the reader (`:438`).
**Why it matters**: The coupon row lock is the only thing that stops two bookings of different listings from both taking the last redemption. The test that is meant to prove it cannot fail, so a later refactor could remove the lock without any test noticing. The reviewer was asked to check exactly this.
**Suggested fix**: Seed two or more listings, or two branches with an all branch coupon, so the parallel bookings hold different listing locks and only the coupon lock orders them. Better still, also observe one transaction waiting on the coupon row in `pg_stat_activity` (`waitForDatabaseLock`). Add a booking level per phone limit test: the same phone with `maxRedemptionsPerPhone: 1` books twice and the second gets `COUPON_INVALID`. Add a parallel version on different listings.

### 🟠 Concurrency tests do not show the transactions overlapped, the C-9 path under the guest lock is not proven, and C-2 and C-3 are missing, `tests/integration/reservations/create-website-reservation.test.ts:486`

**Problem**: C-1, C-9 and C-11 start work with a plain `Promise.all`. They use no barrier and make no `pg_stat_activity` observation. `tests/integration/reservations/AGENTS.md` says "sleeps are not evidence", and the same holds for hoping the calls overlap. For C-9 this matters most. If the four calls happen to run one after another, every retry is answered by the first lookup (`create-website-reservation.ts:258`), and the second lookup under the guest lock (`:277`, Decision 2a) is never run. The test passes either way, so it does not prove the behavior the spec added C-9 for. Also, the test labeled C-2 (`:164`) is a single, sequential two unit booking. The integrity document defines C-2 as a parallel partial overlap and C-3 as parallel adjacent stays that must both succeed. The plan and the task row list C-1 to C-3, and neither C-2 nor C-3 exists.
**Why it matters**: The test matrix entry says "C-1, C-9 and C-11 over 20 rounds", which a reader will take as proof of the locking design. As written, the second lookup and the guest lock serialization could break without any failing test.
**Suggested fix**: For C-9, hold the guest row lock (or run a first booking up to a barrier), start the retry, confirm in `pg_stat_activity` that it waits on the guest row, then let the first booking commit. Assert that the retry replays. A small unit test with a fake repository, where the first lookup misses and the second hits, would also pin the branch. Add C-2 (stays `[10,13)` and `[12,15)` in parallel on one unit, exactly one succeeds) and C-3 (`[10,12)` and `[12,14)`, both succeed) as the integrity table defines them. Add a parallel same phone at the cap race on different listings, so that only the guest lock orders them (spec edge case table).

## Minor

### 🟡 Replay runs after the mutable branch and listing checks, `src/application/reservations/create-website-reservation.ts:131`

**Problem**: The branch active, bookable and WhatsApp setup checks and the published listing lookup all run before the guard. The idempotency lookup only runs inside `prepare`. Suppose a guest's booking committed but the response was lost. If the branch then turns off online booking, WhatsApp setup becomes empty, or the listing is unpublished, the retry gets `BRANCH_NOT_BOOKABLE` or `VALIDATION` instead of its reference.
**Why it matters**: The guest is told the booking failed while a `CONFIRMED` reservation exists. Covering a lost response is the purpose of idempotency, and spec Decision 1 puts the lookup first.
**Suggested fix**: Do a first idempotency lookup (with the fingerprint compare) before the branch and listing checks, or move those checks after the replay in `prepare`. Keep the lookup under the guest lock as it is.

### 🟡 A same key race between two different phones returns a generic `CONFLICT`, `src/infrastructure/db/prisma/repositories/reservations/reservation-repository.ts:310`

**Problem**: Two requests with the same key but different phones take different guest locks, so neither second lookup sees the other. The loser fails on the idempotency unique index and gets `CONFLICT` ("A reservation with that unique value already exists"). Spec Decision 1 step 1 expects `IDEMPOTENCY_KEY_REUSED`, the winner after commit, or `409 IDEMPOTENCY_IN_PROGRESS`.
**Why it matters**: This is an undocumented error code on a public path. T7b will have to map it and has no way to tell it apart from other unique failures.
**Suggested fix**: In the use case, when insert returns `CONFLICT`, translate it to `IDEMPOTENCY_KEY_REUSED`. The fingerprints must differ, because the phone is part of the fingerprint. Or make the repository report which constraint failed. Add a parallel test.

### 🟡 Locked listing ids are computed outside the transaction, `src/application/reservations/create-website-reservation.ts:145`

**Problem**: `roomIds` comes from a slug lookup on the pool client before the transaction. Inside the transaction, `QuoteBooking` resolves the slugs again and checks availability for whatever ids it finds. The insert then uses the outer `roomIds[index]`. Nothing checks that the two sets match. If a slug moves from one listing to another between the two reads (slugs are editable in the CMS), the quote checks availability and prices on a listing whose lock is not held, and the line is stored against a different listing than the one priced.
**Why it matters**: It is rare, but in that case the "load under the lock" rule (AGENTS.md, ADR 016) no longer holds.
**Suggested fix**: After the lock, re-read the listings inside the transaction and refuse (or retry) when the slug to id map differs from the locked ids. Alternatively, expose the resolved room id on `QuoteLineView` and compare.

### 🟡 `validateReservationCreation` gets made up listing facts, `src/application/reservations/create-website-reservation.ts:491`

**Problem**: `listing` is built as `{ id: line.roomTypeId, branchId, maxAdults: line.occupancy.adults, maxChildren: line.occupancy.children }`. The occupancy fit and branch ownership checks in `validateReservationStructure` therefore always pass. The real limits are already in the `published` map.
**Why it matters**: The domain safety net looks active but checks nothing. `QuoteBooking` does check occupancy today. If that check moves, nothing catches the change.
**Suggested fix**: Pass the real `PublicListing` values (id, branchId, maxAdults, maxChildren) for each line.

### 🟡 Unauthenticated requests write and lock a guest row before the token is checked, `src/application/reservations/create-website-reservation.ts:265`

**Problem**: Any request with any phone and a made up token inserts a `Guest` row (`ON CONFLICT DO NOTHING`), takes `FOR UPDATE` on it, and only then rolls back. Repeated calls for a victim's phone keep that guest row busy and can push the victim's real booking to `TRY_AGAIN` after five seconds.
**Why it matters**: It is cheap to abuse, and the HTTP rate limit only arrives in T7b.
**Suggested fix**: Before opening the write transaction, run a cheap read only pre check: `findByTokenHash` must give a `BOOKING` row for this phone that is unexpired and unconsumed. Keep the full check under the locks as now.

### 🟡 The per phone cap query scans by an unindexed column, `src/infrastructure/db/prisma/repositories/reservations/reservation-repository.ts:166`

**Problem**: `listPhoneBookings` filters on `guestPhone`, and `Reservation` has no index on it. The query runs on every booking while the guest row lock is held.
**Why it matters**: As reservations grow, it becomes a sequential scan inside a lock window. That lengthens lock hold time and makes `TRY_AGAIN` more likely.
**Suggested fix**: Filter by `guestId` (indexed with `checkIn`; website reservations always carry the locked guest), or add an index on `guestPhone`.

### 🟡 Planned test cases missing, `tests/integration/reservations/create-website-reservation.test.ts:364`

**Problem**: The approved plan lists services, an inactive branch, an unpublished listing, a cap across branches, and a P6 phone blind regression. The cap test is titled "across branches" but books three times in one branch, so neither counting across branches nor the per branch time zone is exercised. No test books with services, an inactive branch (`NOT_FOUND`), an unpublished listing, or a listing of another branch (AGENTS.md asks for branch isolation). The P6 regression only calls the reader. No test goes through `quoteBooking()` to show that an existing redemption for a phone leaves P6 unchanged. `tests/integration/reservations/quotes.test.ts:572` still says "M7 counts redemptions as zero", which is now stale.
**Why it matters**: The task tier is critical, and the test matrix entry claims these cases.
**Suggested fix**: Add a second branch with a different time zone to the cap test. Add the missing cases. Add a P6 test that seeds a redemption for a phone and asserts P6 still answers `200` for that phone. Update the stale comment.

### 🟡 The test wiring copies production composition, `tests/integration/reservations/support/website-booking.ts:46`

**Problem**: The helper says "Production wiring (src/composition/reservations.ts)", but it is a hand copy. It uses `QueueReservationMessages` directly where production uses `reservationMessageWriter(transaction)`. Neither `createWebsiteReservation()` nor the P6 `quoteBooking()` change is run by any test.
**Why it matters**: The two can drift apart. For example, production could wire `phoneAware: false` into the booking, or the wrong message writer, and every test would stay green.
**Suggested fix**: Have the composition take its clock and client as optional parameters and build through it in the test. Or add a small test that compares the two wirings.

### 🟡 `application/shared/result.ts` now depends on a feature module, `src/application/shared/result.ts:1`

**Problem**: `result.ts` imports `QuoteView` from `@/application/quotes`, while `quotes` imports `result`. The cycle is type only, so lint passes, but `shared` should be the common ground and should not depend on a module (dependency-rules, ports layout).
**Why it matters**: It sets a precedent for `shared` to depend on features, and future value imports would make the cycle real.
**Suggested fix**: Make `PriceChangedError` generic over its context, or define the error type in `quotes` and widen `ApplicationError` there. Or move a minimal quote view type into `shared`.

## Nits

- ⚪ `src/application/inventory/inventory-guard.ts:101`: `undefined as Prepared` lets a caller declare a `Prepared` type without `prepare` and receive `undefined` in `load`. Overloads, or making `prepare` required when `Prepared` is not `undefined`, would close the gap.
- ⚪ `docs/database/integrity-and-concurrency.md:105`: "website bookings are the only writers that take the guest row first" is not accurate. P10 confirmation and guest blocking also lock the guest first, and Decision 7 makes staff and external creation do the same in T8.
- ⚪ `src/infrastructure/db/prisma/repositories/reservations/commercial/coupon-redemption-repository.ts:28`: counting by code with `mode: "insensitive"` (ILIKE) does not use `Coupon_code_upper_key`. The booking already holds the coupon id, so counting by `couponId` would be simpler and exact.
- ⚪ `src/infrastructure/db/prisma/repositories/reservations/guests/phone-verification-repository.ts:43`: `consume` could add `consumedAt: null` to its `where` as defense in depth, even though the row lock already protects it.
- ⚪ `src/application/reservations/create-website-reservation.ts:140`: `BRANCH_NOT_BOOKABLE` has no `context.reason`, which the error model documents. T7b can add it, but the use case is where the reason is known.
- ⚪ `src/application/reservations/create-website-reservation-input.ts:177`: a bare service kind and the `{ kind }` object form give different fingerprints, so a retry that changes only the shape gets `IDEMPOTENCY_KEY_REUSED`. Canonicalizing to the object form would avoid that.

## Strengths

- The lock order is correct and documented: guest row, then verification (the T5 order), then listings through `InventoryGuard`, then the coupon row, then the reservation insert. There is no I/O inside the transaction, and outbox rows are written in the same transaction.
- Token consumption is inside the transaction and is given back on any failure. The tests check that the consumed count stays unchanged after `PRICE_CHANGED`, after the cap refusal, and after a thrown audit error, and that the token works again afterwards.
- The idempotency fingerprint includes the verified phone and the token hash, and a fingerprint mismatch never returns the stored row. A test shows that another client using the same key and body without the token gets `IDEMPOTENCY_KEY_REUSED`.
- `QuoteBooking` is built on the transaction's readers, so prices, coupon counts and availability are read after the locks, and pricing stays in one place.
- P6 gets a real redemption total but stays phone blind, so it cannot reveal which phone used a coupon.
- The audit payload carries identifiers and money only, and a test checks it contains no name, email, phone or token.
- C-1 runs on ten independent clients over twenty rounds and checks the final reservation, audit and outbox counts.

## Test coverage

The single file run passes (23 tests, about 13 s). The happy path, price change, unavailable inventory, validation refusals, token rules, blocked phone, replay, key reuse, order insensitivity, sequential cap, coupon redemption and exhaustion, and rollback on a thrown error are covered well. The `prepare` hook has three good unit cases. The weak points are the concurrency proofs. C-11 is ordered by the listing lock, so it does not test the coupon lock. Nothing shows the C-9 calls overlapped. C-2 and C-3 as the integrity document defines them, the parallel same phone cap race, and the per phone coupon limit are absent. The plan's services, inactive branch, unpublished listing, other branch listing, cap across branches, and P6 phone blind end to end cases are missing. The composition functions `createWebsiteReservation()` and the changed `quoteBooking()` are not run by any test.

## Author response (Sonnet 5.5, same day)

You can read this as the follow up to the findings above. Every major and minor finding was fixed or answered, and the gates were rerun.

**Major**
- C-11 and the coupon lock: fixed. A blocker holds the coupon row with `FOR NO KEY UPDATE` (it conflicts with the booking's `FOR UPDATE` but not with the redemption's foreign key check), and a paused booking on one listing makes a booking on another listing wait for the coupon row. Both tests fail when the coupon `FOR UPDATE` is removed (checked by hand) and pass with it. A booking level per phone coupon limit test was added, and the parallel race now uses two listings.
- Overlap proof, C-9, C-2, C-3: fixed. C-1, C-2, C-9 and the coupon test hold the first transaction open with a paused audit hook and wait until `pg_stat_activity` shows the others blocked on a lock. C-9 now runs the second idempotency lookup (removing it fails the test). C-2 and C-3 follow the integrity document. A parallel same phone cap race and a same key from two phones race were added.

**Minor**
- Replay order: a read only replay lookup now runs first, before the branch and listing checks, so a lost response retry still gets its reference. Tested.
- Same key from two phones: an insert `CONFLICT` becomes `IDEMPOTENCY_KEY_REUSED`. Tested in parallel.
- Locked ids versus the quote: `QuoteLineView` now carries `roomTypeId` (internal, not in the P6 DTO). The booking refuses with `TRY_AGAIN` if the priced listing differs from the locked one.
- Made up listing facts: the real published limits are passed to `validateReservationCreation`.
- Guest row before the token check: a read only pre check on the pool now refuses an unknown, consumed, expired or wrong phone token before any write. Tested (no guest row is created).
- Unindexed cap query: it now filters through the unique guest phone, so the indexed guest id is used.
- Missing cases: services (with details kept), inactive branch, unpublished listing, other branch listing, cap across branches (second branch in another time zone) and the P6 phone blind regression through the real route were added. The stale comment in `quotes.test.ts` was fixed. The P6 test fails when the public wiring is made phone aware.
- Test wiring copy: `createWebsiteReservation` accepts an optional client and clock, and a composition test runs the real wiring (messages, WhatsApp setup, phone aware coupon).
- `shared/result.ts` import: `PriceChangedError` now uses a small structural quote type, so `shared` no longer imports `quotes`.

**Nits**
- Fixed: the integrity document wording about the guest lock, `consume` only updates unconsumed rows, and the bare service kind and `{ kind }` now give the same fingerprint.
- Not changed, on purpose: `undefined as Prepared` in the guard (only this task uses `prepare`; revisit if a second caller appears), counting redemptions by coupon id (the quote reader interface is by code, kept for P6), and `context.reason` on `BRANCH_NOT_BOOKABLE` (T7b maps the HTTP shape).

**Reruns**: `npm run check` (format, lint, typecheck, build, 96 unit files and 2,115 tests) and the full PostgreSQL integration suite (47 files and 732 tests) pass. This is the author's own rerun, not a second review pass.
