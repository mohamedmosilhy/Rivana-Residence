## Minor
### 🟡 A busy settings row silently drops the audit and stored result of a message that was already sent, `src/application/notifications/send-whatsapp-test-message.ts:94`
**Problem**: The Result of `unitOfWork.run` is discarded. If `recordTest` returns TRY_AGAIN (5s lock timeout, whatsapp-settings-repository.ts:84,95), the whole transaction rolls back (unit-of-work.ts:36 throws ResultAbort), so neither `lastTest*` nor the `whatsapp-test.sent` audit event is written, and nothing is logged.
**Why it matters**: Rule "every audited write appends its audit event in the same transaction" is satisfied, but an externally visible Admin action (a real WhatsApp message) can leave no audit trail. Scenario: Admin A saves settings and holds the row lock beyond 5s while Admin B's test completes; B's message is delivered, B gets 200, no audit row exists.
**Suggested fix**: Retry the record step once or twice, or write the audit event in its own transaction independent of the settings row lock (the audit does not need that lock), and log a content-free warning if recording still fails.

### 🟡 Sanitizer misses phone numbers formatted with parentheses or dots, `src/infrastructure/whatsapp/sanitize.ts:27-29`
**Problem**: The pattern `\+?\d[\d\s-]*\d` stops at `(`, `)`, and `.`. `(202) 555-0199` yields runs `202` (3 digits, kept) and `555-0199` (masked); `202.555.0199` has three runs under 6 digits each and nothing is masked.
**Why it matters**: Meta error text can echo a recipient number. Today the number is the Admin's own test target, but the same transport will carry guest numbers and codes in later tasks (verification, outbox), and the text is stored in `lastTestError` and returned in problem detail.
**Suggested fix**: Strip `()`, `.`, and `/` separators when measuring digit runs (for example allow them in the character class), or count total digits in a window after removing all non-digits between digit groups. Add a test for these formats.

### 🟡 WHATSAPP_NOT_CONFIGURED is a 503, so clients get `Retry-After: 5`, `src/app/api/v1/_http/problem.ts:46,99-103`
**Problem**: `problem()` defaults a 503 to `Retry-After: 5`. This code means a setup gap that only an Admin can fix, not a transient outage.
**Why it matters**: A generic client or the future M8-T4b screen that honours Retry-After may auto-retry a request that cannot succeed. The 5 per 10 minutes limiter bounds the harm.
**Suggested fix**: Use 409 or 422 for setup gaps, or let `problem()` skip Retry-After for this code. Check the choice against spec Decision 8 before changing.

### 🟡 Stored template with an unknown value makes every read throw, `src/infrastructure/db/prisma/repositories/reservations/notifications/whatsapp-template-repository.ts:40-47,57`
**Problem**: `record()` throws on an unknown purpose, language, category, or variable key. `list()` maps every row, and `WhatsAppSetupReader.read()` calls `list()`.
**Why it matters**: If a variable key is later removed from the allowlist (or a row is edited by hand), the settings GET, the branch online-booking check, and the sender all 500 until the data is fixed. The sender path (later outbox) would stall all WhatsApp, not one template.
**Suggested fix**: Skip or flag unreadable rows in `list()` and `findActive()` rather than throwing, or at least keep the failure scoped to the one template.

### 🟡 Branch update reports the online-booking refusal even when the branch already has it on, `src/application/branches/manage-branches.ts:158-170`
**Problem**: In the parse-failure branch, `sendsOnlineBookingOn(input)` triggers `onlineBookingIssues` without comparing against `current.onlineBookingEnabled` (the success path at line 199 does compare).
**Why it matters**: Harmless today (nothing can be on before M10), but after M10 an unrelated validation error on a branch already online would add a misleading "not ready" field error.
**Suggested fix**: Only add the issue when the stored value is not already true, matching the success path.

### 🟡 Template category is not cross-checked for MARKETING purpose, `src/domain/notifications/whatsapp-template.ts:182-231`
**Problem**: Rules force VERIFICATION_CODE to AUTHENTICATION and forbid AUTHENTICATION elsewhere, but a MARKETING purpose may be saved as UTILITY (and a UTILITY purpose as MARKETING).
**Why it matters**: A mislabelled category does not break sending but can misrepresent consent handling for M13 marketing sends and is hard to spot later.
**Suggested fix**: Decide the intended mapping (for example MARKETING purpose requires MARKETING category) and validate it, or record that it is deliberately free.
