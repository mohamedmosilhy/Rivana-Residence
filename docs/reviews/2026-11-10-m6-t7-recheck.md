## Major

### 🟠 TRY_AGAIN was added to S22's contract instead of S32's, `src/contracts/api/v1/routes.ts:206`

**Problem**: The only change to an existing route in `routes.ts` adds `"TRY_AGAIN"` to `createPhysicalRoom` (API-S22, an M6-T5 endpoint already accepted). `createRatePeriod` (API-S32, `routes.ts:349` to `:367`) still lists `UNAUTHENTICATED, FORBIDDEN, CROSS_SITE_REQUEST, NOT_FOUND, CONFLICT, VALIDATION` with no `TRY_AGAIN`. The regenerated `docs/api/openapi.json` matches: the S22 default response now says `TRY_AGAIN` and the S32 one does not. S22 cannot return `TRY_AGAIN`: `ManagePhysicalRooms.create` calls `PrismaPhysicalRoomRepository.create`, which sets no lock timeout, and its `translate` rethrows `55P03` as an unknown error.

**Why it matters**: The first review's fix asked for `TRY_AGAIN` in S32's contract, and spec 0003 asks for OpenAPI freshness for every new route. The published contract now documents a 503 that S22 never sends and leaves out the 503 that S32 now does send. The change also edits an accepted task's contract outside M6-T7's scope. The OpenAPI freshness test cannot catch this, because it only compares the generated document with the route table, and both are wrong in the same way.

**Suggested fix**: Move `"TRY_AGAIN"` from the `createPhysicalRoom` errors list to the `createRatePeriod` errors list and regenerate `docs/api/openapi.json`. If S22 really should document a bounded wait, that is a separate T5 change with its own lock timeout and test.

## Minor

### 🟡 Deadlock 40P01 is reported as an overlap conflict with no test, `src/infrastructure/db/prisma/repositories/reservations/pricing/rate-repository.ts:95`

**Problem**: `translatePeriod` maps `40P01` to `409 CONFLICT` with overlap field errors. Spec 0003 line 184 names only `23P01` for the rate exclusion. The comment explains why (two concurrent GiST exclusion checks can deadlock), and that reasoning holds for two overlapping inserts or edits, but nothing in the suite produces a `40P01`, so the branch is untested and the mapping is not checked against the constraint or statement that failed.

**Why it matters**: If a deadlock ever comes from a different lock cycle, a staff user would see "already has an active rate on those dates" for a request that may not overlap anything, when a retry would have worked. This is unlikely today, which is why it is Minor.

**Suggested fix**: Either record the 40P01 decision in the spec next to the 23P01 rule, or map it to `TRY_AGAIN`. Add a focused test or a unit test with a synthetic `40P01` error so the branch is pinned.

### 🟡 Two race shapes are still not exercised, `tests/integration/reservations/rates.test.ts:717`

**Problem**: The period race covers only the case where the holder commits, so the contender must conflict. There is no case where the holder of an overlapping period rolls back and the contender must then succeed with exactly one audit. The base races cover the first insert (commit and rollback) but not two updates of an existing base row, where the contender waits on `FOR UPDATE OF br` and must audit the holder's committed amount as its predecessor.

**Why it matters**: Both paths rely on PostgreSQL semantics the code handles correctly today (re-check after the holder ends, fresh row after `FOR UPDATE` under READ COMMITTED). Without a test, a later refactor, for example reading the base row before taking the lock, would keep the suite green while producing a stale `before` in the audit.

**Suggested fix**: Add a 20 iteration period race where the holder throws after its audit append, asserting the contender succeeds and only its row and audit remain. Add a 20 iteration base race on a pre-existing row with two different amounts, asserting the successor's `before` equals the holder's `after` and the final stored amount.

## Strengths

- The S32 timeout test is discriminating: without the lock timeout the contender would hit the 10 second interactive transaction timeout and return 500, so the test would fail, and it proves no partial row or audit.
- The race harness is now honest evidence: the holder stops inside its transaction after writing its audit, the contender's pid is captured inside its own transaction, and the wait is observed in `pg_stat_activity` before release, repeated 20 times with final resource and audit assertions.
- The base write protocol (`INSERT ... ON CONFLICT DO NOTHING RETURNING`, then `FOR UPDATE OF br`) correctly tells a fresh insert from a locked predecessor, including when a competing first insert rolls back, and it never locks the listing row (proven against the real `FOR NO KEY UPDATE` inventory lock mode).
- Use cases authorize before any repository access, re-check branch scope inside the transaction, and keep handlers thin.
