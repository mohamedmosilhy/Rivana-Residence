# Review, m6-inventory-and-availability (M6-T6 blocks), 2026-11-09

**Reviewed by**: claude-opus-5-5 (fresh reviewer; author on a different session/model)
**Scope**: 29 files, uncommitted (20 tracked modified including the generated `docs/api/openapi.json`, 9 untracked new)
**Verdict**: Changes requested

## Summary
Adds inventory blocks (API S24 to S27): a `PrismaBlockRepository`, the `ManageBlocks` use case, domain parsers, composition, strict Zod contracts, a DTO mapper, thin Route Handlers, OpenAPI, typed audit events, and unit, integration, concurrency, and Chromium tests. The critical paths are correct by inspection. Create and every end date change go through `InventoryGuard`, so the listing lock comes before any unit, block, or sold read. Extension then locks the block row and rechecks cancellation, so the order is always listing then row. Note edits and cancellation take only the block row and never ask for a listing lock, so no deadlock cycle can form with the guarded paths or with the T5 unit paths. Authorization runs before any data access, id paths use a scope limited lookup for a hidden 404, audit never stores note bodies and rolls back with the write, and all raw SQL is tagged. The one major finding is that the new block row `55P03` to `TRY_AGAIN` mapping (and its `503` HTTP shape) has no test at all, while the integration test named for it only exercises PostgreSQL directly and the test matrix claims the coverage. The minors are about a query that returns 400 where the spec asks for 422, an inactive unit policy that differs between create and extension, inconsistent overlap field errors, and weak assertions in two concurrency cases.

## Major

### 🟠 The block row lock timeout mapping is untested, and the test named for it tests PostgreSQL instead, `tests/integration/reservations/blocks.test.ts:224`
**Problem**: `PrismaBlockRepository.lockVisible` (`src/infrastructure/db/prisma/repositories/reservations/inventory/block-repository.ts:101`) is new code with a `55P03` branch that returns `TRY_AGAIN`. The integration case "reports TRY_AGAIN when the block row stays locked past the lock timeout" never calls the repository, the use case, or a route. It holds the row with raw SQL, waits on it with raw SQL and a 200 ms timeout, catches every error as `"timeout"`, and asserts that string. It would still pass if `lockVisible` lost its try and catch, or mapped the wrong code, or forgot `SET LOCAL lock_timeout`. No block route test asserts `503` with `Retry-After: 5`. The unit test at `tests/unit/application/manage-blocks.test.ts:456` uses a fake that returns `TRY_AGAIN`, so it proves the use case passes the result through, not the adapter. `docs/testing/test-matrix.md:18` lists "row lock timeout" and T-HTTP for S24 to S27 as covered.
**Why it matters**: This is a Critical tier task, the brief names `55P03` to `503` as a review focus, and the spec's test plan requires T-HTTP for "lock timeout `503 TRY_AGAIN` with exactly `Retry-After: 5`" on all API criteria. The block row lock is the only lock on the cancel and note paths, so it is the path most likely to time out in practice once M8 writers exist. The docs currently overstate what is proven.
**Suggested fix**: Replace the case with one that holds `FOR UPDATE` on the block row from a second client, then calls `del(id)` (and `patch(id, { note })`, and one extension so the listing then row path is covered) through the real Route Handlers, asserting `503`, `Retry-After: 5`, the safe problem body, and no write or audit. The T5 suite has the pattern for the unit row. If running the real 5 s timeout is too slow, at least call `new PrismaBlockRepository(tx).lockVisible` inside the waiting transaction and assert the returned `TRY_AGAIN` result. Then make the matrix row match what is proven.

## Minor

### 🟡 An impossible calendar date in the S24 query returns 400, not 422, `src/contracts/api/v1/inventory.ts:96`
**Problem**: `BlockQuery` uses the shared `isoDate`, which has a calendar refine. The wrapper validates the query with `INVALID_QUERY`, so `from=2031-02-30` becomes `400` before `parseStaffReadWindow` can return `422`. Only the 62 night limit and the order check reach the use case.
**Why it matters**: Spec 0003 (API surface) says the wrapper's 400 is for malformed structure and unknown keys only, and that date semantics must run in the use case so they return 422; "Do not pass a query schema that turns an impossible date ... into 400. Contract and direct handler tests must prove the distinction." S24 lists `422` for an invalid range. T8 will build S20 on the same pattern, so it is cheaper to settle now.
**Suggested fix**: Give the query schema a regex only date (no calendar refine) and leave the calendar check to the domain parser, then add a handler test for `from=2031-02-30` returning 422 next to the existing missing key 400 case at `tests/integration/reservations/blocks.test.ts:439`. If the owner prefers 400 here, record that as a decision in the spec.

### 🟡 Create refuses an inactive unit, but extension on an inactive unit is allowed silently, `src/application/inventory/manage-blocks.ts:306`
**Problem**: `create` returns `409` for an inactive unit after the lock (line 154). `changingEnd` reloads the unit after the lock but never checks `unit.active`; the projection treats an inactive unit as contributing nothing, so the extension passes. Neither behavior for extension is tested or documented.
**Why it matters**: Inventory stays correct either way, since an inactive unit has no capacity to lose. But the spec says "Recheck activity and cancellation after locks", and two write paths on the same resource now follow different rules. A reviewer or M8 author could read the missing check as an oversight and "fix" it in a way that breaks shortening on inactive units.
**Suggested fix**: Decide the rule (extension on an inactive unit allowed, or only shortening allowed, or refused like create), implement it in `changingEnd`, and add one unit test and a line in `docs/api/api-contracts.md` for S26.

### 🟡 Overlap field errors differ by path and can point at a field the request cannot send, `src/application/inventory/inventory-guard.ts:34`
**Problem**: Under the listing lock, overlaps are caught by the domain check, which returns only a `startDate` field error. The exclusion constraint path in `block-repository.ts:61` returns `startDate` and `endDate`. For S26 the client sent only `endDate`, yet the error names `startDate`. The inactive unit refusal returns a `physicalRoomId` field error, while `docs/api/api-contracts.md:90` says "`startDate`/`endDate` field errors on overlap or an inactive unit".
**Why it matters**: Staff screens later map field errors to inputs. An S26 overlap would highlight a start date field that is read only, and the documented shape does not match either code path.
**Suggested fix**: Return the same fields from both overlap paths, and for an extension put the error on `endDate`. Correct the S25 note in `api-contracts.md` to say the inactive unit error is on `physicalRoomId`.

### 🟡 A lock timeout raised after the listing lock but outside `lockVisible` becomes a 500, `src/infrastructure/db/prisma/repositories/reservations/inventory/block-repository.ts:61`
**Problem**: The guard has already set `lock_timeout = '5s'` for the transaction. Inserting a block takes `FOR KEY SHARE` on the parent `PhysicalRoom` row through the foreign key, and that conflicts with the `FOR UPDATE` held by a T5 plain unit edit. If that wait passes 5 s, `create` raises `55P03`, `translate` rethrows it, and the caller sees a redacted 500 instead of `503 TRY_AGAIN`. The same applies to `update` and `cancel`.
**Why it matters**: Unlikely today because unit edits are short, but it breaks the spec rule that lock timeouts map to 503, and it is the same class of gap the T5 review raised for the unit row.
**Suggested fix**: Map `55P03` to `TRY_AGAIN` in `translate` (and wrap `cancel`), ideally through one shared helper with `PrismaInventoryLock`.

### 🟡 Two concurrency cases assert less than their names claim, `tests/integration/reservations/concurrency.test.ts:521`
**Problem**: In "extension against cancellation", only the refused branch is checked. When the extension succeeds, the test does not assert that the committed row has the new end date and exactly one `inventory-block.updated` audit, so a lost extension would pass. In "block races a deactivation" (line 534), `capacity >= 0` and `capacity - sold >= 0` are always true with sold zero, since capacity is a count. The spec admits this limit, but the case proves only that both commit.
**Why it matters**: These are the AC 5 race proofs for a Critical task. Stronger final state assertions cost nothing.
**Suggested fix**: In the success branch, assert `endDate` is `2031-07-15` and one update audit plus one cancel audit. In the deactivation race, assert the exact final state (u1 has one active block on those nights, u2 is inactive, capacity on 2031-07-04 is 0, and two audit events).

### 🟡 The test wiring duplicates the production composition again, `tests/integration/reservations/support/blocks.ts:27`
**Problem**: `blockUseCase` rebuilds the graph in `src/composition/inventory.ts:47` by hand, as the T5 helper does. The T5 review raised this; T6 repeats it.
**Why it matters**: The concurrency proofs are evidence for production only while the two graphs match. M8 will swap the consumption adapter.
**Suggested fix**: Let `manageBlocks` (and `managePhysicalRooms`) accept a client and test overrides, and have the helpers call them.

Use `rangeWithEnd` or drop it.
- ⚪ `src/infrastructure/db/prisma/repositories/reservations/inventory/block-repository.ts:62`: `translate` maps any `23P01`, not specifically `InventoryBlock_no_overlap`. It is the only exclusion on that table today, but the spec asks for constraint identity.
- ⚪ `src/application/inventory/manage-blocks.ts:285`: `patch.endDate as LocalDate` and `state.current!` (lines 325, 331) could go away by passing the narrowed end date in and making `current` required in an extension specific state type.
- ⚪ `src/domain/inventory/block.ts:18`: a second `isoDate` with a different calendar check from `src/contracts/api/v1/primitives.ts:6`; harmless, but two definitions of a valid date can drift.
- ⚪ `src/app/api/v1/staff/blocks/[id]/route.ts:11`: PATCH and DELETE never call `setBranch`, so their log lines carry no branch id (same as T5's S23).

## Strengths
- The lock order is clean and matches the spec: guarded paths lock the listing then the block row, release and note paths lock only the row, and the create path reads the unit after the listing lock and refuses an inactive one. Cancellation is rechecked under the row lock, so extension against cancellation cannot extend a cancelled block.
- Sparse validation is right for both create and extension: sold nights are filtered to the range, capacity is read only for those nights, and `replaceBlockId` makes the projection count only the added nights of an extension.
- Authorization is first on every path, with `authorizeBranch` for branch paths and `branchScope` lookups for id paths, so hidden blocks return 404; the body cannot pick the branch.
- Audit events carry before and after end dates and only a `noteChanged` flag, and a no op patch or a repeated cancel writes nothing. The rollback on audit failure is proven against real PostgreSQL.
- The listing lock wait test observes the waiter's backend in `pg_stat_activity` and checks nothing was written before release, for both create and extension, 20 times each.

## Test coverage
Unit tests cover the role sweep with zero port calls on refusal, the 62 night window, validation, sold overflow naming the night, sparse consumption, assignments, overlap and adjacency, extension replacing the old range, cancelled blocks, idempotent cancel, audit redaction, and lock order. Integration covers the repository, the `23P01` mapping, all four routes with Location, no store, CSRF, roles, hidden 404, audit rollback, and injected sold nights. Concurrency covers block against block, adjacency, extension against a new block, extension against cancellation, block against deactivation, waiting behind a held listing lock, activation against deactivation, and C-8, 20 iterations each. Gaps: the block row `55P03` mapping and the block routes' `503` with `Retry-After: 5` are untested (Major above); the 400 versus 422 distinction for an impossible query date is untested; extension on an inactive unit is untested; and two race cases have weak final state assertions. As the docs say, sold inventory is injected, so none of this proves real reservation consumption before M8.

## Resolution (author, 2026-11-09)

The major (no test for the block row lock timeout) is fixed: `tests/integration/reservations/blocks.test.ts` now calls `lockVisible` against a held row, and drives DELETE, a note PATCH, and an extension through the real handlers, asserting 503, `Retry-After: 5`, a safe problem body, and no write or audit. Minors fixed: S24 calendar errors are now 422 (the query schema checks shape only), an S26 overlap names `endDate`, a lock timeout after the listing lock maps to 503 in `translate`, the two weak concurrency assertions are strengthened, and the docs name the right field for the inactive unit error. Left as is, by choice: extension on a since deactivated unit is allowed (documented in api-contracts), the hand built test wiring in `support/blocks.ts` (same as T5), and the nits. Gates rerun after the fixes: check passed (61 files, 1,291 tests, build), integration 26 files / 347 tests, Chromium E2E 167 passed, 30 skipped. The reviewer has not rechecked the fixes.
