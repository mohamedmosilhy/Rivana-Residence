## Summary

The change adds the browser API client under `src/presentation/api-client/` (P5, P6, P7, P9, P10, P11 and G1 to G6), a money formatter, and `branch.timeZone` on `GuestReservation` (G1, G4 and G6 `200`), with regenerated `openapi.json` and tests. They all match: Bearer for G1 to G6, `Idempotency-Key` for P7, `If-Match` with the `"v<n>"` ETag that G5 and G6 send, `Rivana-Analytics-Session` read by `analyticsSessionFrom`, the P7 body field stripped before the fingerprint, and P11 accepting `text/plain`. ## Major

### 🟠 P5 query string is silently dropped on supported Safari 16.4 to 16.x, `src/presentation/api-client/request.ts:70`

**Problem**: `urlFor` decides whether to add the query with `query.size > 0`. `URLSearchParams.prototype.size` exists only from Safari 17.0, Chrome 113 and Firefox 112. On older browsers it is `undefined`, so `undefined > 0` is `false`, and the URL is sent without its `?checkIn=…&checkOut=…&adults=…&children=…`.
**Why it matters**: Next.js 16 targets `safari 16.4`, `chrome 111` and `firefox 111` by default (`node_modules/next/dist/docs/03-architecture/supported-browsers.md`; the project sets no `browserslist`), and Next does not polyfill `URLSearchParams.size`. Failing scenario: a guest on an iPhone stuck on iOS 16 (iPhone 8 or X) opens the T8b change flow, which takes availability for new dates from P5 (spec 0007, "Manage … and change (T8b)"). `searchAvailability` sends `GET /api/v1/branches/new-cairo/availability` with no query, and the server answers `400 INVALID_QUERY` every time. The guest can never search. The code already guards against an API that is missing on older phones (`AbortSignal.any`, line 155), so this one was missed. The unit tests run in jsdom on Node 26, where `.size` exists, so they cannot catch it.
**Suggested fix**: Build the string first and test the string. Take `query.toString()` and append `?` plus that string only when it is not empty, or count the entries you add yourself. Add a unit test that stubs `URLSearchParams.prototype.size` as `undefined` (or deletes it) and asserts the P5 URL still carries the query.

## Minor

### 🟡 One malformed analytics event voids the whole batch, `src/presentation/api-client/analytics-events.ts:29`

**Problem**: `withoutAddressSecrets` cuts the path at `?` or `#` but does not check the result against the P11 contract. A path of `"?x"` or `"#t=…"` becomes `""`, and a path longer than 200 characters is sent unchanged. Both fail `AnalyticsEventRequest` (`regex(/^\//)`, `.max(200)`), and the strict schema rejects the whole request with `422`.
**Why it matters**: Up to 19 good events in the same 20-event batch are lost silently (by design the sender never reports a failure). Failing scenario: T10 batches a `STEP_VIEW` together with a `PAGE_VIEW` whose path was derived from a long slug or a raw `location.href` fragment. The `422` drops both, and funnel step 3 goes missing for that session.
**Suggested fix**: After cutting the path, drop or truncate any event whose path does not start with `/` or is longer than 200 characters (the domain already normalizes paths to at most 200 characters), so one bad event cannot void its batch. Add a test for both cases.

## Nits

- ⚪ `src/presentation/api-client/request.ts:127`: `body.code as ApiProblemCode` accepts any string. A code the client does not know yet is typed as a known one. Consider a fallback such as `UNEXPECTED_RESPONSE` for unknown codes, or document that screens must handle a `default` case.
- ⚪ `src/presentation/api-client/guest.ts:79` with `result.ts:45`: G5 always sends `ETag`, but `etag` is typed as optional, so every caller needs `seen.etag!` (as in the test at `requests.test.ts:117`). A success type with `etag: string` for G5 would make that guarantee visible to callers.
- ⚪ `src/presentation/api-client/request.ts:164-177`: A header value that is not valid in a header (a non-ASCII `Idempotency-Key` or `If-Match`) makes `fetch` throw a `TypeError`. The client reports it as `NETWORK` ("Check your connection"). Callers use `randomUUID` and server ETags, so this is unlikely, but the message would be wrong.
- ⚪ `src/presentation/api-client/index.ts:4`: The comment at `analytics-events.ts:7-8` says the sender stays apart from the request module to keep public pages small. The T10 beacon should import `./analytics-events` directly rather than the barrel, so the size goal does not depend on tree shaking.
- ⚪ `src/presentation/api-client/analytics-session.ts:9`: Only `navigator.doNotTrack === "1"` is checked (not `window.doNotTrack` or `"yes"`). The server's `Sec-GPC` and `DNT` header checks still prevent storage, so this is defense in depth only.
- ⚪ `src/presentation/api-client/analytics-events.ts:23`: `new URL("about:blank").origin` (also `android-app:` and `data:` referrers) is the string `"null"`, which is then sent as the referrer. Skip origins equal to `"null"`.
- ⚪ `src/presentation/api-client/result.ts:7-13`: `TransportCode` copies the server's `TransportErrorCode`. The type test (`contract.test.ts:67`) checks only that every server code is known to the client. A code removed on the server would stay in the client list. A reverse check would catch that.

## Separate note: the known pricing issue (not part of this diff)

I agree it is real. `NightlyPriceResolver` validates periods with a `.strict()` `periodSchema` (`src/domain/pricing/nightly-price-resolver.ts:47-57`). `RatePeriodRecord` (`src/application/pricing/ports.ts:15-22`) adds `roomTypeId`, `branchId`, `createdAt` and `updatedAt`. `QuoteBooking` strips those fields (`src/application/quotes/quote-booking.ts:219`), but `currentRates` in `reservation-change-quote.ts:422-426` and `resolveAmounts` in `create-staff-reservation.ts:547-551` pass `rate?.periods` unchanged. So any period that `readMany` returns for the stay throws a `DomainValidationError`, which the API answers with `422`. The trigger is not only an active period that overlaps the stay: an inactive period returned for that range does it too, if the reader returns inactive ones. This breaks guest change quotes that need a new night's price (G5 and G6, which T8b depends on) and rate-priced staff bookings. The fix should map to the five `DateRatePeriod` fields as `QuoteBooking` does, with a regression test that has a period in range. It should be reported to the owner before T8b.

## Pricing fix review (2026-11-26, critical risk: prices)

**Verdict**: Approve with nits

**Scope**: two lines of production code, `src/application/reservations/reservation-change-quote.ts:425-434` (`currentRates`) and `src/application/reservations/create-staff-reservation.ts:552-561` (`resolveAmounts`). I only read code here. I did not run any test, build or database command, as instructed.

### Correctness

- Both callers now give `NightlyPriceResolver` exactly the five `DateRatePeriod` fields (`id`, `range`, `amount`, `active`, `label`). That matches its `.strict()` `periodSchema` (`nightly-price-resolver.ts:47-57`) and the existing mapping in `quote-booking.ts:219`, `search-availability.ts:140` and `get-rate-calendar.ts:50`. All five resolver callers in `src` now map the same way. No caller passes a stored row unchanged.
- Nothing else about pricing changes. The fields keep their values and order. `baseRate` still comes from `rate?.baseRate?.amount ?? null`, a `Money` instance that the resolver's custom check accepts. The resolver's own rules still apply: unique ids, active periods that must not overlap, a period winning over the base rate, an exclusive end date. So for these paths the fix only turns a `422` into the price the resolver would already have produced.
- **Inactive periods**: they cannot be priced on these paths. `readMany` loads only `active: true` periods that overlap the stay (`src/infrastructure/db/prisma/repositories/reservations/pricing/rate-repository.ts:167-171`), and the resolver filters on `active` again. Overlapping active periods are also prevented in PostgreSQL by the `EXCLUDE USING gist` constraints (`prisma/migrations/20261108120000_inventory_and_rates/migration.sql:128-134`). **Correction to my note above**: the trigger was any *active* period that overlaps the window `readMany` is given, not an inactive one.
- **Retained nights**: they keep their stored prices. In `reservation-change-quote.ts`, `nightsFor` (around lines 238-258) takes a retained night from `planned.retained` first and uses the current rate only for nights in `needsCurrentPrice`. A seasonal period that covers a retained night is resolved but never used for it. Before the fix, a period that overlapped only a retained night also caused the `422`, because `readMany` is given the whole requested stay. That case is now fixed too, and it prices correctly.

### Expected amounts (checked by hand)

The fixtures use a base rate of 100.00 a night (`website-booking.ts:210`) and 15% VAT; `TOTAL_MINOR = 34_500` is 3 nights × 10,000 × 1.15.

- **Staff create**, nights 04-10 to 04-13 with a period on 04-11 at 110.00: 10,000 + 11,000 + 10,000 = 31,000, × 1.15 = **35,650**. Correct. The test also asserts each night's `rateSource`, `ratePeriodId` and `label`, which proves the resolver ran with the period. The booking has no `manualAmounts` and is not `EXTERNAL`.
- **Staff stay change** to 04-14 with a period on 04-13 at 120.00: 34,500 + 12,000 × 1.15 = 48,300 = `FOUR_NIGHTS`. That value is sent as `acceptedTotal`, so `ok: true` checks the total exactly, and the new night row is asserted as `PERIOD`, 12,000.
- **Guest preview and apply** (G5, G6): accommodation 30,000 + 12,000 = **42,000**, total **48,300**. Correct. The apply sends the same `expectedTotal` and the stored night is asserted.
- **Paid request and approval**: 48,300 is more than the captured 34,500, so the change is REQUESTED. Approval prices it again under the locks and stores a snapshot total of 48,300 and the night at 12,000 `PERIOD`. Correct.

### Findings

#### 🟡 No test shows that a period on a retained night leaves that night's stored price alone, `tests/integration/reservations/guest-changes.test.ts` (new case near line 360)

**Problem**: Each new test puts the seasonal night only on the *new* night, 04-13. No test puts an active period over a retained night (for example 04-11) together with a new night and asserts that the retained night stays at 10,000.
**Why it matters**: This case reached the same `422` before the fix, and it is the part where prices could go wrong. If someone later builds `nightsFor` from the resolver output instead of `retained`, every guest who extends a stay would be silently repriced. The current tests would not catch it.
**Suggested fix**: Add one integration case, on the guest or the staff path: a period covering 04-11 to 04-14, extend the stay to 04-14, and assert that 04-11 and 04-12 keep 10,000 `BASE`, that 04-13 takes the period price, and the exact total.

#### ⚪ Nit: the five-field mapping is now copied in five places

`quote-booking.ts`, `search-availability.ts`, `get-rate-calendar.ts` and the two fixed files each map the fields by hand. TypeScript cannot catch a missed mapping, because extra properties are structurally assignable, and that is how this bug happened. One exported helper, for example `toDateRatePeriod` next to `RatePeriodRecord` in `src/application/pricing`, would make the next caller hard to get wrong. This is optional and can come later.
