**Reviewed by**: claude-opus-5-5, fresh-context review subagent (author model not stated; the caller ran the review on a different model)

## Summary
M9-T2 adds the pure domain rules for M9: four new reservation transitions, the payment state machine and its mapping to the reservation's `paymentStatus`, amount and currency matching, the late-success decision, `HoldPolicy`, `paymentMethodAvailability`, `CancellationDeadline`, the request status machine, and the CX/GC/Q-96 helpers. The code is small, pure (it imports only `src/domain/shared` plus one sibling file), consistent with the existing `ReservationStateMachine` patterns, and covered by exhaustive transition tables. The domain enums match `prisma/schema.prisma` exactly. The new and affected unit files pass (re-run here: 11 files, 310 tests). Two problems should be fixed before commit. First, the "open request" guard does not cover requests that are approved but still in the refund stage, so a guest could change or re-request a booking that is mid-refund. Second, the new `src/domain/payments` module is not listed for D-8 enforcement. There are seven Minor findings, mostly about documentation and test edges.

## Major

### 🟠 The request guard ignores requests that are approved but still refunding, `src/domain/reservations/cancellation-request.ts:67-110`
**Problem**: `canRequestCancellation` and `canGuestChange` decide only on `reservationStatus === "CONFIRMED"` and a caller-supplied `hasOpenRequest` boolean. The domain never says which request statuses count as "open". Read literally (spec and CX-2 say "OPEN"), the guard misses three cases where a request is still in progress on a `CONFIRMED` reservation:
- `APPROVED`: a paid approval before the refund is sent, and a staff paid cancellation, which is created `APPROVED`.
- `REFUND_PENDING`: the refund is running; the reservation stays `CONFIRMED`.
- `REFUND_FAILED`: the reservation stays `CONFIRMED`, and `reservationPaymentStatusFor` maps it back to `PAID`.

These cases follow:
- A guest can change dates on a booking whose refund is running. `decideChangeApplication(ONLINE, same total)` returns `APPLY_NOW`, so inventory moves and change messages go out for a booking that is about to become `CANCELLED`.
- After `REFUND_FAILED`, a guest can open a second cancellation request (the partial unique index covers only `OPEN`). `planApproval` sees `PAID` and returns `REFUND_FIRST`, so two requests now drive one payment. Staff `RetryRefund` on the first request and approval of the second race to `refundAttempt`, and `CompleteRefund` cannot tell which request to complete.
- A guest can request cancellation while a staff paid cancellation is in progress.

**Why it matters**: This is Critical-tier money logic. The spec's invariant "at most one open request per reservation" is meant to stop competing refund or change paths. The domain is the one place that should encode it, but T7, T10 and T11 would each have to reinvent which statuses block new requests.
**Suggested fix**: Add one domain predicate, for example `blocksNewGuestRequest(status)`, that is true for `OPEN`, `APPROVED`, `REFUND_PENDING` and `REFUND_FAILED`. Document that `hasOpenRequest` means "any request in a blocking status", or take the statuses as input. As a cheap second guard, refuse when the reservation's `paymentStatus` is `REFUND_PENDING`. This is a spec gap rather than a deviation from the spec, so record the owner's decision in spec 0006 and the CX-2/GC-2 rows. Add unit cases for each status.

### 🟠 The new `payments` domain module is outside D-8 enforcement, `eslint.config.mjs:33` and `tests/unit/architecture/module-boundaries.test.ts:45`
**Problem**: `src/domain/payments/` has a public `index.ts`, but `payments` is missing from `PUBLIC_SURFACE_MODULES` in both files. Nothing stops `@/domain/payments/payment-state` deep imports. The boundary tests pass only because they never check this module. The task card says "D-8/dependency-rule tests must stay green", and the D-8 row in `docs/architecture/dependency-rules.md` lists the reservation-era modules by name.
**Why it matters**: T3 to T8 (`src/application/payments`, the callback, refunds) are built on this module next, and a deep import would go unflagged. The project treats the dependency rules as non-negotiable.
**Suggested fix**: Add `"payments"` to both lists (it also covers `src/application/payments` when T3 creates it), and add it to the D-8 row in `dependency-rules.md`.

## Minor

### 🟡 `matchesPayment` throws on an amount that came from outside, `src/domain/payments/payment-state.ts:70-80`
**Problem**: An event amount of zero, a negative number, a fraction or NaN throws `DomainValidationError` instead of returning `false`. The event is external data. A provider may send `0` or no amount on a `DECLINED` or `SESSION_CLOSED` event, or on a bad refund event.
**Why it matters**: Decision 5 says every verified event is recorded and answered with `200`, and a mismatch becomes `IGNORED_MISMATCH`. A throw inside `ProcessPaymentCallback` would roll back, return an error, and make the gateway retry forever without recording the event. The project pattern is a validation error for malformed internal input and a result for business refusals.
**Suggested fix**: Keep throwing for the payment side (our own stored data). For the event side, return `false` when the amount is not a safe positive integer, and test that case.

### 🟡 The absolute 24 h deadline is an interpretation with no recorded decision, and the fall-back case is untested, `src/domain/reservations/cancellation-deadline.ts:41`
**Problem**: CX-1 can be read two ways: 24 hours on the clock, or the check-in time on the previous local day. The code uses 24 hours on the clock. On the two Cairo daylight-saving days the deadline moves by one hour on the wall clock (13:00 local in April; 15:00 local in October). The task card says "DST-correct via `zonedLocalToUtc`", and the code is correct for its own reading, but the reading itself is not written down in the spec or the lifecycle doc. Only the spring-forward case is tested.
**Why it matters**: The guest-facing text in T7 and M10 ("you can request until …") must format the instant, not repeat "14:00 the day before", or the guest is told the wrong time twice a year. Hotel staff usually expect the previous-day wall-clock reading.
**Suggested fix**: Get the owner to confirm the choice and record it in CX-1 and spec 0006. Add a fall-back test (arrival 2026-10-30 14:00, deadline `2026-10-29T12:00Z`, which is 15:00 local). Note that display code must format the deadline instant itself.

### 🟡 `canRequestCancellation` does not check for a blocked phone, `src/domain/reservations/cancellation-request.ts:67-81`
**Problem**: Decision 7 and the spec's security model say a blocked phone cannot request (Q-75, guest session path). `canGuestChange` takes `phoneBlocked`; `canRequestCancellation` does not, even though `PHONE_BLOCKED` is in the refusal type it returns.
**Why it matters**: The two guest-request rules are asymmetric, so T7 has to remember to add the check itself. The return type suggests the function already covers it.
**Suggested fix**: Add an optional `phoneBlocked` input (the caller passes `false` for the manage-token path), or document that the caller checks it. Either way, add a test.

### 🟡 `CANCEL_APPROVED` ignores the payment method, and needs the post-refund state, `src/domain/reservations/state-machine.ts:182-191`
**Problem**: The transition allows `ONLINE` with `NOT_REQUIRED`, and `PAY_AT_HOTEL` with `REFUNDED`. Neither combination is valid, and the M9 test table uses `ONLINE` with `NOT_REQUIRED`. Also, when `CompleteRefund` runs, the stored `paymentStatus` is still `REFUND_PENDING`, which this transition refuses. The caller must therefore pass a state already set to `REFUNDED`. That works, but nothing documents it, and it is easy to get wrong in T8.
**Why it matters**: The check is looser than `CANCEL_UNPAID`, which pairs the method with the status. The calling convention is not obvious.
**Suggested fix**: Require `PAY_AT_HOTEL` with `NOT_REQUIRED`, or `ONLINE` with `REFUNDED`. Document in the comment that the refund-completion path passes the payment status as it will be after the refund. Adjust the test to use valid pairs.

### 🟡 `decideChangeApplication` compares against the current total, but GC-4 says the paid total, `src/domain/reservations/cancellation-request.ts:119-138`
**Problem**: GC-4 and Q-85 say a paid online change applies at once when the new total equals the paid total. After a staff modification (M8-T9, with the difference settled at the desk under Q-66), `Reservation.totalMinor` can differ from `Payment.amountMinor`. The parameter name `currentTotalMinor` invites the caller to pass the reservation total.
**Why it matters**: A guest could apply at once a change whose total equals the current total but not the amount captured, or be sent to approval when the total matches the paid amount.
**Suggested fix**: Rename the parameter to `paidTotalMinor` and document that the caller passes `Payment.amountMinor`; otherwise get a spec decision on which total applies.

### 🟡 Docs are not updated for this change, `src/domain/payments/payment-state.ts:15-23`
**Problem**: The diff changes no file under `docs/`. The task card puts these updates in scope:
- The lifecycle doc's "implemented" markers.
- The test matrix rows.
- The state diagram, which still shows `PAYMENT_FAILED --> [*]` and lacks the M9 edges.

Two of the author's decisions are also not recorded:
- `EXPIRED`/`FAILED → SUCCEEDED`. This follows from Decision 5, but the spec's payment state list omits it.
- The auto-refund path now goes `EXPIRED → SUCCEEDED → REFUND_PENDING` in two steps, while Decision 5 reads "mark the payment `REFUND_PENDING`".

**Why it matters**: AGENTS.md says docs ship with every change. T5 will implement against the spec table and could hit `canTransitionPayment(EXPIRED, REFUND_PENDING) === false` without warning.
**Suggested fix**: Update the spec 0006 payment transitions and the Decision 5 wording, the lifecycle doc (diagram, PY-5, the CX-1 reading, `implemented` markers), the test matrix, and the D-8 row.

### 🟡 Test gaps on branches that are not covered, `tests/unit/domain/payment-state.test.ts:82-119`
**Problem**: `decidePaymentSuccess` is not tested for:
- `CONFIRMED` with `INITIATED`/`EXPIRED`, which returns `REFUND_AUTOMATICALLY`.
- `AWAITING_PAYMENT` with `EXPIRED`/`FAILED`, which returns `CONFIRM`.
- Invalid input, which throws.

Also missing:
- `paymentMethodAvailability` with an unknown method.
- `canGuestChange` validation when the phone is blocked and the status is invalid.
- `CancellationDeadline` on a daylight-saving fall-back day, or with a check-in time inside the spring-forward gap.

The card's planned `payment-method-availability.test.ts` was folded into `hold-policy.test.ts`. That is acceptable, but the file name no longer says what it covers.
**Why it matters**: This is branching logic in Critical-tier money code. These combinations are the ones T5 and T6 will reach under races (for example, a reservation flipped to `PAYMENT_FAILED` by the in-transaction expiry while its payment is still `INITIATED`).
**Suggested fix**: Add a full reservation-status by payment-status table for `decidePaymentSuccess`, plus the edge cases above.

## Strengths
- The tables are exhaustive: every from/to pair for payments and requests, and every status × M9 action for the reservation machine, is asserted. Any table change is caught.
- `decidePaymentSuccess` uses `canTransitionPayment(_, "SUCCEEDED")` as its idempotency gate, so the duplicate rule and the state table cannot drift apart. It also still behaves correctly if a reservation reaches `PAYMENT_FAILED` while its payment is `INITIATED`.
- `reservationPaymentStatusFor(REFUND_FAILED) = PAID` matches spec Decision 2 ("a failed refund returns it to `PAID`") and is the honest reading, since the money is still captured.
- The deadline boundary (strictly before) and the hold boundary (expired at the expiry instant) are both tested to the millisecond.
- Changing `create(WEBSITE, ONLINE)` to return `AWAITING_PAYMENT` is safe today: `create-website-reservation-input.ts:124` still refuses `ONLINE` before any use case runs, and no application code calls `ReservationStateMachine.create`.
- The new actions do not leak into the staff available-actions list (`staff-reservation-reads.ts:178` enumerates its actions explicitly).
