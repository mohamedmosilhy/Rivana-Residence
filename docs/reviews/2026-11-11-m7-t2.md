## Summary
M7-T2 adds the pure coupon rules (`normalizeCouponCode`, `CouponPolicy.validate`) and the service rules (`ServiceKind`, `parseServiceOfferingInput`, `selectRequestedServices`) in the domain layer, matching spec 0004 Decisions 4 and 5 and the approved task card: the fixed check order, the half open window, null limits as no limit, the per phone limit only with a phone, child price only for person units, strict bodies, and only requested services. I found no path where a well typed coupon is wrongly accepted. The headline issues are small: the runtime "fails closed on corrupt input" guarantee covers dates, limits, counts, and kind or value, but not the boolean flags or `branchIds`, so the doc comment overclaims; and a few ordering and bound cases are untested, so a wrong implementation could still pass. Reviewer ran the four new and changed test files plus `tests/unit/architecture`: 7 files, 181 tests passed. The author reports `npm run check` green (not re run here).

## Minor
### 🟡 Runtime fail closed guarantee is partial: `active`, `allBranches`, `branchIds` are checked by truthiness, `src/domain/coupons/coupon-policy.ts:110`
**Problem**: The class comment (`coupon-policy.ts:61-66`) and the task card say "A corrupt record or context throws instead of granting a discount", and the code does validate dates, limits, counts, and the kind or value pair at runtime. But `!coupon.active` (line 110) and `!coupon.allBranches && !coupon.branchIds.includes(...)` (line 116) rely on truthiness and on `branchIds` being an array. A probe outside the type system showed: `active: "false"` returns valid; `allBranches: "no"` returns valid at any branch; `allBranches: false, branchIds: "xbx"` returns valid at branch `"b"` because `String.prototype.includes` does a substring match. Each of these fails open.
**Why it matters**: TypeScript and the Prisma mapper (T3) make these inputs very unlikely, so this is not a live bug. But this is the one component whose stated job is to fail closed, and it guards the inputs that are unlikely to be wrong (finite dates) while leaving the ones that decide branch scope to the type system. A future mapper that builds `branchIds` from a joined string, or passes a raw JSON value, would get a silent branch scope bypass instead of the typed error the comment promises.
**Suggested fix**: Either check them the same way as the other fields (`typeof coupon.active === "boolean"`, `typeof coupon.allBranches === "boolean"`, `Array.isArray(coupon.branchIds)` with string members, otherwise `corrupt(...)`), and compare with `coupon.active !== true` and `coupon.allBranches === true` so a non boolean can never widen access; or narrow the comment to say which fields are checked at runtime. Add one corrupt case per field to the "fails closed" table.

### 🟡 The order test does not pin where `EXPIRED` sits, and an invalid `endsAt` is untested, `tests/unit/domain/coupon-policy.test.ts:154`
**Problem**: "reports the first failing reason in the fixed order" builds a coupon with `startsAt` in the future and no `endsAt`, then peels off one fault at a time. `EXPIRED` never appears in that chain, so an implementation that checked `WRONG_BRANCH` or `LIMIT_REACHED` before `EXPIRED` (or `EXPIRED` before `INACTIVE`) would pass every test. Likewise the corrupt input table tests only an invalid `startsAt` (line 231); a `validDate` check that looked only at `startsAt` would pass.
**Why it matters**: Spec 0004 Decision 4 fixes the order, and the order decides which `context.reason` a guest sees when several apply. The current implementation is correct; the tests just would not catch a regression.
**Suggested fix**: Add a second chain, or extra cases, that use an expired window: inactive and expired gives `INACTIVE`; expired and wrong branch gives `EXPIRED`; expired and over the limit gives `EXPIRED`. Add `["an invalid end date", () => coupon({ endsAt: new Date(NaN) }), {}]` to the corrupt table.

### 🟡 Child price bounds and shape are untested, `tests/unit/domain/service-offering.test.ts:101`
**Problem**: The price bound table (0, -1, 1.5, max + 1, NaN) runs only against `price`. Nothing tests `childPrice` of 0, above `SERVICE_PRICE_MAX_MINOR`, a fraction, another currency, or an extra key. The code reuses the same `amount` schema, so it is correct today, but a refactor that gave `childPrice` its own looser schema (for example `amountMinor >= 0` to mean "free") would pass every test and then hit the database `CHECK childPriceMinor > 0` as a 500 instead of a 422.
**Why it matters**: SV-1 says no child price means children are not charged; a zero child price is a different, refused value, and the spec's S36 row lists the bound as a 422.
**Suggested fix**: Run the same bound table against `childPrice` on a `PER_PERSON` body and assert the issue path is `childPrice.amountMinor`.

## Nits
- ⚪ `src/domain/coupons/coupon-policy.ts:124`, `phone: null` or `phone: ""` counts as "a phone was supplied" (probe returned `PHONE_LIMIT_REACHED`). That is the strict direction and harmless while counts are zero, but Decision 4 says the check runs only for a verified phone; consider treating null and blank as absent, or documenting that T6 must pass `undefined`.
- ⚪ `src/domain/services/service-offering.ts:55-63`, the description field re-implements `optionalText(max)` from `src/domain/shared/content-fields.ts` (trim, max, nullable, blank to null). Reusing it keeps one definition. Like other text fields in the project it accepts U+0000, which PostgreSQL text columns reject at insert time (a 500, not a 422); a project wide decision, not this task's.
- ⚪ `src/domain/services/service-offering.ts:101`, `parseServiceKind` lives in `service-offering.ts`; the task card put it in `service-kind.ts` next to `isServiceKind`.
- ⚪ `src/domain/coupons/coupon-policy.ts:42-44`, `CouponValue` restates `QuoteCouponValue` from `pricing/quote-calculator.ts:14-16` by comment only. A type level assertion in a test (assigning a `CouponValue` to a `QuoteCouponValue`) would catch drift before T6.
- ⚪ `src/domain/services/service-offering.ts:109-112`, the two failure shapes are told apart only by which key is present (`kind` versus `issues`). An explicit discriminant (for example `reason: "UNAVAILABLE" | "INVALID"`) would make the 409 versus 422 mapping in T6 harder to get wrong. The returned array is also not frozen, unlike `QuoteCalculator` output.
- ⚪ `tests/unit/domain/coupon-policy.test.ts:194`, "does not mutate its inputs" freezes the objects, but `Object.freeze` does not protect a `Date`'s internal time, so a `startsAt.setTime(...)` mutation would go unnoticed.
- ⚪ `tests/unit/domain/service-offering.test.ts:213`, when several requested kinds are unavailable, the "first in request order" refusal is not tested (for example `["AIRPORT_TRANSFER", "BREAKFAST"]` with no offerings should report `AIRPORT_TRANSFER`).

## Strengths
- The coupon code normal form is tight and safe. It allows only ASCII, folds case with an explicit `[a-z]` replace (no locale dependent `toUpperCase` on Turkish or German letters), uses a linear, bounded regex, and refuses full width, zero width, NUL, and emoji input, all of which have tests. It matches `upper(code)` uniqueness and `VARCHAR(32)`.
- `CouponPolicy` does not leak: it returns only a reason code, never the branch list. The value pair is checked both ways (a percent coupon carrying an amount, or a fixed coupon carrying a percent, throws), the window is half open as specified, and an inverted window naturally refuses instead of granting.
- `parseServiceOfferingInput` is strict at every level (unknown keys including `branchId`, `kind`, and `__proto__`, and extra keys inside `price`, are refused). The child price rule uses the shared `isPersonUnit`, so the parser and `QuoteCalculator` cannot disagree.
- `selectRequestedServices` returns only requested, active offerings in request order, with the unrequested inactive case tested explicitly.
- The module boundaries are clean: `coupons` and `services` import only `shared` (and `zod`, as other domain parsers do), `pricing` keeps its one way dependency on `services`, both modules have an `index.ts`, and `coupons` joined `PUBLIC_SURFACE_MODULES`. The persistence boundary test passes, with no `.coupon` access or quoted model name.

## Test coverage
New logic is well covered: one test per refusal reason (T-CPN-1 to 5 and 5b), exact start and end instants, all branches versus listed (including an empty list), limits at and above the count, null limits, a typed throw for 14 corrupt inputs, all four price units, the child price allowed and refused by unit, price bounds, unknown keys, description trimming, and every `selectRequestedServices` branch (only requested, nothing requested, inactive, missing, duplicate, unknown, lower case, non list). Gaps that would let a wrong implementation pass: the position of `EXPIRED` in the check order, an invalid `endsAt`, the child price bounds, the boolean and `branchIds` shape cases (see Minor), and the first missing kind among several. The reviewer re ran the new unit and architecture tests (7 files, 181 passed); the full `npm run check` result is the author's.
