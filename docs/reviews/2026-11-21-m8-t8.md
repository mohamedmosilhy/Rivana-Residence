## Summary
The change adds S3 staff creation, S4 external recording, the S1 list, the S2 detail with ETag, and the S15 history. It reuses `InventoryGuard`, `ReservationUnitOfWork`, the guest-first lock order, `QuoteBooking.priceResolved`, and idempotency keyed by actor and source. Authorization runs before any I/O, and the concurrency tests are real PostgreSQL races. Two open issues need changes. First, nothing bounds the stay length for staff or external writes, so a typo or a hostile account can make one reservation expand to millions of nights while it holds the listing locks. Second, S3 accepts past check-in dates, which domain rule AV-5 forbids for non-external sources.

## Major

### 🟠 No limit on stay length for S3 and S4 (memory, lock duration, and inventory DoS), `src/application/reservations/staff-reservation-input.ts:96`
**Problem**: `parseStaffBooking` builds `StayRange.create(checkIn, checkOut)` with no maximum.
- The contract `Stay` (`src/contracts/api/v1/reservations.ts:125`, through `StaffFields`) only checks `checkOut > checkIn`, and `isoDate` accepts any 4-digit year.
- Inside the transaction, `load` expands every night (`src/application/reservations/create-staff-reservation.ts:345`, `[...stay.nights()]`) and sends the array to `inventoryReader.readNights`.
- `NightlyPriceResolver` then prices every night, and `insert` calls `createMany` with `lines × nights` `ReservationNight` rows.
- Unpriced S4 builds the same arrays at `:468`.
- The 32 KB body limit only bounds `priceOverride` and `amounts`. It does not bound an S3 priced from the base rate or an unpriced S4, which need just two dates.

**Why it matters**:
- One receptionist request such as `2031-01-01`→`9999-12-31` with 5 lines is about 18 million night objects and rows. It runs while the room-type row locks are held, so website and staff bookings for those listings stall, and the Node process can run out of memory.
- A typo is enough to cause harm. Checkout `2302` instead of `2032` succeeds in practice (about 98k nights × base rate stays under the INT32 check) and takes the inventory for centuries. Cancellation does not exist until T9.
- The DTO also returns every night.

**Suggested fix**:
- Get the owner's decision on the pending 366-night technical cap.
- Enforce it in one shared domain place, used by staff, external, and later modify paths. It should be a structural stay limit, separate from the public `StayPolicy`, refused as a `422` field error on `stay.checkOut`.
- Add `.max()` to `Amounts.nights` for consistency.
- Add unit tests for the boundary (366 and 367) and one integration test that proves no rows are written.
- Until the cap ships, list this as an open issue in the review package.

### 🟠 S3 accepts past-dated stays, against AV-5, `src/application/reservations/create-staff-reservation.ts:308`
**Problem**: `load` (and `parseStaffBooking`) never compares `stay.checkIn` with branch today. `docs/domain/availability-and-pricing-rules.md` AV-5 says: "Staff may record past-dated stays only for `EXTERNAL` reconciliation and corrections (audited)." A `STAFF` source booking with a check-in in the past is accepted, gets `CONFIRMED`, and takes inventory. With `sendConfirmation`, it also sends a "confirmed" message whose manage link may already have expired (`manageTokenExpiry` is based on check-out).

**Why it matters**: It breaks a documented domain rule, and the past nights it consumes are shown as sold. AGENTS.md also says branch today must come from `localDateAt(clock.now(), branch.timeZone)`, and this writer never derives it.

**Suggested fix**: Inside `load`, after the branch row is read, compute `today = localDateAt(now, branch.timeZone)`. Refuse `source === "STAFF"` when `stay.checkIn` is before today, as a `422` on `stay.checkIn`, and keep `EXTERNAL` allowed. If the owner thinks "corrections" covers S3, record that decision in AV-5 and the spec instead. Either way, add a test.

## Minor

### 🟡 The concurrent duplicate `externalReference` path is untested, `src/application/reservations/create-staff-reservation.ts:294`
**Problem**: Lines 294–305 resolve a `CONFLICT` from the unique `(branchId, externalReference)` index after rollback: winner replay first, then `exists`, then `EXTERNAL_REFERENCE_EXISTS`. The only duplicate test (`tests/integration/reservations/staff-reservations.test.ts:292`) is sequential. The in-transaction `exists` check at `:320` catches it, so this branch never runs. The case this code exists for is two S4 requests with the same reference on different listings. They take different listing locks, so they run truly concurrently.

**Why it matters**: This is error-handling branch logic in a Critical task, and it leans on aborted-transaction behavior (comment at `:294`). A regression here would show up as a raw `409 CONFLICT`, which S4 does not document, instead of `EXTERNAL_REFERENCE_EXISTS`.

**Suggested fix**: Add a 20-round race: two independent clients, two listings, the same reference, different keys, both waiting on a held barrier. Expect one `201` and one `EXTERNAL_REFERENCE_EXISTS`, plus one reservation and one audit row.

### 🟡 Staff and external writers only accept `PUBLISHED` listings, `src/application/reservations/create-staff-reservation.ts:326`
**Problem**: `load` resolves listings through `PublicListingReader.listPublished` (`status: "PUBLISHED"`). S20 (staff availability) deliberately shows "every listing of the branch in any publication status". But S3 and S4 return `404` for a listing in draft or archived status that still has active units and capacity.

**Why it matters**: When an editor takes a listing off the website, staff can still see its free units but can't record the hotel-system bookings for it. Manual reconciliation (S4) then quietly breaks for that room type. The spec does not say whether this is intended, and the card is silent.

**Suggested fix**: Ask the owner. If staff should be able to book any listing of the branch, add a branch-scoped staff listing reader that ignores status and keeps the occupancy limits. Either way, add a T-RES test for an unpublished listing on S3 and S4 that pins down the decision.

### 🟡 S15 projection only tested for `reservation.staff-created`, `src/infrastructure/db/prisma/repositories/audit/audit-log.ts:65`
**Problem**: `reservationChanges` also projects website `reservation.created` events, whose stored `changes` hold `couponCode`, `marketingOptIn` and other fields. Every other action returns `{}`. The integration test checks only one staff-created event.

**Why it matters**: The allowlist is privacy-relevant, and the website event is the most common history entry. Nothing tests that its `couponCode` and consent flags stay out of the response, or that unknown actions come back empty.

**Suggested fix**: Add a repository-level test. Seed one `reservation.created` event with full changes and a reason, plus one unrelated action. Assert the exact projected keys, and assert that `reason` and the guest fields are absent.

### 🟡 The AC-8 log assertion only captures `console.info`, `tests/integration/reservations/staff-reservations.test.ts:414`
**Problem**: The HTTP logger writes failures through `console.error` (`src/app/api/v1/_http/logger.ts:32`). The test spies only on `console.info`, and only for the S3 refusal paths. It does not capture S4, S2, or S1 `q` searches, which carry email and phone in the query string.

**Why it matters**: AC-8 says no log line contains guest personal data. A `q=` value or an error log on a 5xx path would not be caught.

**Suggested fix**: Spy on `info`, `warn` and `error`. Run one S1 search with a distinctive email in `q`, one S4 request, and one forced 500. Assert that none of the values appear.

As a result, `allowedActions` (CHECK_IN, NO_SHOW, CANCEL) can't be made deterministic in route tests. Accept a `clock` option in `staffReservationQueries`.
- ⚪ `src/application/reservations/staff-reservation-reads.ts:186`: today every role with `reservations:read` also has `guests:read`. So the redaction branches can't be reached and are only covered by a mocked `true`. These are `contact`, `internalNotes`, service `details`, and the guest search columns in `staff-reservation-reader.ts:45`. A unit test that calls `staffReservationView` and `list` with `includeGuest=false` would protect them for a future role.
- ⚪ `src/infrastructure/db/prisma/repositories/reservations/staff-reservation-reader.ts:49`: phone search is a raw substring on E.164, so a locally formatted number (`0100 123 4567`) finds nothing. Consider normalizing the digits of `q` for the phone column.
- ⚪ `src/contracts/api/v1/routes.ts`: S3 and S4 `errors` leave out `CONFLICT`, which `createBooking` can still return in a theoretical residual case (`create-staff-reservation.ts:305`). Either list it or map it to `TRY_AGAIN`.

## Strengths
- **Authorization before I/O.** `authorizeBranch` checks the capability for the source, and `pricing:override` is checked before the idempotency key or any lookup. The T-AUTHZ-2 sweep asserts zero port calls on refusal for every role × assigned/foreign/unassigned scope.
- **Lock order.** It matches spec Decision 7: guest upsert and `FOR UPDATE`, then sorted listings via `InventoryGuard`, then the coupon row. The same-phone S3 vs P7 race and the external vs website race are real PostgreSQL tests: 20 rounds, independent clients, waits observed in `pg_stat_activity`, and final inventory and audit counts checked.
- **Idempotency.**
  - The key namespace is source and actor, backed by the `NULLS NOT DISTINCT` unique index.
  - Replay is checked again after the guest lock, and the committed winner is resolved on the outer client after an aborted transaction.
  - A branch mismatch counts as key reuse (422), so a replay can't leak another branch's reservation.
- **Server-side pricing.**
  - `QuoteBooking.priceResolved` was extracted, so website, staff, override, and priced external bookings share one ADR 027 composition with the current VAT.
  - External bookings carry no services or coupon, and their amounts are all nights or none.
  - Override replaces nightly amounts only and records the reason in the audit `reason` column, which the S15 projection never exposes.
- **Privacy.**
  - S1 guest columns and guest search are gated on `guests:read`.
  - S15 is a strict numeric/boolean allowlist with no reason or identity.
  - Wildcard escaping follows the existing precedent, and responses are `no-store`.
  - The external conflict wording promises no real-time sync.
- **Minimal migration.** A nullable `externalChannel VARCHAR(80)`, as the owner approved.

## Independent follow-up after fixes

**Verdict: Approved.** Both majors and all four minors from `docs/reviews/2026-11-21-m8-t8.md` are fixed in the current code, and no code findings are still open. This was a read-only review: I didn't run the unit, integration or E2E suites.

**Majors**
1. **366-night cap: fixed.**
   - `src/application/reservations/staff-reservation-input.ts:103` refuses a stay over 366 nights with a 422 on `stay.checkOut`, and `MAX_STAFF_STAY_NIGHTS` is defined at `:14`.
   - The check sits right after `StayRange.create` (`nightCount` is plain arithmetic). That is before the idempotency lookup, the guest upsert, any lock, and the per-night expansion.
   - The contract's `Amounts.nights` now has `.max(366)` (`src/contracts/api/v1/reservations.ts:122`).
   - The test at `staff-reservations.test.ts:329` checks 366 and 367 nights on both S3 and S4, and confirms no guest or reservation rows are written.
2. **AV-5: fixed.**
   - `src/application/reservations/create-staff-reservation.ts:322` refuses a staff check-in before the branch's local today (`localDateAt(now, branch.timeZone)`) with a 422 on `stay.checkIn`. External bookings may still be past-dated.
   - The test at `:358` uses a clock near midnight in the branch's time zone. It covers a refused past S3, an allowed historical S4, and an allowed same-day S3.

**Minors**
- **Concurrent duplicate external reference: fixed.** The test at `:878` runs 20 rounds with independent clients on two listings. A held `SHARE` table lock lets both duplicate checks pass and makes both inserts wait. The insert only ignores collisions on `reference` (`reservation-repository.ts:274-283`). So the losing request fails its insert on the unique index, the rollback path runs, and it returns `EXTERNAL_REFERENCE_EXISTS`. The test asserts the reservation, room, guest and audit counts.
- **Unpublished listings: fixed.** S3 and S4 now accept listings in any publication status: `load` reads them from `AvailabilityCatalog` with `listRoomTypes(branchId, "ALL")` (`create-staff-reservation.ts:338`). The read is limited to the branch and keeps the occupancy limits. IN-4 still applies only to online booking. The test at `:394` books DRAFT and ARCHIVED listings, and gets a 404 for another branch's listing.
- **S15 history projection: fixed.** The test at `:432` stores a website `reservation.created` event with a coupon code, the marketing consent flag, the guest's name, a token and a reason. The response contains only `{totalMinor, units}`, and an unknown action returns `{}`.
- **AC-8 log check: fixed.** The test at `:645` now watches `console.info`, `warn` and `error`. It runs an S1 search with the guest's email in `q`, an S4 request, an S2 read and a forced 500 (exactly one error log), and asserts no guest data appears in any log.

**Earlier nits:** the clock is now passed into the reservation queries (`src/composition/reservations.ts:188`). The test at `:498` covers what is hidden from a role without guest access. The local phone-format search is out of scope, as you decided.

**Two optional nits, neither blocking:**
- `create-staff-reservation.ts:211` reads the clock a second time for the AV-5 check, while insert and audit use `now` from `:176`. Passing `now` through would keep one timestamp per request.
- `src/contracts/api/v1/reservations.ts:126` says "1 to 366 nights" in the contract text, but the schema doesn't check it; only the application does. The behavior is correct either way.

The date check samples the clock after the listing locks so it uses the branch day at the time of validation. Creation and its audit event use the transaction's start timestamp. The application enforces the 366-night rule for both sources, including requests without a nightly amount array. Phone search uses the stored E.164 value.
