## Summary

This change adds the `/{branch}/book/details` page. It brings in `GetBookingSetup`, which replaces `GetBookingSearchSetup` so the "can this branch book" rule lives in one place, and a server quote under P6's per client limit. The page has a guest details form, a lazily loaded `PhoneVerificationStep` for WhatsApp or email codes, a per tab `sessionStorage` draft, and a live Continue button that rebuilds the basket from `u` on the way back. It matches the approved plan, including decisions 1A to 4A. The security work is careful. The branch always comes from the server. Prices come only from the server quote. The token is held only in component state. The draft writes an allowlist of five fields. Logs record only the error class. AC-14 is gated twice. I found no blocker or major issue. The main issue is that the client treats a refusal from the server's per phone rate limit as if it belonged to one channel. The rest are small coverage, performance and accessibility points.

## Minor

### 🟡 A rate limit is applied to one channel, but the server's per phone limit covers both, `src/presentation/features/booking/phone-verification-step.tsx:101`

**Problem**: `refused()` records a `RATE_LIMITED` wait only for the channel that was refused (lines 180-183). The "Send by … instead" button checks only `limitWait(other)` (lines 369-381) and ignores `sent.resendAtMs`. On the server, P9 checks `requestHistory(phone)` with no channel filter (`src/infrastructure/db/prisma/repositories/reservations/guests/phone-verification-repository.ts:64-69`), and the per client `verification-request` bucket has no channel either. Only the per email history is specific to one channel (`src/application/guests/phone-verification.ts:139-161`).
**Failing scenario**: A guest sends 3 WhatsApp codes within 15 minutes. P9 answers the third with `resendAvailableAt` about 15 minutes ahead, and "Send again" is correctly disabled. "Send by email instead" stays enabled, though. Pressing it reaches P9, which refuses with `RATE_LIMITED` because the phone history counts every channel. The press uses one of the client's 10 hourly verification requests and shows "Too many codes were requested" with the hotel contact. The same happens in the send view: after a WhatsApp `RATE_LIMITED`, choosing the Email radio enables "Send code" again. The comment on line 101 and the unit test "limits only the channel the server refused" (`tests/unit/public/phone-verification-step.test.tsx:217`) describe behaviour that holds only for a refusal of the email channel.
**Why it matters**: The server stays the authority, so nothing unsafe happens. The guest is offered a path that is certain to fail, and the shared per client bucket shrinks.
**Suggested fix**: Apply a refusal of the WhatsApp channel, and `sent.resendAtMs`, to both channels. Keep only a refusal of the email channel limited to email, since that one can come from the email history alone. If that seems too fine grained, apply every refusal to both channels. Then change the comment and the unit test, and add the opposite case (WhatsApp refused, so email waits too).

### 🟡 The search page now reads services on every request, `src/application/booking/get-booking-setup.ts:61`

**Problem**: `/{branch}/book` now calls `getBookingSetup` (`src/app/(marketing)/[branch]/book/page.tsx:78`). This runs `services.listByBranch` on every search render, but the search page uses only `bookable`, `today`, `phone` and `email`. The page is public and the setup read runs before any rate limit.
**Why it matters**: Every search, including bots, makes one extra database round trip that it does not need. It is small but permanent on the busiest booking page.
**Suggested fix**: Load services only when the caller asks. One option is a second method, or an option on `GetBookingSetup`, used by the details page. This keeps one readiness rule (the reason for the merge) without the extra read.

### 🟡 The plan's integration proof for "no token in logs or analytics rows" is not in the integration test, `tests/integration/reservations/booking-details.test.ts:1`

**Problem**: The plan and the spec task row ask for "a test that no token reaches a URL, log line, or analytics row". The new integration file covers setup and the quote limit only. The AC-13 proof is in other places:
- The E2E test (`tests/e2e/booking-journey.spec.ts:197-245`) checks storage, cookies, the address, the page, request addresses, the browser console and the `SiteEvent` rows.
- The existing M8 test `phone-verification.test.ts:385` checks server logs for P9/P10.
- The page's own log line is checked in `booking-details-page.test.tsx:216`.

None of these captures the server's output during the journey, and the journey run is opt in and outside CI.
**Why it matters**: The evidence exists but is spread out, and part of it never runs in CI. A reader of the review package could conclude that the integration test proves AC-13.
**Suggested fix**: Name these exact tests in the review package as the AC-13 evidence, or add one case to `booking-details.test.ts`. That case would spy on `console.*` while running P9 and P10 through the real routes with an analytics session header, then assert that no token, code or verification id appears in the logs or in `SiteEvent`.

## Nits

- ⚪ `src/presentation/features/booking/phone-verification-step.tsx:214`: the token deadline is "receipt + 30 minutes", which is a little later than the server's real `expiresAt`. A token near its end therefore looks valid for a moment after the server has expired it. T6 handles `401 PHONE_NOT_VERIFIED`, but the `codeDeadlines` method (server lifetime minus the elapsed time implied by `expiresAt`) would keep the two in step.
- ⚪ `src/presentation/features/booking/phone-verification-step.tsx:235-243`: a `RATE_LIMITED` answer from P10 shows a message, but "Verify code" stays enabled, so repeated presses keep reaching the confirm limiter. Consider the same wait used for sending.
- ⚪ `src/presentation/features/booking/phone-verification-step.tsx:340`: `aria-invalid` on the code input is set by any problem, including a failed resend. The input also has no `aria-describedby` that points to the alert. Mark it invalid only for code errors, and link the message.
- ⚪ `src/presentation/features/booking/guest-details-form.tsx:209`: `autoComplete="tel-country-code"` autofills a calling code such as `+20`, but the option values are ISO codes (`EG`), so autofill never matches. Use `autoComplete="off"` or `country`, or accept both forms.
- ⚪ `tests/e2e/support/booking.ts:57-60`: `setKnownCode` repeats the HMAC input layout of `NodePhoneVerificationCrypto`. If that layout changes, only the opt in journey run fails, and that run is not in CI. A comment pointing to the crypto file, or a shared helper, would make the link clear.
- ⚪ `src/presentation/features/booking/hotel-contact.tsx:14`: the props are not `Readonly<…>`, unlike the components around it.
- ⚪ Documentation to sync at acceptance: `docs/specs/0007-m10-guest-booking-journey.md:357` still describes `GetBookingSearchSetup` as current. `src/app/api/AGENTS.md:15` should say that the details page shares `QUOTE_RATE_LIMIT` through `consumePublicRateLimit`, as it already says for the search page.

## Security and integrity checklist (Critical tier)

- **Branch scope**: the page resolves the branch with `requireBranch`, reads setup by `branch.id`, and quotes with `branchSlug: branch.slug` (`page.tsx:67-95`). No client branch value is trusted. The draft key is scoped to the branch, and the redirects are built from server values only. No open redirect.
- **Prices**: the summary renders P6's `QuoteView` on the server. No total is computed in the browser, and `restoreUnits` only rebuilds which units were chosen.
- **Tokens and personal data (AC-13)**: the token and verification id stay in `JourneySteps` state. `saveDraft` writes exactly five fields. The address carries dates, slugs and counts only. `notice` is a closed enum mapped to fixed text. The only log line records the error class. A blocked number clears the draft (spec 0007 decision 11).
- **AC-14**: `GetBookingSetup` offers email only with online payment and email ready, and the page also requires `paymentMethods` to include `ONLINE` (`page.tsx:136-139`). The client still handles `EMAIL_NOT_CONFIGURED`.
- **Abuse and limits**: the server quote takes the P6 bucket (`booking-details.ts:29-35`, covered at 60 + 1 in the integration test). P9 and P10 keep their own limits. Double presses are blocked by a `busy` ref in both forms.
- **Failure inputs**: an array or repeated query value, a malformed `u`, more than 5 units, an unknown slug (P6 `VALIDATION` → results with `notice=selection`), a sold out unit (→ `notice=unavailable` with the basket rebuilt), a database error (→ retry panel), and booking switched off (→ contact panel before the address is read) are all handled and tested.
- **Providers and production guard**: no provider names appear in the UI or contracts beyond the channel enum. Fake providers are enabled only in the opt in `BOOKING_JOURNEY_E2E` run on `next dev`. The production refusal of `fake` is unchanged.
- **Bundles**: verification and the phone library are split into separate chunks. The author measured the initial details script at 253,421 bytes, under the 260 KB gate. `selection-link.ts` imports no validator, and the server only modules (`details-query.ts`, `phone-countries.ts`) are not imported by client components.
- **Dependency rules**: application imports only through module index files, composition alone builds infrastructure, and presentation imports only types from application. Nothing breaks D-2 to D-8.

## Strengths

- One readiness rule. `GetBookingSetup` feeds the composed readiness it just read back into `verificationUsableForBranchNow`, so the search page, the details page and P7 cannot drift apart. It also skips the channel reads when the branch cannot book.
- Server deadlines do not depend on the device clock: `codeDeadlines` derives the resend wait from `expiresAt − codeLifetime`, and a unit test covers that. Binding the verification to the contact (`verificationFor`) matches P7. A WhatsApp proof survives an email change, and an email proof does not.
- Strong E2E evidence for AC-13. The journey test checks storage, cookies, the page HTML, request URLs, the console and the stored `SiteEvent` rows for the token, the code, the verification id and the guest's details.
- Accessibility is built in: an error summary that takes focus with links to each field, focus that follows the step, `role="status"` on code delivery, 44 px targets checked with radio labels counted, and a `<noscript>` contact fallback.

### Remaining nits (optional, not blocking)

- ⚪ `phone-verification-step.tsx:264`: a wait from the email channel can also come from the phone's history. P9 combines the phone and email checks (`phone-verification.ts` `combineLimits`), so three email codes fill the phone's 15 minute window too. In that case "Send by WhatsApp instead" stays enabled, and the server refuses it once before the WhatsApp wait applies. The client cannot tell the two sources apart. This follows the option I recommended, so the cost is one extra refused request at most.
- ⚪ `phone-verification-step.tsx:236`: when the server answers `VERIFICATION_EXPIRED`, or no attempts are left, `onChange({ sent: null, … })` drops the code's `resendAtMs`. If that was the third code in the window, the next "Send code" reaches the server once, gets `RATE_LIMITED`, and the wait is shown from then on. Keeping the latest `resendAtMs` in component state would avoid that request.
- ⚪ `phone-verification-step.tsx:411-415`: when only email is limited and the current code is by WhatsApp, "Send by email instead" is dimmed but has no description. The reason is shown only in the alert from the moment of the refusal.
- ⚪ `tests/integration/reservations/booking-details.test.ts`: `JSON.stringify(logged)` turns an `Error` argument into `{}`, so a secret inside an error message would not be caught. Mapping each `Error` to its `message` and `stack` before searching would close that gap.
