## Strengths

1. The page resolves an active branch on the server before rendering, at `src/app/(marketing)/[branch]/book/payment/page.tsx:14`. The client compares branch, reference, and payment method before displaying any server outcome, at `src/presentation/features/booking/payment-return.tsx:151`. A confirmed response for another branch or another reference therefore produces the neutral fallback.
2. The server remains the authority for payment results. `src/presentation/features/booking/payment-return.tsx:161` distinguishes `CONFIRMED`, `PAYMENT_FAILED`, pending, and other reservation states. Return query parameters are never read. A closed or cancelled booking cannot be shown as confirmed merely because a provider appended a success parameter.
3. Polling has one request in flight, skips missed time slots, and has an independent deadline. The next request is scheduled only after the current response, at `src/presentation/features/booking/payment-return.tsx:168`. The deadline aborts outstanding work at line 92, and cleanup cancels every timer and the request at line 200. A response that finishes after the deadline cannot overwrite the waiting screen.
4. Temporary failures stop automatic polling and offer a manual retry. The retry delay is honored and long browser timer values are bounded at `src/presentation/features/booking/payment-return.tsx:107`. Keyboard retry moves focus to the persistent result panel before the button disappears, at line 263.
5. The page reuses the existing G1 client, which puts the credential in the Authorization header and disables caching. No payment write, schema, provider adapter, server secret, or infrastructure dependency was introduced into the client. The shared details extraction preserves the existing server supplied price display at `src/presentation/features/booking/booking-details.tsx:25`.
