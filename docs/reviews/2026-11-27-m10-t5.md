# Review, m10-guest-booking-journey (M10-T5), 2026-11-27

**Reviewed by**: claude-opus-5-5 (independent reviewer; author on a different session/model)
**Scope**: 25 files (14 modified, 11 new; PNG screenshots excluded), uncommitted
**Verdict**: Approve with nits

## Summary
M10-T5 adds step 3 of the booking journey: an extras picker (breakfast, airport transfer with a car selector and flight details), one coupon field, and a live price panel. Every amount on screen comes from the latest P6 answer. The browser does no money arithmetic, and flight text, coupon codes and tokens stay in component state. I traced the price-checking state machine (`extras-state.ts`, `extras-answer.ts`, `extras-step.tsx`, `useDebouncedQuote`) through every server outcome, including abort and unmount/remount races. I found no stale price shown as current, no request loop, and no dead end on step 3. The remaining findings are small: a misleading "Updating price…" label beside other steps, focus lost when a service is withdrawn, an unpayable message that names a coupon that may not exist, and a few test gaps.

## Minor

### 🟡 Sidebar says "Updating price…" indefinitely while the guest is on another step, `src/presentation/features/booking/booking-journey.tsx:232-238`
**Problem**: Price checks run only while `ExtrasStep` is mounted. If the guest leaves step 3 before the current check answers, the request is aborted (correct) but the held extras stay unpriced. Example: tick Breakfast, then press "Back to verification" within the 250 ms debounce or while the request is in flight. The `PriceSummary` beside the verification and details steps then shows "Updating price…" with no request pending, for as long as the guest stays there. I confirmed this with a throwaway journey test (deleted). Zero calls were sent, and the label persisted on "Phone verified" and on the details form. Returning to step 3 resumes the check correctly.
**Why it matters**: It is not a wrong price (the table is hidden), but the page says it is doing work it is not doing. A guest re-verifying for several minutes sees a permanent spinner-like message. AC-3 ("every price shown comes from the latest server answer") is respected; the honesty of the status text is not.
**Suggested fix**: When step 3 is not mounted, label the unpriced state differently ("Price updates when you return to extras", or show the server summary). Alternatively, let the journey own `useDebouncedQuote` so the check finishes regardless of which step is visible. Add a journey test for "leave step 3 with a pending check, then come back".

### 🟡 Keyboard focus is lost when the server withdraws the service the guest just ticked, `src/presentation/features/booking/extras-step.tsx:99-103` (with `extras-answer.ts:107-113`)
**Problem**: On `SERVICE_UNAVAILABLE`, the kind is added to `withdrawn` and its checkbox is removed from the DOM. The guest usually has focus on that checkbox (they just toggled it), so focus falls to `<body>`. The notice is announced through the status region, but a keyboard or screen reader user loses their place.
**Why it matters**: WCAG 2.4.3 (focus order) and the task's keyboard criterion (AC 4). The rest of the step manages focus carefully (Check again → heading, Remove → coupon input, errors → field).
**Suggested fix**: When a withdrawal removes the focused control, move focus to the step heading or the notice (make the notice focusable with `tabIndex={-1}`). Assert it in the existing "removes a service the branch switched off" test.

### 🟡 Unpayable message always tells the guest to remove a coupon, even when none is applied, `src/presentation/features/booking/extras-step.tsx:288-291`
**Problem**: `unpayable` is `emailVerified && !paymentMethods.includes("ONLINE")`. Besides a zero total from a coupon, it also becomes true when online payment becomes unavailable after the page loaded. Example: staff turn off the branch's online payment, or the gateway readiness changes, and the next price check (say after ticking Breakfast) returns `["PAY_AT_HOTEL"]`. The guest has no coupon but reads "Remove the coupon or contact the hotel". The opening phrase "With a code by email you pay online" is also easy to misread as a coupon code.
**Why it matters**: The guest gets a wrong instruction at the step where they are blocked (Q-100 path).
**Suggested fix**: Mention removing the coupon only when `value.appliedCode` is set. Otherwise say online payment is not available right now and show the hotel contact. Reword the opening, for example "Bookings verified by email are paid online, and this total cannot be paid online." Add a unit case with no coupon applied.

### 🟡 Test gaps around the riskiest transitions, `tests/unit/public/booking-journey.test.tsx`, `tests/unit/public/extras-step.test.tsx`
**Problem**: The suite is strong (81 tests pass, run with `npx vitest run` on the 7 affected files), but some branching paths in the price state machine have no test:
1. Leaving step 3 with a pending price check or coupon check (`trying` set), then returning. Covers the abort on unmount, the resumed request, and the sidebar label above.
2. `NOT_FOUND` from P6 (branch deactivated) mapping to the "closed" hotel-contact state (`extras-answer.ts:41`). Only `bookable: false` is tested.
3. `RATE_LIMITED` while a new code is being tried on top of an applied one. "Remove coupon" then removes both codes (`extras-step.tsx:252-255` → `removeCoupon`), which is intended but unproven.
4. `SERVICE_UNAVAILABLE` arriving while a coupon is being tried. `trying` must survive so the follow-up check still carries the code (`extras-answer.ts:107-113` keeps it, which is correct).
**Why it matters**: These are the branches where a regression would leave a stuck "Updating price…" or silently drop a code. The test bar for this task asks for "every failure in the table above".
**Suggested fix**: Add the four cases. Each takes a few lines with the existing `Harness`, `refused()` and `answer()` helpers.

## Nits
- ⚪ `src/presentation/features/booking/extras-answer.ts:71` and `price-summary.tsx:68`. Destructuring `const { coupon } = quote` to avoid `persistence-boundaries.test.ts` matching `.coupon` is acceptable, since the test is a heuristic for Prisma delegates like `db.coupon.findMany`. It is fragile, though: the next author will trip on the same thing. Better to narrow that heuristic to delegate calls (`.coupon.<method>(`) or a Prisma-ish receiver, in a follow-up.
- ⚪ `src/presentation/features/booking/extras-answer.ts:98,112`. Only one `notice` is held. If a withdrawn service and an invalidated applied code arrive in consecutive answers (services are checked before the coupon on the server), the second message replaces the first visually. The removed checkbox and price panel still show it, so this is a rare edge.
- ⚪ `src/presentation/features/booking/extras-step.tsx:110-123`. Pressing Apply again on a code that was just refused, without editing it, resends it and spends one of the 20 coupon-bucket checks per 10 minutes. Remembering the last refused code and showing the reason again would protect the guest's budget.
- ⚪ `src/presentation/features/booking/selection-quote.ts:38`. `ExtrasStep` never reads `result`, so `setAnswer` causes one extra render per answer. Harmless. An `onAnswer`-only mode, or skipping the stored answer when a callback is given, would avoid it.
- ⚪ `src/app/(marketing)/[branch]/book/details/page.tsx:144-147`. The inline `money` helper repeats the `usd()` mapping already in `src/application/quotes/quote-display.ts`. Consider exporting that helper (or a `displayServices`) so the page keeps no DTO mapping of its own.

## Strengths
- The price state machine is small and sound. `priceKey(services, code)` plus `isPriced` makes "is this total for exactly what is chosen?" a single pure check. The server's own spelling of the code is written into the key (`extras-answer.ts:70-82`), so `save10` → `SAVE10` does not cause a second request. Every non-terminal answer changes a memo dependency (services, code, or `wanted`), so I could not construct a stuck or looping state on step 3.
- Abort handling is correct. Unmount and replaced requests abort, `ABORTED` is ignored, the client's own timeout reports `NETWORK` rather than `ABORTED` (verified in `request.ts`), and `useEffectEvent` keeps the reporter fresh without re-running the effect. A refused new code keeps the earlier applied code and its total (CP rules, AC-4). An applied code that stops working is dropped with its reason and re-priced.
- No browser money arithmetic, no flight text in price checks, and nothing in storage or the address. These are proven in unit and E2E tests, and the E2E covers the real database with keyboard, 320 px and axe checks. `Object.hasOwn` guards the refusal table against prototype keys (tested with `constructor`). The stale table uses `invisible`, so old figures are hidden from assistive technology too.

## Test coverage
Covered well: nothing preselected, unit wording and child price, car range, flight text never sent, latest-answer-wins with abort, Continue disabled while stale, every coupon refusal reason, same code twice, empty code, typed-but-not-applied code, applied code invalidated, service withdrawn (asked and not asked), car limit, network/internal/unexpected errors, rate limit with and without a code, unavailable/selection/closed (bookable false), email-verified unpayable, choices kept across steps and re-verification, the page's plain-money props. The E2E covers real pricing of breakfast, 2 cars and WELCOME10, failures via route interception, and the email zero-total block.
Untested: leaving step 3 mid-check and returning, P6 `NOT_FOUND` → closed, rate limit while trying a code over an applied one, service withdrawal during a coupon try, focus after withdrawal, unpayable without a coupon. One throwaway test was written under `tests/unit/public/` to confirm the first Minor and was deleted.

### New observations from the fixes (nits only, nothing blocking)
- ⚪ `booking-journey.tsx:151-157`. Off step 3, a **terminal** problem (`unavailable`, `selection`, `closed`) also reads "The price updates when you return to extras." On return, the guest sees the problem instead of a price. Consider showing "The price needs checking." for any `problem`, and the "return to extras" text only for an unpriced state without a problem.
- ⚪ `extras-step.tsx:126-132`. Pressing Apply again on a refused code writes the same `couponError` string. React makes no DOM change, so the `role="alert"` does not announce again. The field's description is still read when focus moves to it, so this is acceptable. The remembered refusal also blocks a retry of a time-dependent reason (`NOT_YET_VALID`, a re-activated code) until the guest edits the field. The new test documents this as intended.
- ⚪ `extras-step.tsx:97-99`. The focus fallback also fires if focus happens to be on `<body>` for an unrelated reason (the guest clicked the page background) when a service is withdrawn. This is harmless and arguably helpful.

No new Minor or Major issue was introduced. The price state machine's invariants still hold: every non-final answer changes a request memo dependency, and the new `refused` and `notice` fields are not part of the price key.
