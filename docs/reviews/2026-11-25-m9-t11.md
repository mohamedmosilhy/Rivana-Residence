## Summary

M9-T11 compares the proposed total with the successful payment, saves a price-changing proposal without changing the booking, and links the approved change to a staff decision. Four findings affect release compatibility, request contention, staff notes, and the documented API errors.

## Major

### 🟠 A staff refund can lose its guest notification across a release, `src/application/reservations/complete-refund.ts:228`

**Problem**: The backfill reads staff cancellations present when the migration runs. The previous release can still insert a cancellation with a populated `decisionReason` and null new columns while the next release builds. The new refund worker interprets null as a decision to stay silent and records `OTHER` as the reason. In the opposite direction, a rolled-back worker reads only `decisionReason`, which the new writer leaves null. The deploy sequence explicitly runs the migration before switching the release and retains previous releases for rollback in `docs/operations/deployment.md:48`.

**Why it matters**: A successful refund can leave the guest without the cancellation message that staff selected. The cancellation audit can also lose the staff member's reason code.

**Suggested fix**: Bridge both writer formats across the release window. Preserve the staff's choice for previous-release readers, and recover the submitted reason and notification choice for previous-release writes made after the backfill. Exercise the populated upgrade, an old writer after migration, and a previous-release reader on a new staff request.

### 🟠 Request-only submissions acquire every listing lock, `src/application/reservations/guest-reservation-changes.ts:413`

**Problem**: G6 acquires listing locks through `InventoryGuard` before distinguishing a price-changing request from an immediate paid change. Even a confirmed total that already differs from the captured amount takes the same hotel inventory locks as a sale. Spec 0006 Decision 5, line 143, reserves listing locks for paths that can consume inventory.

**Why it matters**: A pending sale can make a guest's request to join the staff queue time out with `TRY_AGAIN`. A request-only submission can also delay sales for the original and requested listings.

**Suggested fix**: Use the captured amount and expected total to select a request-only transaction. Recheck the actual capture, quote, eligibility and availability under the reservation lock. Only the listing-locked path may ever apply a booking change. Hold a real listing lock in a separate connection and prove the request commits while that lock remains held.

### 🟠 The approval endpoint silently discards the staff note, `src/application/reservations/decide-change-request.ts:339`

**Problem**: S57 accepts and validates an optional note, then stores only `noteProvided`. The shared approval contract defines the note as internal audit information, and S18 persists it in the protected audit reason.

**Why it matters**: A manager can successfully approve a request believing the desk or an auditor can retrieve the rationale. The original text is absent from every saved record.

**Suggested fix**: Store the validated note in the approval audit's protected reason field, just as S18 does. Assert the saved value and its absence from the request DTO, guest emails, WhatsApp messages, and public history projections.

## Minor

### 🟡 The staff decision error lists disagree with the runtime, `src/contracts/api/v1/routes.ts:546`

**Problem**: If an added service is withdrawn between submission and approval, repricing returns `SERVICE_UNAVAILABLE`. S57 persists that conflict and returns the error, but its OpenAPI entry omits the code. Both S57 and S58 advertise idempotency-key errors even though neither handler reads that header. S58 also advertises an inventory error for a rejection.

**Why it matters**: A staff client using the contract cannot reliably distinguish a withdrawn service from other failed approvals.

**Suggested fix**: Build the route error lists from staff decision errors, add the actual repricing errors to S57, and regenerate OpenAPI. Cover service withdrawal with a saved open conflict and an unchanged booking.

## Strengths

- Approval commits an inventory or price conflict before returning the HTTP error. A change to a lower price receives the same protection as an increase.
- The transactional reservation lock serializes request types and terminal decisions. Approval, the linked change history, audit, updated booking, and outbox share one transaction. Paid cancellation closes the request before dispatching the refund.
- Guest-facing request records and staff queue summaries omit proposed contact values and service details. The reservation's captured amount stays intact after an approved total change.
