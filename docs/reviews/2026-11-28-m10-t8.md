## Minor

### 🟡 Sign out keeps the manage link key in this tab, `src/presentation/features/booking/my-reservations.tsx:200`
**Problem**: "Sign out" calls `end()`, which clears only `rivana.access.session`. If the guest also opened a private link in this tab, `rivana.access.manage` stays in tab storage. So does `rivana.booking.result` (with its manage token) if they booked in this tab. A later visit to `/reservations/manage` in the same tab opens that booking again with full contact details and the cancel button.
**Why it matters**: Decision 5 is justified as "it clears the access from this tab, useful on a shared device". A guest who signs out on a shared device can reasonably expect that nobody else in the tab can open their booking. Today that is true only for the session.
**Suggested fix**: Either have sign out also call `forgetManageToken()` (and drop the booking result key), or narrow the sign out copy so it does not promise more than it does. This is the owner's call. The first option matches the decision's stated reason.

### 🟡 Refusal detection trusts bare 401 and 404 statuses, `src/presentation/features/booking/use-guest-reservation.ts:17`
**Problem**: `accessRefusal` treats any answer with status 401 or 404 as "the key is gone", including `UNEXPECTED_RESPONSE`, the code `request.ts` gives to a non-API body such as a proxy or CDN error page. On the manage page that runs `forgetManageToken()` and shows "Open your booking link". The guest then needs the message link again even though the key is still valid.
**Why it matters**: A brief misrouting during a deploy, or a protected staging proxy, would make guests lose access in the tab for a reason that has nothing to do with their key. It does not leak anything, but the wording would be wrong.
**Suggested fix**: Map refusals by API code (`UNAUTHENTICATED`, `PHONE_NOT_VERIFIED`, `NOT_FOUND`, `PHONE_BLOCKED`), not by status alone. Leave `UNEXPECTED_RESPONSE` on the retryable "Check again" path. Add one unit test for a 404 `UNEXPECTED_RESPONSE`.

### 🟡 Session-mode branches of the shared code screen are untested, `src/presentation/features/booking/phone-verification-step.tsx:291`
**Problem**: The new `purpose="GUEST_SESSION"` branches have no tests:
- the `help` slot that replaces `HotelContact` when there is no single hotel (both the "cannot be sent" panel and the channel alert);
- the "A code cannot be sent right now. Contact the hotel about your booking." copy;
- "Change your phone or email" returning to the form with the typed values kept.

A small fallback in `reservation-view.tsx:215` ("Online cancellation is not available…") and the empty `HotelContacts` text (`hotel-contacts.tsx:12`) are also uncovered. The existing step tests pass unchanged, as the card required. I ran 139 tests across 4 files and all passed.
**Why it matters**: The `help` slot carries the only way to reach a hotel when the chosen channel turns out to be unconfigured. If `help` is missing, nothing renders, and TypeScript cannot catch that because both props are optional.
**Suggested fix**: In `my-reservations.test.tsx`, add a case where P9 answers `WHATSAPP_NOT_CONFIGURED` and assert that every hotel's name and the session copy show. Add a case that presses "Change your phone or email" and checks the phone field keeps its value. Consider a type that requires `contact` or `help`.

## Strengths

- **Fragment handling is careful and proven.** `takeManageLink` removes the key with `replaceState` only after a deferred tick, so Next's patched `history.replaceState` (checked in `node_modules/next/dist/client/components/app-router.js:302`) is installed first and syncs the router's `canonicalUrl`. The E2E journey proves the key does not come back after a reload, a client navigation and Back. The same journey checks that no key appears in request URLs, console output, the DOM, cookies, `localStorage` or `SiteEvent` rows.
- **Stored values are validated on read.** Both stored keys are checked against the server's token format (`/^[A-Za-z0-9_-]{43}$/`). A broken link clears the stored key ("never falls back to an earlier booking"). Storage access is wrapped so a blocked `sessionStorage` still works from memory.
- **The cancellation flow handles every outcome.**
  - There is no abort signal on the write, so leaving the page cannot make a sent request unknown.
  - Rate limit and busy refusals keep the form and the typed reason.
  - Every other outcome, including no answer, re-reads the booking before another try.
  - If that re-read fails too, the button stays hidden behind "Check again".
  - Server refusals map to plain words.
- **The server decides what the guest can do.** The button depends only on `allowedActions`. The device clock picks a sentence and nothing more. `noCancellationReason` never mentions blocking, and a test asserts that. Money is only formatted (`formatMoney`).
- **The session expiry is safe.** It is computed from the device time before the code check plus the token lifetime, so the page never trusts a session longer than the server does. The server's 401 also ends it.
- **Hotel data stays public.** The server parts of both pages pass only public branch facts. `HotelContact contactPage` avoids linking to a deactivated branch's 404 contact page.
- **No contract change.** The pages reuse the T1 typed client and the T4 code screen.

## Security and integrity checklist (critical tier)

- **Keys in addresses**: none. G4 puts the booking reference in the API path (not a secret). The manage key is removed from the address at once, and the session token never reaches the address bar (unit and E2E asserted).
- **Keys in logs or analytics**: `request.ts` logs nothing. The unit tests spy on every console method. P11 already strips query strings and fragments. E2E asserts no key in `SiteEvent`.
- **Authorization and ownership**: decided by the server (G1 to G4, `lockGuestBooking`). The client only shows what comes back. A wrong reference in a session gets a 404, which becomes "That booking is no longer in your list."
- **Cross branch**: the pages belong to no branch. The branch list is used only for contacts and stay hours. No client branch value reaches the server.
- **Concurrency**: a second open request is refused by the server (`CANCELLATION_REQUEST_EXISTS`). A double submit is blocked in the client by a ref plus a disabled button (unit tested). A lost reply forces a re-read.
- **Failure inputs**: busy (429 with `Retry-After`), offline, 5xx and non-API answers are all handled. See the second Minor finding about 401 and 404 non-API bodies.
- **XSS**: everything renders as React text, including the staff's `decisionReason`. No `dangerouslySetInnerHTML`.
- **Search engines**: both pages are `noindex, nofollow`. `reservations` is already a reserved branch slug.
- **Accepted trade-off**: keys in `sessionStorage` (decision 1, and the spec allows it). See the first Minor finding about sign out.
