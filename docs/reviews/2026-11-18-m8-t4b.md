## Major
### 🟠 Controlled selects and the Active checkbox revert after a failed save, so the next submit posts other values, `src/presentation/admin/whatsapp/template-form.tsx:101`
**Problem**: Purpose, language, category, and Active are controlled by state (lines 101-104, rendered at 218-226, 242-249, 279-286, 401-408) and also carry a `name`, so `FormData` reads them from the DOM. With a function `action`, React 19.2 calls `requestFormReset` on every submit and runs `form.reset()` at the end of the commit that delivers the action result (react-dom `recursivelyResetForms`). Nothing restores controlled values after that reset. A select goes back to its `defaultSelected` option (the server rendered value on a full load, or the first option when the form mounted on the client, as it does after clicking Edit), and the checkbox goes back to the `defaultChecked` set at mount. State keeps your choice, and no re-render follows a failure to fix the DOM. I reproduced it with the real component in jsdom: edit a BOOKING_CONFIRMED template, pick "Reservation modified", untick Active, submit, get an error. After the error the DOM shows purpose VERIFICATION_CODE, category AUTHENTICATION, Active ticked; the second submit posts `VERIFICATION_CODE / AUTHENTICATION / active=on / variables [reference]`.
**Why it matters**: The variables list and the "Add a variable" choices still follow the state purpose, so the screen contradicts itself. Many combinations are refused by the server with a confusing error, but some save silently: Active flips back on, or a purpose with the same allowlist (BOOKING_CONFIRMED, RESERVATION_MODIFIED, CHANGE_REQUEST_APPROVED all use the stay keys) is saved as the reverted one. The task's acceptance criterion "forms keep typed values after an error" is not met for these fields. The existing forms avoid this: `catalog-form.tsx` restores checkboxes from `state.values`, and `social-links-form.tsx` submits its controlled rows through one hidden input.
**Suggested fix**: Send the controlled values through hidden inputs (React keeps a hidden input's value attribute in sync, so reset does not touch it) and remove `name` from the visible controls, then force one re-render after an error (for example an effect on `state` that updates a small counter) so the visible controls show state again. Add a unit test that changes purpose and Active, fails a save, resubmits, and checks the second `FormData` and the visible select values.

## Minor
### 🟡 The chosen test template is not restored after a failed send, `src/presentation/admin/whatsapp/test-message-form.tsx:81`
**Problem**: The select is uncontrolled and passes `defaultValue={state.values?.templateId}`. React only applies a select's `defaultValue` at mount; a changed `defaultValue` on update is ignored, and `form.reset()` then selects the original default option. Confirmed in jsdom: choose a template, fail, and the select reads `""` again. The next send uses the default TEST template instead of the one you picked.
**Why it matters**: A silent switch of which template is tested; low harm, but the code says it restores the choice and it does not. (`branch-form.tsx:180` has the same latent pattern; out of scope here.)
**Suggested fix**: Key the select on the submission (for example `key={state === idleFormState ? "idle" : JSON.stringify(state.values)}`) so it remounts with the restored default after the reset, or make it controlled with a hidden input as in the Major.

### 🟡 Keyboard focus is lost when a variable moves to the first or last place, or when the last variable is added, `src/presentation/admin/whatsapp/template-form.tsx:175`
**Problem**: After a move, focus goes to the same direction button at the new index. At index 0 the "Move up" button is disabled, and at the last index "Move down" is disabled, so `focus()` does nothing and the browser drops focus to the page body (the button that had focus also becomes disabled). The same happens at line 156 when adding the last allowed variable disables the "Add a variable" select. jsdom does not model this, so the unit test passes.
**Why it matters**: The task asks for keyboard reorder; a keyboard or screen reader user loses their place on the most common moves. The pattern this was copied from handles it: `social-links-form.tsx:124-127` sends focus to a field when the target button would be disabled.
**Suggested fix**: Fall back to the other move button (or the row's Remove button) when the target is first or last, and to the variable list or the preview field when the add select becomes disabled.

### 🟡 A successful test does not show the provider message id, `src/app/admin/(protected)/settings/whatsapp/actions.ts:70`
**Problem**: The task card (Behavior, Test panel) says the screen "shows provider message id on success". `actionResult` drops the result value and the toast only says "Test message sent. Check the phone."
**Why it matters**: The id is what you would quote to Meta support when a message is accepted but not delivered. Either the card or the code should change.
**Suggested fix**: On success, include `result.value.providerMessageId` in the success message, or record with the owner that it is dropped.

### 🟡 The "already active" conflict has no inline error on the Active checkbox, `src/presentation/admin/whatsapp/template-form.tsx:400`
**Problem**: The use case returns the one active per purpose and language conflict under the `active` field (`manage-whatsapp-templates.ts:59-61`). The summary links to the checkbox, but the checkbox renders no error text and has no `aria-invalid`, unlike every other field in the form.
**Why it matters**: After following the summary link, a screen reader user lands on a checkbox that announces only its hint, not the problem.
**Suggested fix**: Render `fieldErrorsFor(state, "active")` next to the checkbox with an id, add it to `aria-describedby`, and set `aria-invalid` when present.

### 🟡 New branching logic is not covered, `tests/unit/admin/whatsapp-forms.test.tsx:98`
**Problem**: No test covers the add form's reset after success (the state during render block, template-form.tsx:118-128), a resubmit after a failure (which would have caught the Major), the rate limit message in `sendWhatsAppTestAction` (actions.ts:76-87), or the test form's error summary mapping. The card's E2E plan also listed one UI assertion that the branch screen refuses online booking while WhatsApp is not configured; it is not in `admin-whatsapp.spec.ts`.
**Why it matters**: These are the paths most likely to regress, and the reset behavior is exactly where the bug sits.
**Suggested fix**: Add jsdom tests for the success reset, the failed resubmit, and the test form's rate limit and not configured messages (an action stub returning each error), and either add the branch screen assertion or note in the evidence that integration covers it.
